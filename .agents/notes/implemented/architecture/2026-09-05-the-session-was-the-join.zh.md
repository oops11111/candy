# Agent Note: The session was the join

Status: implemented

[English](2026-09-05-the-session-was-the-join.md) | 中文

## Problem

`RunScheduler.meter` 为一次运行的模型调用设了界，而没有任何东西调用它。要把它接上去，看起来需要模型请求上带一个 run id，而 `GenerateOptions` 不携带任何 Candy 概念 —— 加一个进去，会让单独一个消费方去支配整个 `dsh-llm` 缝隙共享的一份契约。此前三份备注都以这个理由推迟了这次接线，称它是那个缝隙没有概念的归属信息。

它有。`GenerateOptions.sessionId` 由循环打在每一个被组装的请求上，而执行断言本来就指名了它那次运行所驱动的会话。`dsh-session-checkpoint-policy` 自打存在起，就一直用这个字段挑出属于它自己的那些流。

## Decision

一次运行的持久记录指名它的会话，而调度器注册一个 `llm/stream` 监听器，把请求记到其会话所指名的那次运行头上。

映射住在记录里，因为运行的身份本来就住在那里，也因为一个要挺过重启的查找不可能是内存里的索引。存储上的 `runsOfSession` 就是它的全部。

一个不带会话的请求，或者一个指名了本运行时并无开启中运行的会话的请求，会原样通过。它不归本运行时计费：一次为无人准入过的会话所做的标题生成、一个同时也跑非 Candy 工作的部署、另一个运行时的会话。

一个被两次开启中运行同时认领的会话会被拒绝，并给出一个终止的 `error` finish。控制平面为一个会话铸出了两次运行，而记到查找先找到的那一个头上是一笔谁也不会察觉的错账 —— 这里唯一一种租户无法察觉的失败。停下这次调用才是那种看得见的。

## Consequences

一个跑在某次运行的会话上的 agent 会被计量，而无需任何人把 run id 穿过任何东西：`ctx.llm.stream(request)` 会被记到那次运行头上，在该运行什么都不剩时被拒绝，在调用跑过它的挂钟时间时被切断。组合测试让一个真实请求穿过真实的 `LlmRuntime` 瀑布流，打到一个已注册的适配器上，因此这条路径就是产品的那一条，而不是它的替身。

监听器注册在服务自己的上下文上，并随它一同消失：销毁测试把调度器挂在它自己的 fiber 上、销毁它，并观察到下一个请求原样通过、未被计费。

这件事没有做到的，是为没有会话的工作归属。一次在自己会话之外花钱的运行 —— 一个被启动的提供方进程、一个向外调用的工具 —— 不会被它触及，而边界页所要求的那条启动审计记录仍然没有产出者。

## Alternatives considered

**在 `GenerateOptions` 上加一个 `runId`。** 最直接的路线，而它会让一个继承来的缝隙去承载一个只有 Candy 才有的概念。其他每一个适配器与消费方都会看到一个对它们毫无意义的字段。

**把监听器限定到 agent 的上下文里。** `AgentFactory` 的 `setup` 组装 agent 的作用域世界，本该是天然的归宿。瀑布流是针对 `LlmRuntime` 自身派发的，因此一个被限定的监听器无论如何都会收到进程里的每一条流 —— 那种限定只是装饰，而真正做出挑选的是 `sessionId` 检查。

**会话有歧义时记到找到的第一个运行头上。** 那让调用继续可用。它也会在任何地方都没有信号的情况下，让一个租户为另一棵树的工作买单，而那正是整条租户边界所要防止的结果。

**等一个能从被准入运行组装出 agent 的东西。** 那个组件仍然不存在，而这件事恰恰需要它不存在也能成立：harness 的循环本来就打上了会话，因此对于随后来建它的人，强制执行已经就位。
