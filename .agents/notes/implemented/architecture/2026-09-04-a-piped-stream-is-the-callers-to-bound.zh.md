# Agent Note: 一条被 pipe 出来的流，由调用方来界定

Status: implemented

[English](2026-09-04-a-piped-stream-is-the-callers-to-bound.md) | 中文

## Problem

[Candy 运行时边界](../../../../docs/candy-runtime-boundaries.zh.md)把输出限制列为阻断进程逃逸的手段之一。Claude CLI 这条路由一个都没有。

它以 `stdout: 'pipe'` 启动子进程，而子进程缝隙对这个模式的说明是：把「原始 `Readable` 交给调用方做协议解码」—— 调用方解码它，因此也由调用方界定它。这条路由解码了，却没有界定。读进来的每一个字节都会被累积：在一行尚未结束时累积进 `ClaudeCliLineDecoder` 的那半行，在它的帧解析成功后累积进一个内容块。仓库里另一条子进程路由早就把这件事做对了 —— `dsh-bash-local` 有一个经校验的 `maxOutputBytes`，默认 64 000 —— 于是两条承载子进程输出的路由里，一条既有界又可配置，另一条两样都没有。

这条路由上也没有别的东西界定响应长度。CLI 没有输出 token 的开关，因此 `projectRequest` 会拒绝 `maxTokens`，而不是把它传下去。一次运行的输出，只受提供方愿意吐出多少的限制，而它跑在一台与其他租户共享的运行时上。

## Decision

`maxOutputBytes` 界定一次运行可以写出的 stdout：它是一个经校验的 `Config` 字段，默认 16 MiB，同时是 `ClaudeCliAdapterOptions` 与 `ClaudeCliDeployment` 上的必填字段。把它做成必填而不是可选，才补上了这个洞的后一半：为某个租户组装这个适配器的那份绑定，在缺了它的情况下也能编译通过，而一个缺席的上限与任何字节计数比较都为假 —— 于是这个界限恰恰会在它为之存在的那条多租户路径上被静默关闭。

按字节，不按码元。`stdout.setEncoding('utf8')` 产出的是字符串，因此 `chunk.length` 计的是 UTF-16 码元，而这样读出来的上限，最多会放进它所承诺持有量的四倍。

超过它会终止进程并让这次运行失败，而不是截断。截断适合模型要读的工具结果，这也正是 `dsh-bash-local` 保留尾部的原因；对协议流则不适合 —— 一个写了一半的帧根本解析不了，而一个被截短的响应本来会被当作完整的交付出去。这次终止是显式写出来的，因为这个生成器在那条路径上是正常返回的，于是 `runProcess` 会把这次运行当成已完成，什么也不去回收。

默认值有依据，而不是靠一个整数好看。录制到的该 CLI 运行，把一次简短的文本对话装在 8 KB 的 stdout 里，最长的一行 2.2 KB。唯一会增长的项是响应文本，它在 `result` 帧里被带一次，在各个 `stream_event` 增量里又被带一次，因此 stdout 大约是文本的两倍再加上 JSON 转义 —— 一个最大的单次响应仍在约一兆字节以内。16 MiB 留出了一个数量级以上的余量，同时仍然界定住失控的情况。

## Consequences

一个没有指名上限的组合会得到一个。知道自己上限的部署可以从 `cordis.yml` 设置它，而控制平面的绑定把它作为一项主机事实，与可执行文件和终止宽限期并列携带。

触到上限的运行会以一个携带 `OUTPUT_LIMIT` 的 `finish` chunk 结束，那是一次普通的适配器失败：缝隙的「恰好一个终止 chunk」保证依然成立，而一次在溢出之前就已经完成的运行，保留它自己产出的那个终止 chunk。

## Alternatives considered

**改为界定 `ClaudeCliLineDecoder` 的半行缓冲。** 那是更窄的修法，而且会漏掉同样要紧的情形：一百万个格式良好的小帧永远不会让那半行变长，却照样耗尽运行时。对读进来的量计数，可以在一处覆盖两者。

**改用缝隙的 `SubprocessCollect` 模式收集 stdout。** 那个模式有界地缓冲并交回偏移量，适合事后读取结果的调用方。这条路由是边到达边解码一条流，而该模式在溢出时保留的是尾部 —— 对一条协议流来说，那是错的那一半。

**截断，并让这次运行正常结束。** 那会把一个不完整的响应当作完整的交付出去。失败才是诚实的结果，而约定测试套件本来就覆盖了适配器对一次失败的运行欠下什么。
