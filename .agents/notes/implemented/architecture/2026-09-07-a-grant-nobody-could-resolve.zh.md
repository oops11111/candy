# Agent Note: 一份谁也解析不了的授权

Status: implemented

[English](2026-09-07-a-grant-nobody-could-resolve.md) | 中文

## Problem

`WorkspaceGrantId`过去只是一个品牌化字符串,别无其他。在仓库里 grep 它,找到的是这个品牌自身的定义、`ExecutionAssertionClaims` 上的那个声明、`DurableRunRecord` 上承载它的那个字段,以及在通往存储的路上给它加上和去掉品牌的那些转换器 —— 没有任何读者。`dsh-run-admission` 一次都没有提到过它。

于是一次运行想指名哪份工作区授权就指名哪份,而没有任何一步会看。准入会拒绝一个指名了另一个租户或另一个账户的子代,因为父代各自只持有一个,这个不匹配是可裁定的;工作区授权则被留在了外面,还带着一条陈述过的理由 —— "收窄是合法的,而没有任何收容模型可以把它与放宽区分开来" —— 那句话对*比较根目录*而言是对的,却悄悄变成了"什么都不检查"的理由。授权上的租户没查,设备没查,是否已被吊销没查,是否存在也没查。

而这是子代所继承的三份授权里最宽的一份。租户与账户决定花谁的钱;工作区授权决定进程能碰到哪些文件。一个被委派的子代可以指名一份属于另一个租户的授权,或者一份运维人员一小时前就吊销掉的授权,并带着它被准入。

## Decision

授权成为一条持久记录,而准入在消费 nonce 之前解析它。

`dsh-workspace-grant` 持有这个 id 所解析到的东西:它被签发给哪个租户与哪台设备、那台设备授予的根目录、以 `SandboxMode` 表达的文件效应上限 —— 那是 `dsh-sandbox` 已经拥有、且 `dsh-subagent` 已经用来钉住子代的词汇 —— 授权自身的修订号,以及它的吊销。`admitWorkspaceGrant` 裁定一次运行是否可以持有它,而 `dsh-control-plane-store` 把它存进控制面域,版本升到 6。

子代必须**精确**指名其父代的授权。相等是子集规则最强的形态:一个不能指名另一份授权的子代,既放宽不了它的根目录,也抬高不了它的模式,因此超额授予是不可能的而不是可检测的 —— 这正是 `dsh-run-budget` 对 token 与并发已经采取的形状。`RunScheduler.startChildRun` 本来就把父代的授权 id 复制进它铸造的断言,所以这条规则拒绝的是手工铸造的子代,而不是委派路径产出的任何东西。

**路径包含关系刻意不在这个包里。**一份授权的根目录是为签发它的那台设备拼写的,而判断一条路径是否落在其中一个之下,是那台设备的文件系统语义 —— 大小写、junction、符号链接、8.3 别名。Debian 上的控制面拿字符串去和一台 Windows 主机的根目录比较,只会是在近似一个它看不见的边界,而近似一次收容检查正是逃逸发生的方式。这里裁定的是身份与继承,而这两者在每台主机上都相同。根目录随 `AdmittedRun.workspace` 一起传递,好让拥有它们的那台设备在文件操作发生的地方去执行它们。

这次拒绝的次序排在世系检查旁边、nonce 之前。两者回答的是同一类问题 —— 给定父代所持有的,这次运行可以持有什么 —— 而且两者都是可恢复的:重新签发一份授权就是修复手段,而烧掉那个一次性令牌会让一份仍然有效的断言永久地被拒绝。

记录带上 `version`,是因为一份断言只指名一个 id。一次在运维人员收窄授权之前被准入的运行,与一次在之后被准入的运行,单看 id 无从分辨;因此准入把它读到的版本记在被准入的运行上,文件系统那一侧的检查拿它来比较,而不是默默认可这次运行当初拿到的东西。

吊销是一个被存下来的 `revokedAt`,而不是一次删除。一条被删除的记录读起来像是一份从未签发过的授权,而这与一份被撤回的授权是不同的事实,而运维人员读到的那次拒绝应当说出是哪一种。

## Consequences

现在每一次运行都要像它早已证明自己的租户与账户那样,证明自己的文件系统权限。多出了五种此前不存在的拒绝:解析不到任何东西的 id、已被吊销的授权、属于另一个租户的、属于另一台设备的,以及指名了其父代之外任何一份授权的子代。部署必须在任何运行开始之前签发一份授权 —— 没有隐含的授权,而一个一份都不持有的存储什么也准入不了。

这项检查是每次运行启动时的一次查找,落在凭据与预算本就来自的同一个存储上,并且不在按调用的路径上。

它不做的,是阻止一次运行写到它的根目录之外。准入裁定的是一次运行可以持有一份授权;今天还没有任何东西在文件操作处读 `roots`,也没有任何文件系统缝隙会查阅这条记录。链接逃逸、junction 与长路径是**那**项检查的验收标准,不是这一项的,而且它们属于授权所指名的那台设备。

也没有任何东西在签发授权。部署通过 `saveGrant` 手工写入记录:没有配对流程,没有运维界面,也没有在设备注册时创建一份授权的生命周期。

九个单元用例钉住这条规则,两个钉住可用性判定;六个真实组合用例在一个真实的 SQLite 后端存储与一个已启动的调度器上钉住这些拒绝,其中包括一个在父代只持有一份很窄的授权时、却指名了一份覆盖 `/` 的 `danger-full-access` 授权的子代,以及一次在授权被恢复后让同一份断言重新可用的拒绝。一个存储用例钉住一份授权及其吊销能跨重启留存。把这项检查从 `admitRun` 里去掉,会让其中六个失败。

## Alternatives considered

**拿子代的根目录去和父代的比较。**这是"其父代授权的一个子集"最直白的读法,被否决:它恰恰就是那种从控制面无法正确完成的跨主机路径算术。`dsh-fs-sandbox` 有一个真正的收容检查 —— `isPathUnder`,带有针对大小写与 8.3 别名的文件系统身份回退 —— 而它之所以正确,正是因为它运行在它所判定的那个文件系统上。在这里重新实现一个只看字符串的版本,会是一项在 Debian 上通过、在 Windows 上判断错误的检查。

**现在就为收窄建模,在授权之间加一条 `derivedFrom` 链接。**很有吸引力,而且这大概就是它未来的去向,但作为推测性设计被否决:本仓库没有任何东西签发收窄后的子代授权,因此这条派生将没有写入方,它的子集规则也没有任何能把它与相等区分开来的测试。当有消费方需要它时,那条派生记录由签发设备创建 —— 那台设备可以检查包含关系 —— 而本规则会接受它。

**把记录放进 `dsh-control-plane`,和 id 放在一起。**被否决:那个包是零依赖的身份词汇包,而授权的模式是 `SandboxMode`。在那里加一条通往 `dsh-sandbox` 的边,会把 sandbox 包拉进每一个碰到品牌化 id 的地方。

**把授权检查放在额度之后,保持既有次序。**被否决:一次没有文件系统权限的运行不该去查询一份它用不上的额度,而这两项继承检查读的是同一次父代查找。把它们排在一起,也正是让 `findParentIdentity` 只被调用一次而不是两次的原因。
