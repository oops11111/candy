# Agent Note: 每个 spawner 都经由同一条缝隙上报

Status: implemented

[English](2026-09-06-every-spawner-reports-through-one-seam.md) | 中文

## Problem

边界文档要求为每个被启动的提供方或工具进程留一条审计记录。而本仓库里没有任何 spawner 发出过这样的记录——不只是 Candy 运行所启动的 Claude CLI,harness 自己的 bash、pwsh 与语言服务器子进程同样没有。这道缺口缺的是生产者,不是消费者。

把记录加到每一个 spawner 里,恰恰是那种保证下一个 spawner 会忘记的形态。`dsh-subprocess` 是它们全都必经的缝隙,而它把 `spawn` 与 `spawnTerminal` 声明为抽象方法,因此它自己没有任何可以上报的位置。

## Decision

`spawn` 与 `spawnTerminal` 现在是这条缝隙自己的方法。它们发出 `subprocess/launched`,并委托给由实现覆写的 `spawnProcess` 与 `spawnTerminalSession`。一个 spawner 无法在不自报的情况下启动子进程,因为自报的那一半根本不是它写的。

记录指名可执行文件、工作目录、pid,以及子进程是否拥有一个终端。它既不指名参数,也不指名环境:一个 spawner 的 argv 里装的是调用方放进去的任何东西——一段模型提示词、一个作为命令行开关传入的凭据——而环境正是凭据所在之处。一条关于启动的记录,绝不该成为两者外泄的途径。

pid 为 `-1` 表示这次启动失败了。这条缝隙无论如何都会返回一个句柄,因此这条记录是在报告一次没有发生的启动,而不是干脆不存在。

## Consequences

仓库中的每一个受管子进程,现在都能从同一个监听器观察到,包括那些不由任何 Candy 包启动的。

有八个类改用了新的方法名:两个生产运行时和六个测试桩。这次改名正是让这条记录无法被遗忘的原因,而它就是全部代价。

反向对照——去掉那次 emit——让两个新测试都失败。其中一个会启动一个真实进程,并在参数里放一个秘密,断言记录中不含它,因此载荷的"沉默"是被钉住的,而不只是被描述的。

**目前刻意还没有任何消费者。** 显而易见的消费者是 Candy 的审计踪迹,而把每一次启动都归档进去是错的:踪迹是按主体有界的,一个繁忙的运行时每次工具调用就启动一个子进程,而那些记录会把被拒断言的记录挤出去——那正是踪迹里最锐利的信号,也会把折叠刚刚修好的那次泛滥问题重新弄坏。归属也仍然缺失:这条缝隙对租户与运行一无所知,而一次 spawn 没有可供连接的会话。消费者要等编排层的连接点,也要等一个关于"高频记录该放在哪里"的决定——那个地方不该是同一扇有界的窗。

## Alternatives considered

**由每个实现各自发出。** 两个生产运行时并不算多,但未来的每一个都是一次忘记的机会——而本仓库正是这样走到"一条记录也没有"的。

**把参数也记下来。** 调查一次启动的运维人员想要它们,而它们恰恰是凭据或用户提示词最可能待着的地方。有理由、也有安全去处的消费方,可以在它自己那一层去捕获。

**改为发出一个会话事件。** 会话事件是给模型能看到的东西用的,而"可从会话日志重建"是它们的契约。一次启动是运行时的观察,没有模型可见的那一半,因此一个普通的上下文事件才是诚实的那一类。
