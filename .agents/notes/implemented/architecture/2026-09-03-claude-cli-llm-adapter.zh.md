# Agent Note: 把 Claude CLI 作为一条 LLM 路由，以及它拒绝什么

Status: implemented

[English](2026-09-03-claude-cli-llm-adapter.md) | 中文

## Problem

[多租户运行时计划的 R2](../../proposed/architecture/2026-09-02-multi-tenant-cli-agent-runtime.zh.md) 需要 Claude CLI 服务 `dsh-llm` 缝隙。协议部分已单独确定（[实测的流式协议](2026-09-03-claude-cli-stream-protocol.zh.md)）；剩下的是适配器 —— 进程生命周期、取消、清理 —— 以及协议工作暴露出来但没有回答的一个设计问题。

那个问题是缝隙发送的东西与 CLI 接受的东西之间的落差。`GenerateOptions` 携带完整对话、工具目录与生成控制项。CLI 的命令行接受一条位置参数提示词、一段系统提示词、一个模型和一个力度级别。没有任何东西能桥接它们，而假装可以的那些做法都会悄无声息地失败。

## Decision

`@deepseek-ai/dsh-llm-claude-cli` 注册一条路由，并拒绝它无法表达的东西。一次 `stream()` 调用就是一个 CLI 进程；适配器拥有该进程，而不拥有协议。

### 历史被拒绝，而不是被摊平

存在两个选项，都基于证据被否决。

通过 `--input-format stream-json` 喂入对话行不通：CLI 在那里只接受用户消息，而一次录制的两条消息输入产出了**两个回合、两个终止帧**。它是一个会话协议，不是历史回放，无法服务一次模型调用。

把对话渲染成提示词文本在机械层面可行，而这正是陷阱。那意味着发明一种转录格式 —— 某种回合边界与角色的写法 —— 而本仓库对它没有任何依据。`dsh-subagent-claude-code` 是把工作交给这个 CLI 的唯一先例，它拒绝一次性文本任务以外的一切，而不是去发明一种格式。错误的格式会悄悄降低模型输出质量，而 harness 中没有任何地方会显示出来，这正是[证据规则](../../../../packages/AGENTS.md)所覆盖的情形：可配置性并不能为一种没有依据的格式背书。这个决定要等到出现真正需要它的消费者。

其后果被明确写出而不是掩盖：智能体循环无法使用这条路由，因为它在每个请求上都发送历史与工具。这条路由服务一次性调用 —— 也就是缝隙自身 `compaction` 与 `session-title` 用途的形状。

### 每一个无法表达的选项都被具名拒绝

工具模式、`maxTokens`、`temperature` 与 `stop` 都没有对应的 CLI 开关。每一项都以 `UNSUPPORTED_REQUEST` 被拒绝，并指明是哪一项让运行停下；拒绝发生在 `stream()` 调用处，在启动任何进程之前。悄悄丢弃其中任何一项，都会在调用方毫不知情的情况下改变对模型的提问。`reasoningEffort` 是那个*确实*能映射的选项：`--effort` 接受五个级别，因此适配器恰好暴露这五个，并拒绝由其他适配器铸造的力度 id 而不是把它丢掉。

### 取消只由信号判定，绝不由进程判定

当 stdout 在没有终止帧的情况下关闭时，说明运行被取消了或进程死了。早期版本在两种情况下都等待进程结果；一个 `done` 永不落定的进程的测试抓住了它。subprocess 缝隙只是*启动*终止阶梯，因此一个忽略 `SIGTERM` 的子进程会在调用方早已放弃之后，把这次运行占住整个宽限期。现在取消只从调用方的信号读取，只有未被取消的运行才等待退出事实。

被中断的运行仍然报告它已发送的计数。翻译器保留最后一次 `message_delta` 的用量，正是为了让被杀死的进程有账可算，而不是看起来免费。

### 隔离在这里被强制执行，因为只有这里拥有一次可供失败的运行

协议包能说出 CLI 是否用注入的密钥完成了认证；但它不拥有任何进程。在 `requireCredentialIsolation`（出厂默认）下，一个指向其他凭据来源的 init 帧会在流中途抛出，于是一次触及宿主自身登录态的运行会停下，而不是完成并记账给一个从未提出请求的人。配置了却没有凭据的路由会在加载时让组装失败，而不是先注册、之后再失败。

### 身份位于实例上，而不在请求中

`ClaudeCliAdapter` 携带某一个租户的 home 与凭据。多租户运行时为每个运行时池构造一个。`stream()` 上没有任何参数能让一个租户的请求指名另一个租户的凭据 —— 这与 `dsh-run-admission` 为调度所做的「代理人混淆」闭合是同一个，只是应用在进程边界上。

## Consequences

这条路由对一次性调用确实可用，对循环确实不可用，而 README 就是这么写的。随之而来两项代价。成本核算丢失了：终止帧的 `total_cost_usd` 包含 CLI 自身的辅助调用，而 `TokenUsage` 没有对应字段，因此 `maxBudgetUsd` 能给一次运行封顶却不报告它花了多少。重试分类也缺席：每种失败都映射到 `CLI_EXIT` 或 CLI 自己的 `terminal_reason`，而 CLI 还会在报告之前内部重试 —— 那对 `dsh-llm-retry` 是不可见的。

组装测试关掉了隔离默认值，因为唯一带有模型输出的夹具是在不加 `--bare` 的情况下录制的，因而报告的是环境中现成的凭据。这一点被记为开发备注而不是被隐藏：录制一次隔离的成功运行需要 API 密钥，而产出这些夹具的机器只有一个 OAuth 会话，而 `--bare` 有意忽略它。默认值本身是有覆盖的 —— 另有一个组装测试断言它恰好会拒绝那份夹具。

## Alternatives considered

**为每个 harness 会话保持一个 CLI 会话**，只发送最新的一个回合。这能带来真正的多轮行为，被否决是因为那样 CLI 就拥有了对话记录。harness 的规则是：任何进入模型请求的东西都必须能从会话日志重建；由 CLI 拥有的历史会与该日志分叉且无从察觉，而恢复一个会话也不是缝隙能够描述的一次模型调用。

**像 `dsh-subagent-claude-code` 那样通过 subagent 缝隙注册适配器。** 那条缝隙已经成功运行着这个 CLI，但它委托的是一个智能体循环。`dsh-llm` 缝隙需要的是一次模型调用，而一个委托出循环的适配器会让 harness 同时拥有两个。

**默默接受那些无法表达的选项。** 因这些拒绝之所以存在的理由而被否决：一个工具模式或 token 上限被丢弃的请求，仍会返回看似合理的输出，于是失败会表现为无法解释的模型行为，而不是一个错误。
