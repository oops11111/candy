# Agent Note: 没人上过发条的那个时钟

Status: implemented

[English](2026-09-04-the-clock-nobody-wound.md) | 中文

## Problem

一次 Candy 运行的每一个零件都已经作为库存在，而没有任何东西拥有这些库所操作的那份状态。

`RunLedger` 与 `RunReplayStore` 是按运行时存在、且必须被共享的对象：一个父运行和它的子运行必须记在同一个账本上，而一个 nonce 只有在同一个存储看见每一次准入时才只被消费一次。没有任何东西持有它们中的任何一个，于是每个调用方都自己造一个。准入策略 —— 期望、密钥、密钥环、池基目录、三个端口 —— 在每一个调用点被手工重新拼装一遍，而那正是「为子运行写错 `findBudget`」既容易发生、又无从察觉的地方。

而 `RunLedger.expire` 是一次没有任何东西发起的调用。它的 README 把后果写得很直白：「一个从不调用它的部署，永远不会释放一份被遗弃的占用。」一次没结算就死掉的运行，会在它父运行活着的整段时间里一直占着父运行的额度。

## Decision

`RunScheduler` 是一个 Cordis 服务，持有一个账本与一个重放存储，从 `ctx.controlPlaneStore` 组合出准入策略，并运行一个把两者一起清扫的时钟。

预算端口在这里被组合而不是被转交，因为这里是那两种生命周期唯一相遇的地方：根运行针对它租户的持久额度被准入，子运行针对它父运行在内存中的剩余被准入。一个还剩很多的租户可以有一个已经耗尽的父运行，因此一个拿租户自己的额度去回答子运行的存储，会让这项检查失效。

秘密以环境变量名的形式指名，而不是写进组合里，沿用 `dsh-llm-claude-cli` 的做法。任何一个未设置都会让启动失败；一个不是 32 字节的凭据密钥同样会，因为保险库正是以那个长度密封的，而那里长度错了，会在之后表现为一个打不开的信封。

`sweep` 是公开的，并接收它自己的 `now`。时钟会调用它，而持有决策时间戳的调用方可以直接调用 —— 测试正是这么做的，另外还有一个假定时器用例，证明那个 interval 会在没人要求的情况下触发。

它刻意不是策略。某个租户还能不能再开一次运行、跨不相关的树同时能有多少个存活，以及排队请求以什么顺序运行，这些决定目前都没有任何东西做出，而在这里把它们发明出来，等于把一个租户级的上限塞进一个按树记账的账房里。

## Consequences

组合顺序现在能从一个令牌端到端跑通：测试签发一份断言，而这次运行抵达一个私有的池目录，凭据已被打开，背后是一个真实的 SQLite 数据库。

实时状态仍在内存里。存储会跨重启保住账户与额度；开启中的运行以及它们的占用不会挺过一次重启，而且没有任何东西把一次运行的花费折回租户的持久额度。

## Alternatives considered

**让每个调用方各自持有账本。** 那正是原先代码所做的，而它不成立，理由 `dsh-run-ledger` 早就写明：两个账本会各自认为自己持有全部额度，于是委派上限在哪一个里都不成立。

**在 `RunLedger` 内部用定时器驱动到期。** 那会让一个纯数据结构拥有一个时钟和一条销毁路径，并给每一个测试都塞进一个需要停掉的东西。服务本来就有一套 Cordis 会销毁的生命周期；账本保持为一个值。

**把断言密钥与密钥环作为配置值传入。** 把一把 HMAC 密钥和一把保险库密钥写进组合文件，等于把它们都放进任何持有那份文件的地方。指名变量名，能让秘密留在部署自己的秘密处理机制里。
