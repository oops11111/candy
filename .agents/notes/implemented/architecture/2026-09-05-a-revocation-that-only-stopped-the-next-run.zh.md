# Agent Note: 只拦下了下一次运行的吊销

Status: implemented

[English](2026-09-05-a-revocation-that-only-stopped-the-next-run.md) | 中文

## Problem

交付计划要求被吊销的账户立即拦下新工作。`revokeProviderAccount` 会销毁凭据信封,因此下一次准入无法再打开它,而一次探测确认了吊销本身是真实生效的。

同一次探测随后在一个其运行已经开着的会话上发起了一次模型调用,得到:`{"last":{"reason":{"kind":"stop"}},"revokedAt":true,"spent":{"tokens":42,"costMicroUsd":900}}`。

一次运行只在准入时打开一次它的凭据,并在其存活期间一直持有那把已解开的密钥。销毁存储的信封触及不到任何已经用它完成认证的东西。每次调用时运行的所有检查——会话查找、预算、墙上时钟——问的都是这次运行,而没有任何一项去问它背后的账户是否还存在。于是一个被攻陷的账户,只要它的运行还在发起调用,就会继续花费其租户的额度。

## Decision

`meterRequest` 在每次调用时读取该运行的账户记录,并在它被吊销、被删除或已不存在时以 `CREDENTIAL_REVOKED` 拒绝。拒绝发生在触及提供方之前,因此不计任何费用。

"是否仍可授权工作"这条规则该由 `dsh-provider-accounts` 陈述,而它此前已经内联陈述了两遍;现在它是一个导出的 `isProviderAccountUsable`,原有的两个调用方都用它。

这次读取是同步的,那正是一个 waterfall 监听器能做的事。`ControlPlaneStore.find` 保持异步,因为它是 `dsh-provider-accounts` 消费的端口,而别的后端未必从内存作答;`accountOf` 是计量路径自己的读取者,它返回记录而不带旁边那份密封凭据——这个决定本就无权触碰它。

## Consequences

吊销现在能停下已经在进行中的工作,而不只是下一次准入。

运行会一直开着,直到它结算或租约到期,因此一次吊销停下的是花费,而不是释放那份占用。关闭一个账户所资助的那些运行能更早释放它,但那是一个更大的改动:它需要吊销以事件而非存储写入的形式抵达这个运行时,而那也正是由另一个进程执行的吊销所需要的。

反向对照——移除这项检查——恰好让那一个断言拒绝的测试失败,而不会让那个断言"另一租户的吊销不影响本运行正常计量"的测试失败。

## Alternatives considered

**在吊销时关闭那些运行。** "在做出决定的那个操作里强制它"是本仓库的规则,而这也是正确的终态。`dsh-provider-accounts` 是一组作用于存储之上的函数,对运行、账本和调度器一无所知,因此这需要一条尚不存在的缝隙;按次调用读取则不需要任何缝隙,而且是失败即关闭,不依赖某个通知的抵达。

**改为在保险库里检查。** 准入已经在那里拒绝被吊销的账户。而缺口恰恰是那个再也不会回到保险库的运行,因此检查必须待在调用发生的地方,而不是凭据被打开的地方。

**终止提供方进程。** 那会比下一次调用更快地终结泄漏,而它属于运行的生命周期,而不属于某一个 waterfall 监听器——与关闭运行所缺的是同一条缝隙。
