# Agent Note: The read that was not in the queue

Status: implemented

[English](2026-09-05-the-read-that-was-not-in-the-queue.md) | 中文

## Problem

`storage-domain`把它的保证说得很精确：每一次写入都排在按域划分的那一条链上，等待持久化，然后修改内存。它没有排队的，是调用方为了决定「写什么」而做的那次读取。

`ControlPlaneStore` 向审计踪迹追加、为租户的额度记账、以及修改授予额度，用的都是先读出记录再放回一条新的。两个调用方在任何一方写入之前就读取，于是各自基于同一个值计算，而第二次写入把第一次丢掉了。

针对已启动存储的一次探查把它量了出来。三十二次并发的审计追加只留下一条记录。三十二次各记一个 token 的并发记账只消耗掉一个 token。每一种都丢了三十一个，悄无声息，而每一次调用都成功返回。

审计那一种是可达的：`RunScheduler.start` 归档它的记录时，走的并不是它为运行记录所用的那条写入链，因此一个同时启动多次运行的租户，会丢掉除一条之外的全部记录 —— 一条恰恰在运行时最忙时少报的审计踪迹。记账那一种目前由调度器串行化结算挡住了，而那是用调用方的自律去顶替存储的契约。

## Decision

存储里每一次读—改—写都排在同一条链上，于是那次读与它所喂养的那次写一起发生。

这条链是整个存储一条，而不是每条记录一条。这些是结算、审计追加与授予额度变更 —— 不是热路径 —— 而一条链无需任何本身也可能出错的按键簿记就已经正确。代价是一个缓慢的介质会把某个租户的记账排在另一个租户的审计追加之后，这一点被明说出来，而不是留给人去撞见。

对于一条已经存在的记录，`KvTable.update` 本来就解决了这个问题，而 `recordRunSpend`、`absorbChild` 与 `markRunSettled` 用的正是它。它解决不了第一次写入：`update` 会拒绝一个不存在的键，而用来创建该记录的先读后放，正是同一场竞争提前了一步。这条链把两者都覆盖了。

`setTenantGrant` 与 `recordAudit` 保持 `async`，因此链之外的参数检查会让返回的 promise 被拒绝，而不是向一个只做 await 的调用方同步抛出。

## Consequences

并发的追加全部落地，并发的记账全部计入，而与记账同时发生的授予额度变更两者都保住。一次被拒绝的写入让链仍然可用，测试把这一点钉住了：一次被拒的记账不会挡住下一次。

「恰好一次」的结算标记仍然要求每个出资方同一时刻只有一次结算 —— 那是对调用方的语义要求，本次没有改变它，而 `dsh-run-scheduler` 仍然满足它。改变的是：丢失一次写入不再取决于调用方有没有把那件事做对。

## Alternatives considered

**到处都用 `KvTable.update`。** 那是域自己的答案，而且是原子的，但它无法创建第一次追加所需要的那条记录。「在则更新、不在则放入」的混用，会把创建时的那场竞争留在原地。

**按记录键分链。** 那会让不相关的租户可以并发写入。它需要一张有自己生命周期的链的映射，而这里没有任何东西频繁到值得为此付费。

**留给调用方。** 调度器本来就串行化运行记录的写入，所以看上去像是已经处理过了。并没有：审计那条路径不走那条链，而一个其正确性取决于「碰巧是哪个调用方做了串行化」的存储，就是一个下一个调用方一定会用错的存储。
