# Agent Note: 两个被标为默认的账户

Status: implemented

[English](2026-09-06-two-accounts-marked-default.md) | 中文

## Problem

撤销或删除一个提供方账户时，会无条件地提升一个替补默认项，而不去问租户是否还有一个。一次探测给某个租户建了三个账户，让第一个保持为默认，然后撤销了另外两个中的一个：

`before ["a:true","b:false","c:false"] → after ["a:true","b:false","c:true"]`

同一个租户、同一个提供方之下，有两个账户被标为默认。解析"该租户的默认账户"的一方随后拿到的将是其中任意一个，而租户的工作会被记到一个它没有选择的账户上。这个不变量正是隔壁那个测试的名字所指：每个用户与提供方之下只有一个默认。

## Decision

只有当租户在该提供方之下已经没有任何仍能授权工作的账户时，才提升替补。租户仍然拥有的默认项是租户的选择，保持不变。

可用性规则是 `isProviderAccountUsable`，现在拼写它的三处都在用它——这一处正是此前那次提取漏掉的第三处。

## Consequences

撤销或删除一个非默认账户，会把租户的默认项留在租户放的地方。

把测试写对花了第二轮，这值得记下来。第一次反向对照通过了：去掉那道守卫什么都没变，因为这次重写同时把"第一个可用的非默认账户"换成了"第一个可用账户"，而只要默认项恰好是最早的那个，第一个可用账户**就是**现有的默认项。把两者区分开的用例，是一个选择了较晚账户的租户。补上那个测试之后，对照就如它应该的那样失败了。

这已经是这项工作中第二次出现"某个机制看起来在起作用、却没有被它自己的测试区分出来"。检验方式很便宜：把机制还原，然后不要相信任何仍然通过的测试。

## Alternatives considered

**只在被移除的账户就是默认项时才提升。** 那是更窄的规则，读起来也像是显而易见的那个，但它修不了任何东西：一个已经持有两个默认项的存储会继续持有它们，而这个函数是唯一可能注意到这一点的地方。

**拒绝移除最后一个可用账户。** 那能让租户不至于完全没有默认项，但那是另一个问题——而且它会拒绝一个租户本就有权执行的操作。

**在存储层强制这个不变量。** 一次拒绝第二个默认项的写入能覆盖每条路径，而不只是这一条。但存储把账户当作不透明记录持有，由 `dsh-provider-accounts` 来裁定；把规则搬过去，等于把提供方账户的语义放进一个对它一无所知的持久化层。
