# Agent Note: 一次丢失的运行不必靠猜

Status: implemented

[English](2026-09-03-run-ledger-settles-exactly.md) | 中文

## Problem

`dsh-run-budget` 在预留时把子运行的额度从父运行那里扣除，在结算时归还未花完的余额。这两半都假定结算会发生。它自己的 README 记下了结算不发生时会怎样：「没有任何东西让未结算的预留过期，因此一个丢失而未结算的子运行会占着父运行的额度，直到调用方去对账为止。」

那就是整个委派上限在悄悄失效。一个有四个子运行名额的父运行，丢了三个子运行之后就永远只剩一个名额和四分之一的 token，而任何地方都不会报错。R3 把缺失的那一块点名为持久运行记录，而那个算术包不可能是它：预留是调用方持有的一个值，而一个值无法注意到它的持有者已经不在了。

第二个问题是租约到期在别处通常值多少。在别处它只能猜 —— 持有者已经不在，没有任何东西知道它消耗了多少 —— 于是系统要么把整份预留全额退回，凭空造出那次运行已经花掉的预算，要么什么也不退，把额度漏掉。两者都错，而且错在会体现在账单上的地方。

## Decision

`RunLedger` 持有一棵委派树中开启着的运行：每一次被给了什么、还剩什么，以及它的占用何时被释放。每一次计费都经过它。

### 存储的是花费，剩余是推导出来的

一条记录持有这次运行被给了什么、消耗了什么；它还能花多少，则由这两者加上每一个开启中子运行的预留算出来。最初的形状存储的是 `remaining`，并拒绝装不下的计费，而这对这条缝隙来说方向是反的：计费发生在提供方已经计过费之后，因此被拒绝的计费会让账本继续报告那次运行已经花掉的额度，而下一次调用会按一个并不真实的数字来定尺寸。它也与紧挨着它的结算规则相矛盾 —— 那条规则一直接受子运行「消耗超过其预留量」。

因此花费会被完整记录，而计费改为报告哪些维度现在已经用尽，那正是那次拒绝所替代的决定。父运行依然只吸收它授权过的部分 —— 一个超支的子运行不该动用它兄弟的额度 —— 而结算报告的是真实数字。

### 计费与占用在同一处，让到期变得精确

因为账本记录了每一次计费，一次被丢弃的运行不需要估算：归还给父运行的是那次运行自己的 `remaining`，也就是它确实没有花掉的部分。那个「猜」消失了，不是因为到期逻辑变聪明了，而是因为在别处让它成为猜测的那两项事实，在这里从来就没有被分开过。

有一处不精确留了下来，并且是被点名而不是被暗示的：一次最后的计费从未抵达账本的运行，会被多退那么多，其上界是一个计费间隔。

### 关闭一次运行会关闭它的后代

子运行的预留是从父运行记录里做的一次扣除。父运行在子运行仍开启时关闭，会让那次扣除失去为它作证的运行，也不会再有任何结算把它逆转 —— 这份额度会被搁浅到整棵树结束。因此一次关闭会结算整个子树，它报告的 `spent` 覆盖整个子树，而 `closed` 点名了随它一起结束的后代，否则运维人员无法分辨一次到期究竟结束了哪些运行。

### 租约是一份占用，不是一个截止期限

到期释放的是一次运行所占用的东西；它不取消那次运行。取消工作属于启动它的那一方，而一个会杀掉运行的账本会同时是两样东西。`renew` 是活着的运行用来表示自己仍在工作的方式，这让一份不再往前推的租约恰好就是一次没有任何东西在驱动的运行。

### 一个账本持有一棵树

预留是从一条记录里做的扣除，因此父运行与它的子运行共用同一个实例。两个账本会各自认为自己持有全部额度，而上限在两边都不成立。

## Consequences

三样此前没有调用方的东西现在有了。`reserveChild` 与 `settleChild` 是没有任何东西调用的算术；`admitRun` 通过 `findBudget` 读到的预算没有写入方；`TokenUsage.costMicroUsd` 现在报告的成本没有可以计费的对象。账本正是这三者交汇的地方，而这才使它们成为一套机制，而不是三个各自站得住的零件。

没有任何东西持久化账本。R3 要的是持久运行记录，而这是那份记录、但没有持久性：记录是调用方可以自行存储的纯数据，这里不提供任何存储、格式或恢复顺序，因为不存在可供对着设计的对象。一次重启会丢掉每一次开启中的运行以及它们携带的占用。

也没有任何东西驱动时钟。`expire` 是一次调用而不是一个定时器，从不调用它的部署就永远不会释放被遗弃的占用。选择那个节奏需要 R3 尚未构建的调度器。

## Alternatives considered

**像预算 README 描述的那样，把到期留给调用方。** 这正是本次变更所取代的状态。它在最要紧的那个方向上不可行：那个本该去对账的调用方是父运行，而父运行恰恰是唯一无法观测到自己子运行死亡的东西，而一次没有人执行的对账与一次泄漏无法区分。

**租约到期时把整份预留全额退回。** 更简单，而且它会凭空造出预算：一个花光了全部额度然后死掉的子运行会把全部额度退回去，让父运行把同一笔钱花两次。把精确结算改回这个形状会让五个测试失败，其中三个说的是普通关闭而不是到期，因为那是同一套算术。

**把账本做成 Cordis 服务。** 那会让这棵树的生命周期挂在一个 fiber 上，并随它一起释放记录。目前予以否决，理由与本组其余部分相同：仓库里没有任何东西在调度运行，因此这个服务会有生命周期却没有调用方，而无论最终由哪个调度器持有它，这个类都可以被直接构造。
