# Agent Note: 一次结算过却仍在跑的运行

Status: implemented

[English](2026-09-06-a-run-that-settled-but-kept-running.md) | 中文

## Problem

`RunScheduler.settle` 把结束一次运行当作记账来做:给出资方写下一笔费用,然后忘掉这条记录。一次因故结束的运行——账户被吊销、租约到期、所在的树被围着它一起关闭——这个决定发生在调度器清扫的深处,而它触及不到该运行自己那次调用仍在运行的进程。这条线索之前的每一次修复都结束了运行的**账本**记录;没有一次触及过进程。这个缺口在方案笔记里被点名了两次,两次都留着没解决:"终止这样一次运行留下的提供方进程,仍在等一个能针对运行生命周期注册处置器的地方,以及一个会去注册它的生产者",还有"关闭该提供方的进程仍属于启动它的那一方"。

把它彻底修好并不是个小改动。`GenerateOptions` 在派发前会被深度冻结,正是为了让计量监听器无法改写适配器收到的东西;而调用方自己的 `AbortSignal`——适配器唯一会服从的取消方式——调度器手里并没有能触发它的引用。因此从结算触及一个存活中的进程根本没法走 `llm/stream` 瀑布这条路;它需要一条 LLM 缝隙那套中立词汇表从未打算携带的通道。

## Decision

这条通道就是进程句柄本身,在它被创建的那一刻去够住,而不是通过那个被冻结的请求。`RunScheduler.registerDisposer(runId, dispose)` 为每个运行保有一个处置器,并在 `settle` 关闭该运行、或 `RunLedger.settlementOf` 报告与它一并关闭的任何后代时调用它、然后清空它——发生在持久写入之前,因为一个即将不再计费的进程应当在这个决定做出的那一刻就停下,而不是等到随后的写入成功之后。`disposableSpawn(runId, spawn)` 把一个 spawn 函数包一层,这样一个提供方绑定只需围绕它已经交给适配器的那个 `spawn` 组合这一层就能得到这项能力,不需要别的改动:它返回的每一个句柄都在创建时被注册,并在该句柄自己的 `done` 落定后取消注册,因此一个自行退出的进程永远不会成为 `settle` 之后误发信号的一条陈旧登记。

这是可选加入的,而且今天故意还没接到任何提供方上。目前没有任何组装去调用 `disposableSpawn`——那次组装正是这个发行版还没建成的 R3 编排接合点——所以这次修复给出的是这份触及能力,还不是真正的触及动作。一个抛出异常的处置器会被记录并吞掉:它自身的失败不构成让这次运行的账目卡在打开状态的理由,因为它本可能阻塞的那次结算,在它运行时早已被决定了。

## Consequences

未来的提供方绑定,只需围绕它已经透传给适配器的那个 `spawn` 函数组合一次调用就能补上这个缺口;绑定、适配器或 LLM 缝隙都不需要再做别的改动。每个运行只保有一个处置器而不是每次调用一个,这对一次会发起若干次连续调用的运行来说是正确的——只有那个仍活着的调用才需要被释放,第二次注册正确地做的是替换而不是叠加。

六个测试用一个假句柄在调度器层面钉住了这一点:关闭时会跑处置器、父运行的树把子运行一并关闭时也会跑子运行的处置器、被取消注册的处置器不会跑、第二次注册会替换而不是叠加、即便处置器抛出异常运行仍会结算,以及 `disposableSpawn` 既会在结算时终止一个仍开着的句柄,也会放过一个已经自行退出的句柄。第七个测试围绕一次真实的 `dsh-subprocess-local` spawn 组合出 `disposableSpawn`,启动一个真实的、会挂起的 `node` 进程,并断言 `close` 之后那个 pid 已经无法再被触及——正是这道缝隙上既有的取消测试所要求的同一种「真实 pid」纪律。把 `disposeOf` 改回空操作会让这个测试超时,而不是仍然通过,这正是它与那六个假句柄测试的区别:那六个钉住的是登记表自身的记账,这一个钉住的是那份记账真的够到了一个操作系统进程。

## Alternatives considered

**把一个调度器自有的 `AbortSignal`穿进 `GenerateOptions`。** 以 `dsh-run-scheduler` 自己 README 里早已说明的、不往那儿加 `runId` 的同一个理由被否决:`dsh-llm` 是继承来的、提供方中立的缝隙,把一个 Candy 专属的终止开关放进它的请求词汇表,会让一个消费者去支配所有其他消费者共用的契约。请求在派发前也被深度冻结,恰恰是为了不让监听器改写它们;为这一个目的开个口子,会削弱这份冻结存在的理由本身。

**从这个调度器已经在监听、用于归因的 `subprocess/launched` 事件出发,按 pid 去够那个进程。** 这个事件刻意只携带 pid、别无他物——"这份载荷只指名可执行文件与运行位置,从不携带参数或环境……需要更多信息的消费者,懂得比这道缝隙本身更多"——而在 `dsh-subprocess` 里再建一条按 pid 索引的终止通道,会让任何持有那份登记表的人都获得触及任意租户进程的手段,这正好与这道缝隙对租户与运行的刻意无知所要保护的东西相反。

**由调度器直接调用外层流的 `.return()`,而不是注册一个处置器。** 调度器并不在整次调用期间持有外层流的迭代器——`oneCallAtATime` 才持有,而且是在它自己的闭包里;即便调度器持有,在同一个异步生成器上,与一次尚未落定的 `.next()` 并发调用 `.return()` 也只会排在那个尚未完成的步骤后面,而不会抢占它,因此并不能可靠地打断一次卡在读取一个此刻并未写任何东西的进程上的调用。
