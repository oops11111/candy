# Agent Note: 那个无法共享的适配器

Status: implemented

[English](2026-09-06-the-adapter-that-could-not-be-shared.md) | 中文

## Problem

`dsh-llm-claude-cli` 注册的 `ClaudeCliAdapter`,其隔离信息——一个主目录和一个 API key——在组装时就被钉死在实例上。这对该包自己声明的契约来说是对的:"一个多租户运行时不会加载这个插件一次、再按请求变换身份——它会为每个运行时池构造一个适配器。"harness 里没有任何东西去构造那些按池分开的适配器。一个想用这条路由的多租户运行时无处可去:只注册那一个共享的适配器一次,会用不管当时配置的是哪个凭据去认证每一个租户的调用,而没有任何机制能按被准入的运行去构造、注册、处置一个适配器。

这件事在本次会话中被点名了两次,而且都被有意留了下来——作为交还给用户的问题,而不是我自己决定的事,因为它触及一次请求如何被路由到一个按租户划分的提供方实例,而 LLM 缝隙自身的中立性规则让这个决定变得有分量。用户的方向:把它解决掉。

## Decision

`dsh-claude-cli-route` 在固定的路由名 `claude-cli` 之下挂载一个 `SessionRoutedClaudeCliAdapter`,按调用而不是按实例去解析身份。每一次 `stream()` 调用都会读取 `options.sessionId`,询问 `RunScheduler.runIdentityFor` 哪次运行驱动着它,再从这个答案为这一次调用单独构造一个全新的 `ClaudeCliAdapter`。两次调用之间不保留任何东西,即便是同一次运行的两次调用也是如此:凭据每次都从保险库重新读取,这正是 `meterRequest` 自己的账户检查已经具备的性质,原因也相同——两次调用之间发生的一次吊销必须停下第二次调用,而不只是停下下一个被计量的 chunk。

`RunScheduler.runIdentityFor(sessionId)` 是这次组装所需要、而任何一块单独的拼图都答不出来的新接口:它把会话解析成那一个开启中、可用的运行(与 `meterRequest` 所做的检查相同,被提取进 `findSessionRun` 并共享,而不是重复一份),读取账户自己的提供方并通过这个运行时自己的密钥环打开它的凭据,再连同池根目录与剩余预算一起返回。`dsh-claude-cli-binding` 新增了 `bindClaudeCliCredential`——`bindClaudeCliRun` 实际用到的那两个字段,一个密钥和一个池根目录,从完整的 `AdmittedRun` 接口背后被抽出来,因为后一次调用根本没有办法诚实地重新构造出那整个接口。

处置则接上了本次会话早些时候那份工作已经打开的那个触及能力所留下的缺口:本路由围绕它交给 `ClaudeCliAdapter` 的那个 `spawn` 组合出 `RunScheduler.disposableSpawn(runId, spawn)`,于是本路由启动的一个进程,在它存在的那一刻起就被登记到该次运行的生命周期上。因故结束这次运行能够触及它——这一点针对一个真实的挂起进程和一次真实的结算而不是一个被模拟出来的句柄得到了证明。

## Consequences

一个多租户 Candy 运行时只需挂载一次 `dsh-claude-cli-route`。不再需要任何组装去手工为每个池构造和处置一个 `ClaudeCliAdapter`;一个 `dsh-run-scheduler` 准入的每一个租户,都由那一条被挂载的路由来服务。

`session-routing.spec.ts` 里的五个测试针对一个真实进程证明了这一点:两个租户的调用(在同一次运行上先后进行)把正确的凭据落到了一个真实子进程的环境里、一个被吊销的账户会拒绝下一次调用、一个没有会话的请求在任何解析发生之前就被拒绝,以及一次挂起的启动会在调度器因故结算该运行时被回收——并由一个反向对照确认:去掉 `disposableSpawn` 的接线之后,同一个测试会超时。`refusals.spec.ts` 里另外十个测试则针对一个伪造的 `runIdentityFor` 钉住了每一条拒绝分支,因为真实调度器自身的解析逻辑是那个包自己要去测的东西。

## Alternatives considered

**为每次运行注册一条动态路由,在该运行结算时处置掉。** `ctx.llm.registerAdapter` 本来就会返回一个处置器,所以以同样方式组合出的一个按运行命名的路由(`claude-cli/${runId}`)在机制上是可行的。之所以否决它,是因为它把一个路由决定推给了任何组装 `GenerateOptions.provider` 的一方——会话/预设组装需要知道一个在运行开始之前根本不存在的按运行命名的名字,而这正是 `dsh-run-scheduler` 自己的 README 早已拒绝放进 LLM 缝隙请求词汇表里的那类 Candy 专属概念。在一个固定名字的适配器内部、从每个请求本就携带的会话出发去解析身份,根本不需要发明任何新的命名方案。

**按运行缓存已打开的凭据,只在保险库未命中时才刷新。** 基于 `meterRequest` 早已定下的同一个理由被否决:一个被缓存的凭据观察不到在它被缓存之后发生的吊销,而打开一次保险库的代价——在一次配置查找之上多一次 AES-GCM 解密——并不是本路由自己的限制小节在没有证据的情况下值得去规避的代价。

**不再进一步扩展 `dsh-run-scheduler`,而是把凭据/池的解析放进这个新包里。** 考虑过并否决了:那样它就需要自己拷贝一份运行时的凭据密钥配置才能打开一个保险库信封,让两个插件各自独立读取同一个密钥。把这个解析过程路由经过调度器——它在一次运行的准入时刻本就已经组装过完全相同的配方——意味着只配置一次密钥、读取一次,却两处都能用。
