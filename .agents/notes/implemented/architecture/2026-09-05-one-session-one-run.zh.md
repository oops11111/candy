# Agent Note: One session, one run

Status: implemented

[English](2026-09-05-one-session-one-run.md) | 中文

## Problem

计量通过模型请求所面向的那个会话来找到运行。而没有任何东西让这份映射是唯一的。

同一个会话上可以开启两次运行 —— `admitRun` 从不查看 —— 而只有计量查找会注意到，一次调用一次地注意到，且远在冲突被制造出来之后。针对已启动运行时的一次探查证实了这一点：两个租户的运行都在 `session-1` 上启动了，都占住了各自的额度，而那个会话里的第一个模型请求返回的是拒绝。

可达性是有界的 —— 会话 id 在断言的签名之内，因此在控制平面不去铸造的前提下，一个租户无法认领另一个租户的会话 —— 但这次失败的形状是反的。一个被铸到另一个租户会话上的租户，拦住的是那个租户的工作，而不是它自己被拦住；而本可以把这件事说出来的运行时，什么也没说。

## Decision

`admitRun` 增加一个 `findSessionRun` 端口，并在 `session` 阶段拒绝第二次运行，指名那个已经持有它的运行。

这项检查位于额度之后、nonce 之前。两种拒绝都是调用方能够修复并重试的 —— 充值，或者等那个会话的运行结算完 —— 之后再出示同一个仍然有效的断言，因此都不得为一个并非调用方造成的冲突烧掉一次性令牌。

子运行也不例外。它需要属于自己的会话，理由与它的父运行相同，这让「一次运行一个会话」成为对签发断言的控制平面的一项要求，而不是一种惯例。组合测试现在为每一次运行铸一个会话，而那正是一个正确的控制平面所做的事。

计量那一侧的拒绝保留下来。`start` 并不是运行记录的唯一写入者：另一个共享此 audience 的运行时，或者一次直接的 `openRun`，仍然可以造出被两条记录认领的会话，而本运行时并不独占那张表。它的测试现在按那种状态真正的产生方式来构造它。

## Consequences

冲突在它被制造出来的地方就被拒绝，早于任何占用被取走，而被拒的那次运行保住了它的 nonce。

写这件事时发现了第二个缺陷，在复核里而不是在代码里：反向对照本该让三个测试失败，却只让一个失败了。两个组合测试被后来一次针对重叠区域的编辑删掉了，因此它们本该提供的覆盖并不存在。是那次对照注意到了它；测试已经回来，而对照现在让三个都失败。

## Alternatives considered

**在存储的 `openRun` 里拒绝。** 事实住在那里，而调度器本来就会回滚一次失败的记录写入。那会把一次被拒绝的运行变成一次抛出的介质错误，而那条路径本来的含义就是介质错误，调用方也就分不清「会话冲突」与「磁盘坏了」。

**只在跨租户时拒绝。** 那是有攻击者在场的那种情形。同一个租户的两次运行落在一个会话上，同样无法归属，而记错的是同一个租户而不是另一个租户 —— 更安静，但并不更好。

**把它留给计量查找。** 那已经是现有行为，而它会永远拒绝那个会话里的每一次调用，而不是拒绝那一次制造了冲突的运行。
