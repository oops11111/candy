# Agent Note: 没有会话的调用方

Status: implemented

[English](2026-09-10-a-caller-with-no-session.md) | 中文

## 问题

`dsh-device-registry` 已经能配对一台主机,却没有任何东西能抵达它。Candy 的每条管理路由都经过同一个信封,而该信封存在的全部保证就是:身份来自存储认证过的会话 Cookie;兑换配对码的 Harness Host 既没有 Cookie,也没有浏览器,更没有任何在先的身份。它请求体中的配对码就是它声明的全部。

两条出路都是错的。放宽 `registerApiRoute` 去接受某种别的证明,会为了容纳一条路由而一次性削弱信封赖以存在的那句话——持有 `Actor` 即意味着已认证会话——对每一条路由都是如此。把兑换直接注册到 Web 服务器上,则会重复来源检查、有界的请求体读取、JSON 解析、回复头部和失败词汇,并且把这条唯一无人登录的路由放到部署中审查最少的传输层上。

构建过程中还浮现出第三个问题。信封在处理器失败时以 `500` 作答,随后重新抛出;而 Harness Host Web 服务器会销毁那些在头部已发出之后其处理器被拒绝的响应。于是调用方收到的是套接字挂断,而不是信封刚刚裁定的状态。会话路由掩盖了这一点:回复与抛出之间的两次 await 通常足以让响应体刷出,因此这个缺陷只有在加入一条没有那两次 await 的路由时才显现。

## 决定

信封获得第二种注册方式,而不是一个更宽松的第一种。

`registerAnonymousRoute` 共享传输——被寻址的主机、方法、有界的请求体、回复头部、失败词汇——并且根本不向处理器交出 `Actor`,只交出请求体与请求本身。不存在任何凭据能够抵达的 `Actor` 构造途径,因此关于会话的那条保证毫无变化;以这种方式注册的路由自行推导其凭据所证明的身份,而类型系统阻止它把该身份伪装成会话。

它的来源检查只看 `Host`。`Origin` 的作用是把本部署的页面与仅仅知道 URL 的页面区分开,而它之所以重要,是因为浏览器会自行附上会话 Cookie。这里没有 Cookie,调用方也不是浏览器:要求该头部会拒绝每一个真实客户端,而伪造这个请求的页面必须已经持有配对码,并且读不到回复。

对这样的路由,信封不会按租户归档任何东西,因为它没有可归档的租户。设备兑换在配对码解析出租户之后自行记录其成功;被拒绝的兑换只抵达部署的日志——未知的配对码指不出任何人,而一条每次猜测都留一条记录的踪迹,会被猜测者灌满。

`dsh-device-api` 挂载三个租户操作与兑换。配对码是来自三十二字形字符集(不含 `I`、`L`、`O`、`U`)的十六个五位字形。八十位是固定而非可配置的:该配对码是通过公共互联网出示的持有型凭据,猜测与尝试之间没有速率限制,而这正是让在其有效期内猜中变成不可能而不是缓慢的原因。字符集大小整除 256,因此对随机字节做掩码即可选出字形,不会带来对 26 或 36 取余所引入的偏置。设备 id 与令牌都在服务端铸造,理由与账户 API 铸造账户 id 相同:自选二者的主机可以指名另一租户的设备,并覆盖将其绑定的那条记录。

两种注册方式中的重新抛出都已移除。错误改为送往新增的 `ApiHost.report`,这样部署仍然读得到失败是什么,而调用方收得到信封裁定的答案。该成员是必需的:省略它的挂载插件会把每一次处理器失败变成一个无人能解释的 `500`,而那比重新抛出所导致的挂断更糟。

## 结果

租户现在可以把一台机器接入自己的部署,也可以再把它移出。配对已经端到端存在:在浏览器会话中签发配对码,由人带过去,被一台此前没有身份的主机一次性兑换,产生一台绑定该租户的设备和一枚只有该主机持有的令牌。

信封上的每条路由现在都对失败的处理器作答,而不是挂断。这对账户 API 和审计 API 与对本 API 一样是行为变化,而它正是它们的测试原本就断言的行为——此前之所以通过,只是因为恰好有两次 await 插在中间。

目前还没有任何东西消费设备令牌。主机持有它,没有路由接受它,因为一台已配对主机接下来做的事——连上 Remote Gateway、执行工具、解析工作区根目录——都是继承自 Harness 的行为,而 R5 仍需把它们绑定到设备。准入会解析设备:`admitDevice` 作为独立的一步运行,因此一台被撤销的设备立即失去它的运行。

有两项代价值得点名。租户可以无限制地签发配对码与配对设备,正如他们可以无限制地创建服务商账户;也没有任何东西把用尽的配对码从介质上清扫掉。在出现普遍限定租户占用的机制之前,这两项都只受已认证成员自身的克制约束。

## 考虑过的替代方案

**给 `ApiRoute` 增加一个 `authenticate` 钩子。**否决。它读起来像是一次泛化,实则是一次削弱:此后每条路由都只差一行配置就能接受会话之外的东西,而这条不变量将栖身于最后被写下的那个处理器里,而不是类型之中。

**兑换同样要求 `Origin`。**否决,因为非浏览器的 HTTP 客户端不会发送它,而该头部防范的是浏览器自行附上的 Cookie——这条路由并没有 Cookie。

**用速率限制代替加长配对码。**作为首要防线否决。限流器是需要保存、跨进程共享并且容易做错的状态;八十位不需要其中任何一项,并且在增加第二个运行时时不会退化。部署前面的限流器仍然有用,而它属于反向代理,对其他每条路由也是如此。

**让主机自选设备 id,以便重新配对时保持不变。**否决:调用方选择的 id 可以指名另一租户的设备,而它将覆盖的那条记录正是绑定本身。

**保留重新抛出,让 Web 服务器去记录它。**在实测之后否决。服务器记录错误,随后销毁响应,于是调用方失去了那个 `500`——对一个信封已正确作答的请求而言,那是一次它无法与崩溃区分的挂断。

## 验证

`packages/control-plane/device-api/tests/loader-composition.spec.ts` 通过 Loader 启动存储栈、持久控制面、真实的 Harness Host Web 服务器与本插件,每个用例都是对监听端口发出的 HTTP 请求。它覆盖端到端配对、配对码与令牌各自只出现一次、所铸配对码的形状以及主机以不同写法拼写它、一个配对码只兑换一次、未知与过期的配对码、试图指名租户或设备 id 的请求体、撤销与另一租户得到的 `404`、没有会话的每条受管路由、寻址到另一权威的请求、格式错误的提交、审计踪迹、拒绝写入的审计汇聚点、抛出异常的介质,以及随 fiber 移除路由——达到该包的 100%。

`packages/control-plane/control-plane-api/tests/control-plane-api.spec.ts` 为第二种注册方式与失败路径新增九个用例,使信封达到 100%。`packages/bundle/candy-app/tests/loader-composition.spec.ts` 证明已发布的层在所配置的来源上挂载了全部四条路由。

四项变异对照证明这些用例确实在做判断:从请求体接受设备 id、从请求体取租户、按记录自身的租户而不是会话的租户执行撤销,以及恢复重新抛出,各自都会让一个用例失败,随后实现被还原。
