# Agent Note: A settlement that a crash could lose

Status: implemented

[English](2026-09-04-a-settlement-that-a-crash-could-lose.md) | 中文

## Problem

`RunLedger` 把每一次存活运行都放在内存里，而调度器结算一次运行的做法是：先在那里关闭它，再把账写到介质上。这个顺序带来两件事。

一次重启会丢掉每一个开启中的运行。租户的运行自上次结算以来消耗的一切都随之而去，而那些运行正扣着的额度则整份回来了 —— 在负载下重启的运行时，把整份授予额度连同上一个切片刚刚赋予意义的并发名额，一起还给了每一个租户。

而且，即便进程一直活着，一次结算也可能丢失。关闭在前，且不可能失败；写入在后，且可能失败。当它被拒绝时，占用已经释放，本该被记账的那条记录也已经没了，于是没有任何东西能重试。上一个切片的备注和包 README 都精确地点了这一条，并点明持久的运行记录才是关闭它的东西。

## Decision

这笔账在任何东西移动之前算出来、写下来、施加出去，之后才忘掉那次运行。

`RunLedger.settlementOf` 报告关闭一次运行会记多少账、覆盖哪些后代，且不改变任何东西。它不是结算算术的第二份实现 —— `settle` 调用同一次递归，随后删除它所指名的东西 —— 因此把预览出来的数字写下来的调用方，写下的正是关闭将要应用的东西。`RunLedger.restore` 安装账本并未开启过的记录，并刻意不重跑创建它们时的检查：一个此后已经花掉大部分额度的父运行，已经腾不出空间去预留一个它早已拨过款的子运行，因此重放 `openChild` 会拒绝掉正确的记录。

`ControlPlaneStore` 为每一次存活运行持有一条记录，就放在早已持有账户与额度的那个域里。记录携带账本自己的记账、这棵树被记到哪个租户头上、是哪个运行时开启了它，以及一旦写下之后的那个已结算数字。

一次结算是这个介质无法合并成一次的两次写入：为这次运行的出资方记账，然后忘掉这次运行。因此两种出资方 —— 根运行对应租户的额度，子运行对应父运行的记录 —— 都携带它们最后吸收的那次结算的 id，由与记账同一次原子更新写入。重复同一个 id 是空操作，因此重启中的运行时可以在不知道上次走到哪一步的情况下重新驱动一次被打断的结算。这两个标记是相隔一层的同一套机制，而「租户是每一棵树所悬挂的根」本来就该长成这样。

这项保证只在没有两次结算彼此交错时成立 —— 两次结算留下的是较晚那次的 id，而一次崩溃随后会把较早那次记两遍账 —— 因此调度器里每一次对运行记录的写入都排在同一条链上。

重启是结算而不是恢复。本运行时写下的记录，就是它当时在驱动的运行，而驱动它的那个进程已经没了，因此 `Service.init` 完成每一次被打断的结算，恢复剩下的，并关闭每一个被恢复的根。恢复只读它自己那个运行时的记录，依据是每条记录上的 audience 戳记，因为共享同一介质的两个运行时否则会结算掉对方仍在进行的运行。

一次运行属于哪个租户，搬到了它的持久记录上，而原先持有它的内存映射没了。那是一份重启并不拥有的事实的第二份副本，而现在每一个读者 —— 结算、恢复与租户剩余额度查询 —— 读的都是那份能活下来的。

## Consequences

一次重启会按每个租户的运行实际消耗的量为其计费，并以一个干净的账本开始。一次被拒绝的结算写入让运行在两边都保持开启，于是它的租约会把下一次清扫带回来重试；组合测试驱动的正是这一条：让写入失败，观察到运行仍然开启且租户未被计费，然后恢复介质，看着下一次清扫把它结算掉。

`RunScheduler.charge` 现在是异步的：一笔没有被写下来的花费，就是一次重启会丢掉的花费，因此它在调用完成之前先抵达该次运行的记录。`start` 也会写下运行的记录，并在那次写入失败时关掉它刚刚开启的账本条目 —— 一次本运行时无法记录的运行，就是一次重启会遗忘、而它的提供方还在继续花钱的运行。

域版本从 1 走到 2。版本 1 的额度会被丢弃，因为它说不出自己已经吸收过哪一次结算，而在它旁边被恢复出来的运行记录可能因此被记两遍账。

这件事没有做到的是：它挺不过一个损坏的存储。无法构成完整树的记录会让启动失败，而不是被丢弃，因为对一个并不存在的父运行的占用是没有任何东西能结算的，而且这里没有修复路径。它同时也把运行时内每一次运行记录写入串行化了，因此一个缓慢的介质会把不相关租户之间的计费也串起来。

## Alternatives considered

**继续先在内存里结算，然后重试写入。** 重试队列比那个标记更费机器，而且在崩溃时仍然会丢账，因为队列同样在内存里。先写则不需要队列：介质持有那个意图。

**让运行记录就是账本。** 那样每一次计费都会变成一次持久的读—改—写，而 `remaining` —— 准入对每一个子运行都要调用的东西 —— 会从介质推导出来。账本之所以是记账权威，恰恰因为它便宜且同步；记录是那个能活下来的东西，而把这两个角色分开，正是为什么 `settlementOf` 与 `restore` 就足够了。

**永久保留已结算记录，并由它推导租户的消耗。** 按构造就是幂等的，完全不需要标记，而且无界：每一次运行一条记录，直到部署终结。标记只是两个可选字段。

**恢复开启中的运行，让它们的租约自然到期。** 它在启动时不需要任何结算，代价是重启之后，那些明明已经结束的运行还会把租户的额度占住一个租约周期。在启动路上就结算，既更准确也更及时。

**让子运行的结算没有持久步骤。** 子运行的账无论如何都会通过它的根抵达租户，因此子运行那条路径本可以什么都不写。它不行：一旦父运行被记入的花费被之后的一次计费持久化，一条仍然存在的子运行记录就会被算第二遍。`absorbed` 标记正是让这两种顺序彼此一致的东西。
