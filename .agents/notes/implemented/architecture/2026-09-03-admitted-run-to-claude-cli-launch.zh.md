# Agent Note: 准入与它所授权的那个进程之间的接点

Status: implemented

[English](2026-09-03-admitted-run-to-claude-cli-launch.md) | 中文

## Problem

`dsh-run-admission` 的终点是交还一个 `AdmittedRun`：已校验的 claims、一份被打开的凭据、一个池键、该池拥有的目录，以及这次运行可以花费的预算。`dsh-llm-claude-cli` 的起点是索要一个主目录、一把 API 密钥、一个花费上限，以及是否要求凭据隔离。两者是对着同一份设计写出来的，严丝合缝，却没有任何东西把它们连起来。

这道缺口不是缺一个功能，而是错误会发生的那个位置。准入产出的每个字段在启动那边都有对应项，因此手工接线的部署要写四条赋值 —— 而把一个租户的池目录与另一个租户的密钥配在一起的那条，类型检查完全通过。准入之所以存在，正是为了让这种配对无法被表达；而在启动前一步停下，等于把它交还给写最后四行的那个人。

## Decision

`bindClaudeCliRun(run, deployment, allowance)` 就是本包的全部。每一个随租户变化的值都从那次被准入的运行里读出 —— 一个已由准入证明其自洽的对象：池根目录成为 `HOME` 与工作目录，被打开的密钥成为 API 密钥。额度的 `costMicroUsd` 成为美元上限，而它之所以是独立的，理由见下。

deployment 参数只携带该主机上每个租户共享的东西 —— 可执行文件路径与进程树终止宽限 —— 别无其他。只有当一个字段不可能在租户之间有差异时，它才属于那里；正是这一点让这个参数不会重新长回它所取代的那种手工接线。

### 上限是按调用生效的，因此额度是一个参数

一次运行每做一次模型调用就发起一次调用，而 CLI 把 `--max-budget-usd` 施加在它面前的那一次调用上。因此把每一次调用都绑定到被准入的预算，给这次运行的会是按调用而不是按运行的限额：它可以每调用一次就花掉一遍全部额度，而没有任何东西会拦住它。额度之所以是第三个参数，正是因为这个 —— 持有 `dsh-run-ledger` 记录的调用方传入该记录的剩余额度，而一次运行的第一次调用传入 `run.budget`。

这是通过追问这个绑定如何与账本组合而来的，不是由一个失败的测试发现的。如今钉住它的那个用例会跑两次真实调用，并从第二个进程自己的参数里读出那个上限。

把额度改成参数，同时也拿掉了原本由准入提供的一项保证，因此一份什么都不剩的额度会在这里被具名拒绝。`claudeCliArguments` 拒绝零上限，而若没有这项检查，绑定一次已花光运行的调用方会在流开始时从适配器内部撞上一个 `RangeError`，而不是在它选定额度的地方得到拒绝。

### 凭据隔离在这里不可配置

`ClaudeCliAdapterOptions.requireCredentialIsolation` 是一个由部署设置的布尔值。本绑定始终把它设上。抵达本模块的每一次运行都恰好是为一个租户准入的，因此 CLI 报告自己用了注入密钥以外任何凭据的运行，花的是一个并未授权它的租户的钱。这是多租户情形下的安全不变式，而禁止硬编码可调项的规则恰恰豁免这一类。

### 凭据只会被拒绝，不会被修补

保险库存放的是任意字节，而这里是它们第一次成为进程环境的地方，因此这些检查就是环境自己的限制：非空、合法 UTF-8、无 NUL、无换行。跨行的值在任何把环境渲染成文本的地方都会被读成两个变量；带 NUL 的值则根本无法成为一个变量。

它们没有一个能靠剥掉那个字节来修好。被悄悄改动的密钥谁也认证不了，而运维人员会在好几层之外遇到一次无从解释的提供方拒绝，而不是在字节抵达的那一点遇到一次具名的拒绝。

### 什么没有被重复检查，以及为什么

池根目录不做校验。`runtimePoolRoot` 拒绝相对基准目录，因此「绝对路径」按构造就是每一个 `AdmittedRun` 的性质，在这里再检查一次会是一段声称在守护什么的不可达代码。凭据之所以被校验，是因为它的字节来自磁盘上的一个密封信封 —— 一个持久边界 —— 而池根目录来自同一个进程里的一个函数。

## Consequences

从一枚令牌到一个运行中的提供方进程，这条路径现在是连续的：签发、准入、绑定、启动。每一步的输出都是下一步唯一与租户相关的输入，其中没有任何一步会在凭据之外再单独接收一个租户身份参数。

目前还没有任何东西启动它。那个会为每个适配器实例持有一次被准入运行的调度器属于尚未交付的 R3 工作，README 就是这么写的，而没有暗示已经接通的路径。已经存在的是这个组合及其测试，正是它让下一步成为装配而不是设计。

隔离这项主张是对着操作系统检验的，而不是对着对象。`tests/tenant-isolation.spec.ts` 会签发一份断言、把它准入、把它绑定，并通过 `dsh-subprocess` 启动一个真实进程；一个替身可执行文件报告它实际拿到的 `HOME`、工作目录、密钥与花费上限。两个租户拿到两个主目录，两个进程都看不到对方的密钥；而环境里已有的 `CLAUDE_CODE_USE_BEDROCK` 或 `ANTHROPIC_BASE_URL` 不会抵达子进程，一个普通的环境变量却会 —— 因此墓碑化是被观测到的，而不是被假定的。把主目录改回一个常量会让其中两个用例失败，把凭据隔离关掉会让第三个失败，正是这一点让它们成为证据。

`tests/run-accounting.spec.ts` 从另一个方向闭合了这条回路：它在 `dsh-run-ledger` 里开启这次运行、启动它、用进程报告的用量与成本给账本计费，然后结算它。把上限改回被准入的预算，恰好会让那个跑第二次调用的用例失败。

同一套装置还检验一次运行不会留下任何东西。一个被要求先启动自己的子进程再挂起的替身，在一个用例里被取消、在另一个用例里在流中途被放弃；CLI 以及它启动的那个进程都必须变得不可寻址。这两个用例钉住的是不同的机制，并且各自独立失败：去掉适配器在生成器被放弃时的 `terminate()` 只会让放弃用例失败，而不把调用方的信号传给 spawn 只会让取消用例失败。只杀 CLI 本身是不够的 —— 一个普通子进程会活过它的父进程并被重新挂载父级，这一点是被检验过的，而不是被假定的。

Codex CLI 的运行需要它自己的绑定。启动事实并不相同 —— 那个 CLI 的隔离方式、预算标志与凭据变量都不是这些 —— 而共通的部分是一种形状而不是代码，因此写一个横跨两者的函数会凭空造出一套两个适配器都不具备的通用启动词汇。

## Alternatives considered

**把这个接点放进 `dsh-llm-claude-cli`。** 那会少一个包，也会让一个 LLM 适配器依赖控制平面，使得单租户部署要背上它从不使用的准入类型。理由是依赖方向：适配器不该知道租户是什么。

**让 `admitRun` 直接返回启动事实。** 那样准入就会知道每一个提供方的进程参数，而新增一个提供方会改动那个决定运行是否可以开始的模块。准入回答的是授权；绑定回答的是某一个提供方在这份授权之下如何启动。

**让部署覆盖花费上限。** 予以否决：那会是第二个限额，可能与被准入的那个不一致，而两个上限之间的不一致会以一张账单的形式被发现。运行可以花多少，预算已经是答案，而 CLI 需要的转换全部就是把它除以一百万。
