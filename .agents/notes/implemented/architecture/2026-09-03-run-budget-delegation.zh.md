# Agent Note: 跨委派树的运行预算

Status: implemented

[English](2026-09-03-run-budget-delegation.md) | 中文

## Problem

[多租户运行时计划的 R3](../../proposed/architecture/2026-09-02-multi-tenant-cli-agent-runtime.zh.md) 要求父子运行记录，携带父集授权，以及深度、并发、token、时间与成本预算。读一遍 harness 已有的东西，把这个范围显著收窄了，并留下一处没有任何东西覆盖的缺口。

`dsh-subagent` 已经限制了委派深度：`delegationDepthOf` 从父运行推导子运行的深度，`SubagentDepthError` 拒绝超过 `maxDepth` 的那一次。它也已经打上血缘标记，而 `captureDelegatedPolicyOverrides` 把被委派子运行的沙箱模式钉在父运行的显式覆盖上、把审批策略钉为 `'never'` —— 这正是 R3 所说的那种父集授权。所以深度与授权是继承来的，不是 Candy 要建的。

没有任何包覆盖的是花费。在所有 `packages/*/*/src` 中检索成本记账，一无所获：没有金额类型，没有 token 额度，没有并发预算。仅有深度并不能为一棵树设界 —— 深度 3、每层十个子运行就是一千次运行，每一个都可以随意消耗租户的 token、时间与金钱，直到外部有什么东西注意到为止。

## Decision

`@deepseek-ai/dsh-run-budget` 只拥有预算这一半。它是对四个维度 —— token、挂钟毫秒、整数微美元、存活子运行名额 —— 的纯算术，提供四个操作：从父运行那里预留子运行的额度、把未用完的余额结算归还、按消耗为一次运行计费，以及询问是否还有剩余。

### 预留是扣除，而不是检查

父运行的额度在子运行启动时就被减少，`reserveChild` 会把这个减少后的父运行作为一个值返回，调用方必须采纳它。另一条路 —— 拿请求和父运行做检查、让双方各自保留自己的数字 —— 能通过每一个单子运行的测试，却在真正要紧的情形上失败：一个持有 1000 token 的父运行可以批准十个各要 700 的子运行，因为每次检查看到的都是完整的 1000。扣除让超额委派变得不可能，而不是变得可被发现；并且有一个测试恰好断言：第二个子运行拿不到第一个已经持有的 token。

### 金额是整数微美元

用浮点比较或扣减的预算会漂移，而会漂移的花费上限不是上限。微美元在安全整数范围内给出一美分的四位小数，比任何提供方的定价粒度都细。

### 子运行名额是被占用，而不是被花掉

`children` 的行为与另外三个不同：预留占用一个名额，结算归还它；而 token、毫秒与金钱则一去不返。这正是 `RunSpend` 没有 `children` 字段的原因 —— 一个能够「花掉」并发度的调用方，会摧毁它本应释放的那份容量。子运行自己可以再委派的并发度归它自己持有，不从父运行的名额中抽取；只有该子运行占用的那一个名额才抽，因此只剩一个名额的父运行，仍然可以启动一个被允许拥有五个孙运行的子运行。

### 超支不予返还

消耗超过其预留量的子运行已经让租户付出了那笔钱，而把差额返还等于凭空为父运行造出预算、让它再花一次。按这条规则结算需要的是活跃运行的记录，而不是调用方来回传递的值，因此它连同那个累加运行花费的计费一起移到了 [`dsh-run-ledger`](2026-09-03-run-ledger-settles-exactly.zh.md)；留在这里的是预留、耗尽判断，以及三者共用的那些值。

### 请求会被拒绝，而不会被削减

每一个拒绝都指明那唯一不够的维度，并且什么也不改变。把请求削减到剩余量，会让子运行在一个其调用方从未选择过的额度下启动；一个因为被悄悄只给了所要求的五分之一而中途停下的 subagent，比一个被干脆拒绝的更难诊断。这与 `dsh-run-admission` 和 `dsh-llm-claude-cli` 已有的拒绝报告方式一致。

### 畸形预算抛出；耗尽的预算返回拒绝

一个负数、带小数或超出安全整数范围的预算是存储或算术缺陷，而不是一次被耗尽的运行，两者绝不能经由同一条通道抵达调用方。耗尽是一个供分流的值；而畸形的预算是一个指明参数与字段的 `RangeError`，因为带着它继续会产出根本不成立的上限。这与 `admitRun` 在部署错误和被拒运行之间所做的划分是同一个。

## Consequences

R3 的第二条如今是：深度（继承）、授权（继承）、预算（在此），比该条目字面所暗示的剩余范围要小。持久化一次运行剩余额度、并拒绝启动已耗尽运行的调度器仍未构建，而本模块有意不去够它：它是对调用方所持值的算术，没有存储、没有时钟、也没有服务。

有两项后果值得写明，因为它们约束着别处的工作。`wallMs` 由调用方计费，因此一次从不为其耗时计费的运行，也永远不会因超时被停下。而 `costMicroUsd` 只有在有东西报告成本的地方才可强制：`TokenUsage.costMicroUsd` 现在携带由提供方报告的数值，`dsh-llm-claude-cli` 会提供它，而 HTTP 路由不报告任何成本，仍让调用方自行为 token 定价。两者都被记为限制，而不是被暗示为已经工作。

预留也不是租约：没有任何东西会让未结算的预留过期，因此一个丢失且未结算的子运行会一直占着父运行的额度，直到调用方去对账。这需要 R3 所拥有的持久运行记录。

## Alternatives considered

**只拿请求与父运行做检查而不扣除。** 更简单，但因上述原因并不成立：每次检查都独立地看到父运行的完整额度，因此父运行可以批准任意多个各自都「放得下」的子运行。

**只在运行结束时计费。** 操作更少，但那会让上限沦为建议 —— 等到总数已知时，token 早已花掉。随运行计费，才使一次拒绝能在额度尚存时把它停下。

**把预算并进 `dsh-subagent`，放在深度上限旁边。** 深度就在那里，这样两个上限会放在一处。被否决是因为预算并不专属于进程内的 subagent 委派：一个为租户的提供方进程设界的调度器需要同样的算术、却不需要 subagent 缝隙，而那样一来 harness 包就会拥有一项 Candy 控制面的关切。

**用浮点数表示美元。** 因漂移被否决；对一个在委派树中被扣减数千次的值来说，这不是假想问题。
