# Agent Note: 什么都没说的提供方

Status: implemented

[English](2026-09-05-the-provider-that-said-nothing.md) | 中文

## Problem

一次运行的挂钟时间是在块之间被检查的:每产出一个块之后,计量器把时钟与截止时刻比一次。而一个接受了请求随后就安静下来的提供方不会产出任何块,于是根本没有东西可供比对。

一次探测把一个沉默的源计量到一次只被允许 50 毫秒的运行上:

`{"raced":"still-waiting-after-1s","wallMsAllowed":50}`

二十倍于它的额度,而且还在继续。挂钟这个维度界定住了话多的那种失败,却把沉默的那种留给几分钟后的租约清扫——而在这整段时间里,该运行一直占着它父运行的额度和租户的额度。

## Decision

每一次读取都与运行剩下的时间赛跑。计量器持有源的迭代器,而不是用 `for await` 循环,因此一次永远不作答的读取,也会终结在与一次答得太慢的读取相同的维度上。

时钟在每次赛跑之前也会被读一次。一个已经越过截止时刻的调用方时钟不会拿到任何定时器,因为 `setTimeout` 把非正的延迟当作一个 tick——那会从一个时间已经耗尽的源里再读一个块。这项检查同时取代了原先块之间的那次比对,于是同一个截止时刻在同一个地方被强制一次,而不是两处。

持有迭代器就意味着持有关闭,而[防御性模式](../../../../docs/defensive-patterns.zh.md)中的两条规则决定了如何关闭。对一个仍在作答的源,静默是被等待的。而在截止时刻这条路径上则不:这条路径之所以存在,正是因为提供方停止了作答,而一个卡在同样沉默里的源同样不会回应关闭——等待它,会恰好把那次刚被截止时刻界定住的调用挂住。关闭仍然会被发起,因此一个持有提供方进程的源能听见它,而它的拒绝会被吞掉,而不是变成未处理的拒绝。

## Consequences

一个沉默的提供方现在按运行自己的挂钟时间结束它的调用,而不是按租约。

反向对照——读取时不与时钟赛跑——恰好让那四个新测试失败,而且是以挂满整个测试超时的方式失败,那正是这个缺陷以时长表达出来的样子。

收割提供方的进程仍然属于启动它的那一方。本包结束的是一条流;它不运行提供方,而它发起的关闭是一次请求,不是一次终止。

## Alternatives considered

**交给租约。** 租约是分钟级的,而且它的存在是为了释放一次被遗弃运行的占用,不是为了界定一次调用。一个每次调用都卡住的提供方所在的运行,会把它整份挂钟额度花完,而没有任何一次调用曾被切断。

**另设一个空闲超时。** 第二个维度需要一个没有任何依据的取值,而且会让一次调用活得比运行实际拥有的挂钟时间更久。运行本就带着那个唯一重要的数字。

**在每条路径上都等待关闭。** 那正是静默所要求的,而它会在唯一那条源已经证明自己不作答的路径上挂住。按源是否仍在作答来划分,才能把这项保证保留在它能被保留的地方。
