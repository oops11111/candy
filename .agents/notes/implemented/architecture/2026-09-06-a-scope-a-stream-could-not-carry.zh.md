# Agent Note: 一条流带不动的作用域

Status: implemented

[English](2026-09-06-a-scope-a-stream-could-not-carry.md) | 中文

## Problem

`dsh-subprocess` 会为它启动的每一个受管子进程自报,而它对租户一无所知。Candy 有租户,却没有办法从一次启动出发抵达它们:提供方进程是在适配器深处被启动的,没有会话,也没有属于自己的运行可指名。归属,正是启动记录仍然缺失的那一半。

一次启动确实拥有的,是它在"启动它的那次调用"中的位置,而调度器本来就为每一次被计量的调用解析出了运行。显而易见的机制是 `AsyncLocalStorage`,也正是 `ctx.agents.withInitiator` 用来把发起 Agent 贯穿驱动链的那一个。

## Decision

调度器在被计量流的**每一次拉取**周围进入一个运行作用域,而 `subprocess/launched` 监听器读取它。

是围绕每一次拉取,而不是围绕整条流。异步生成器的函数体是在消费方索要块时才运行的,运行在消费方的上下文里,而不是生成器被创建时的那个上下文。在把任何东西建立在这之上以前,一次仓库之外的探测先确认了它:

`{"generator":["at-first-yield:none","after-await:none"],"promise":"async-fn:RUN-2"}`

包在流创建处的作用域触及不到函数体的任何部分。而一个普通的 async 函数会保留它——这正是凭 Promise 的经验容易犯这个错的原因。围绕每一次 `next()` 重新进入,才能触及函数体,以及两次拉取之间的嵌套工作。

发生在任何被计量调用之外的启动会被丢弃。harness 自己的 bash、pwsh 与语言服务器子进程不属于任何租户,把它们归档进去会把某个租户自己的记录挤出一条按主体有界的踪迹——那正是折叠被加进来要阻止的那种挤占。

## Consequences

启动记录拿到了它当初就是为之而建的归属,而边界文档所要求的"每个被启动的提供方进程一条审计记录",对这个运行时所计量的那些运行来说,端到端地存在了。

反向对照正是本篇的要点:把作用域包在流的创建处而不是每一次拉取上,会让测试以"零条记录"失败。那个错误的版本能启动、能流式、能计费、能结算——它只是悄无声息地什么都没归属。

另外三条窄路径也被钉住:一次失败的 spawn 带着 `spawn-failed`;一次其运行已不在存储中的启动会被丢弃,而不是记到一个它指名不出的租户头上;而一条无法接收记录的踪迹,不会让它所描述的那次调用失败。

这个连接点原本被期待解锁的另外两件事——关闭被吊销账户的存活运行,以及运行结算时释放 agent——不在这里。两者需要的是运行的生命周期,而不是一次调用的,而这个作用域覆盖的是一次调用。

## Alternatives considered

**通过 `GenerateOptions` 传递运行。** 那会让继承来的 LLM 缝隙携带一个 Candy 专有的概念,而会话连接点当初的形状,正是为了避免这一点。

**给 subprocess 缝隙加一个租户字段。** 那样这条缝隙会持有一个它无法替自己的调用方填上的概念,而每一个 spawner 都不得不提供某个为真的值。

**按进程树归属。** 提供方进程是这个运行时的子进程,因此它的家谱是可知的。但那回答的是另一个问题——哪个操作系统进程——而且为了回答真正被问的那个问题,每次启动都要走一遍进程树。
