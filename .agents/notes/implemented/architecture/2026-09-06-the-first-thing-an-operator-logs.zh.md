# Agent Note: 运维人员做的第一件事

Status: implemented

[English](2026-09-06-the-first-thing-an-operator-logs.md) | 中文

## Problem

交付计划要求诊断面不返回令牌、凭据路径、原始环境值或另一个租户的元数据。一次探测读取了这个运行时所有面向运维人员的接口——某个租户的踪迹、运行时踪迹、一次被拒绝的结果、一条账本记录——没有任何一个携带秘密、密钥、池路径或另一个租户的身份。

真正携带的,是运维人员最先伸手去拿的那一个。对一次成功启动结果做 `JSON.stringify`,里面一个字节一个字节地含着租户已解密的提供方密钥:`AdmittedRun.secret` 是一个普通对象上的普通属性,而这次运行正是 `start` 返回的东西。

## Decision

`secret` 不可枚举,而这次运行带有一个把它替换成 `[redacted]` 的 `toJSON`。

两者都必要,而且覆盖不同的调用方。`JSON.stringify` 会调用 `toJSON`,因此正是它让这次脱敏是可见的,而不是一个悄悄消失的字段。`console.log`、`util.inspect` 以及每一个遍历自有属性的结构化日志器都会完全忽略 `toJSON`,并会从一个普通属性上把密钥打出来——不可枚举的定义才是拦住它们的东西。

读取 `run.secret` 不受影响。那正是启动提供方的调用方要做的事,也正是这次运行携带它的全部理由。

池根目录仍然可读。它是一条由摘要推导出来的路径而不是秘密,一个运维人员问"这次运行落到了哪个池"是一个真实的问题,而任何能在宿主上读取那个目录的人,拥有的已经比这条路径多得多。

## Consequences

那个最自然的诊断动作不再泄露凭据。

把测试集弄对花了第二轮,这值得记下来。第一次反向对照——去掉不可枚举的定义、保留 `toJSON`——通过了,这意味着测试从头到尾只演练了 `JSON.stringify`,而可枚举性根本没有被钉住。补上 `util.inspect` 与 `Object.keys` 的断言之后,对照就如它应该的那样失败了。一个没有任何测试能区分的机制,就是一个没人知道它在起作用的机制。

有四个接口探测下来是干净的,并被以干净的状态钉住,因此日后某个改动一旦开始泄露其中之一,会失败而不是悄悄通过。

## Alternatives considered

**把池根目录也脱敏。** 计划里点名了凭据路径,而池根目录正是凭据被写入的那个目录。但它同时是一个正当运维问题的答案,它不是秘密,而且要用上它所需的宿主访问权限本就超过它。以一个比"移除密钥"更弱的理由去移除它,会白白削掉真实的诊断价值。

**通过另一个调用交出凭据。** 那样 `admitRun` 会返回一个不含秘密的运行,外加一个取秘密的途径。它把凭据彻底挡在对象之外,代价是多一个调用,以及它自己那套全新的失败模式与生命周期规则;而且它并不能阻止调用方把那个调用的返回值打进日志。

**用一个带私有字段的类包住凭据。** 它的 `toString` 与 `inspect` 都可以定义成脱敏的,这比一个属性标志更强。但它也改变了每个消费方所持有的东西,而 `dsh-claude-cli-binding` 是直接解码那些字节的;属性定义在不改动类型的前提下就覆盖了同样那两条日志路径。
