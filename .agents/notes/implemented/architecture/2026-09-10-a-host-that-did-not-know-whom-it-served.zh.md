# Agent Note: 不知道自己服务于谁的主机

Status: implemented

[English](2026-09-10-a-host-that-did-not-know-whom-it-served.md) | 中文

## 问题

配对产生了设备 id 与令牌,一次性交给主机,而主机无处安放它们。

harness 只有一个持久身份 `dsh-anonymous-user-id`,而它是一个按安装生成、被刻意设计为*不*标识个人的 UUID。`host/` 中没有任何东西命名一台通过网络访问的机器:它是本地 Web GUI 的那一半——HTTP 服务器、SPA 服务器、目录选择器、插件清单——它们全都假定浏览器与 harness 是同一台机器。于是一台已配对的主机重启之后又变回未配对,而 R5 生命周期所问的第一个问题没有答案:这台机器服务于哪一台服务器,以谁的身份?

同一条要点所问的第二个问题——连接状态、离线检测、重连——并不缺失。`dsh-client-connection` 拥有带有界抖动指数退避的重试计划、浏览器的 `online`/`offline` 事件、心跳、代际,以及显式的 `reconnect()`。把其中任何一项再造一遍,都是在造第二套传输,而边界页禁止这样做。

## 决定

Candy 记录绑定,而对连接不做任何事。

`dsh-device-binding` 是一个持有单条记录的 Cordis 服务:部署的 origin、租户、设备、令牌,以及配对发生的时刻。它作为 `grant` 记录存放在 `ctx.credentials` 中,因为令牌是密钥而这道接缝本来就负责持久密钥——也因为 `modifyRecord` 是一次序列化的读-改-写,在存储支持时跨进程成立。

**唯一绑定,天然如此。**只有一个记录键,而 `bind` 拒绝替换已经成立的绑定。一台同时服务两个租户的机器,是一台任一租户的工作都能触及另一租户文件的机器,因此改变一台机器的服务对象是 `release` 之后重新配对——一次运维动作,而不是一次随手调用就会做到的事。这份互斥属于凭据接缝,这正是同时配对的两个 `dsh` 进程不可能都装上一条绑定的原因。

**重新配对同一台主机不是改绑。**同样的部署、租户和设备配上新令牌,只替换令牌并保留 `boundAt`,因为这台机器自绑定以来一直在服务那个租户,而轮换后的凭据不是一段新关系。

**来源被归一化为小写的 scheme 与 authority。**人们输入的 URL 会带路径、末尾斜杠或大写,而这些都不区分部署。比较原始文本会让针对同一台服务器的重新配对读起来像是另一台,而那正是 `already-bound` 存在所要拒绝的情形。

**存储的载荷在读出时被校验。**接缝把 grant 载荷当作不透明 JSON 存放并原样返回,因此手工编辑过的文件会作为一种寻常可能抵达这道边界。不是绑定的载荷会读成一台未配对的主机,并且不会挡住给这台主机配对。

## 考虑过的替代方案

**把绑定放在设置里,把令牌放在凭据里。**否决。两条必须彼此吻合的记录可能不吻合——从备份恢复的设置文件配上已轮换的令牌,指向的是一台凭据已经不在的设备——而使「唯一绑定」为真的那份互斥只覆盖其中一条。

**给这个服务一个 `serverOrigin` 配置字段。**否决:它不是组合者做出的随部署而变的选择,而是某个人执行过的一次配对的结果。把它配置化,会让一次配置修改悄无声息地把一台已配对的机器指向另一个部署。

**让 `bind` 替换任何已成立的绑定,依靠运维不要调用两次。**否决。这种失败是无声的,而其影响范围是前一个租户的文件;拒绝只是一个分支,却让这个错误从不太可能变成不可能。

**在这里建模连接状态,让调用方读一个对象就够。**作为对继承传输的重复而否决。`ConnectionController` 已经拥有重试计划、离线信号和重连命令,而覆在其上的第二套状态机,会成为对「是否已连接」的第二个答案,并且可能与第一个不一致。

**同时存归一化的 `serverOrigin` 与原始 URL,好让原文留存。**否决:原文没有读者。需要 URL 的一方从 origin 构造一个即可。

## 结果

已配对的主机在重启之后仍然知道自己应答哪个部署、扮演哪台设备。这是 R5 生命周期那条要点的前一半,也是此前不存在的那一半。

它是刻意惰性的。本仓库中没有任何东西用这条绑定去连接、出示它的令牌,或者去问服务器它是否仍然成立。这就是这一片之后诚实的位置:记录存在了,而会使用它的传输是继承来的那一套,而后者目前还没有可以指向的远程主机这一概念。

得知一条绑定已经失效仍然需要主动去问。服务端会拒绝已撤销设备的下一次运行——那是同一次发布落地的——但主机会一直保留绑定,直到运维释放它,因为这里既不轮询也没有推送。

有一项命名上的后果值得点明:绑定属于一个凭据存储,而不属于一台机器。两个 `$DSH_HOME` 不同的安装,对这条记录而言就是两台主机;这与其他每一项凭据一致,但并不是「一台机器一条绑定」所暗示的样子。

## 验证

`packages/control-plane/device-binding/tests/device-binding.spec.ts` 针对真实的 `dsh-credentials-local` 提供方与真实文件运行,而不是用替身,因为这条记录必须挺过重启并在并发下保持唯一,而替身两者都证明不了。它覆盖未配对的主机、在同一文件上第二次启动后读回的绑定、不含令牌的视图、来源归一化、两种输入拒绝、对另一租户/另一设备/另一部署的拒绝、一次轮换令牌并保留时刻的重新配对、同时落地的两次配对且只装上一条、释放与改绑、八种不可用的存储载荷以及一条类型不对的记录,还有令牌只抵达凭据文件而不去别处——达到该包的 100%。

四项变异对照证明这些用例确实在做判断:替换任何已成立的绑定、比较原始来源文本、信任存储的载荷,以及在重新配对时重置时刻,各自都会让至少一个用例失败,随后实现被还原。
