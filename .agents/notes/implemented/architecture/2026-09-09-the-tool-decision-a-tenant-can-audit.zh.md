# Agent Note: 租户可审计的工具决定

Status: implemented

[English](2026-09-09-the-tool-decision-a-tenant-can-audit.md) | 中文

## 问题

Candy 的租户踪迹已经记录准入、委派、模型路由、提供方进程启动、用量与结算，却没有记录工具调用的最终授权决定。Harness 已经拥有权限 waterfall（瀑布式事件）、审批解析、单调守卫、分发与结果。只观测 `tools/pre-execute` 会遗漏后续审批和守卫决定，而只观测 `tools/result` 无法区分授权拒绝与执行失败。

## 决定

Harness 工具注册表现在会在审批解析与所有单调守卫完成之后发布作用域化的 `tools/authorization`，时间点紧邻返回拒绝结果或允许分发之前。该事件携带既有执行身份与最终允许／拒绝决定。它是被等待的仅观测通知：监听器失败会被记录并隔离，任何监听器都不能改变决定或执行工具。没有观察者时，发布会同步返回，因此既有取消与分发调度不会增加一个 Promise 轮次。

`RunScheduler` 只在执行归属于一个会话，且该会话恰好对应一条开启中的 Candy 运行时消费这个通用事件。它写入 `event: 'tool'`，以工具名称作为 `action`，并以 `allowed` 或 `denied` 作为 `outcome`，同时带上既有运行谱系、租户与账户身份。它刻意不保留参数、拒绝理由、结果，或无法归因到唯一一条受管运行的调用。持久控制平面声明推进到版本 11。

## 后果

管理员可以把租户的工具授权决定与同一运行的路由、用量和终止状态关联起来，而无需 Candy 定义另一套工具注册表、审批服务或执行器。审计写入会在获准的主体开始执行前或拒绝结果返回前完成，但审计介质不可用不会把工具调用变成失败。

工具注册表测试固定了最终守卫决定、事件顺序与失败隔离。调度器组合测试固定了租户归因，并验证路径与拒绝理由不会进入序列化审计踪迹。反转允许与拒绝结果的变异会让该测试失败。

## 考虑过的替代方案

**包装 `tools/pre-execute`。** 未采用，因为审批解析和单调守卫在该 waterfall 返回后运行，所以包装层无法观测最终决定。

**根据 `tools/result` 推断授权。** 未采用，因为被拒绝的调用、无效参数、未知工具、取消、主体失败与执行后阻止都会产生错误结果。根据消息猜测会让审计语义依赖呈现文本。

**新增 Candy 工具网关。** 未采用，因为 Harness 已经拥有工具身份、权限、审批、分发与执行。Candy 需要的是最终决定的租户归因，而不是第二套强制执行流水线。
