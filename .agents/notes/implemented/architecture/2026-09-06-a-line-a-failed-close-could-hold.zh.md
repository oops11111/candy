# Agent Note: 一次失败的关闭就能占住的队列

Status: implemented

[English](2026-09-06-a-line-a-failed-close-could-hold.md) | 中文

## Problem

交付计划要求取消能够穿透提供方进程传播,并要求验证清理是否彻底,而其中属于 Candy 的那一半,是一次被取消的调用对它所属的运行做了什么。

一次探测针对已启动的运行时,在流进行到一半时取消了一次被计量的调用。结果在每个维度上都是正确的:流结束了而不是挂住,提供方的源被关闭,该运行被记上了调用方放弃之前那次调用已消耗的 42 个 token,运行保持开启,而它的下一次调用跑通了。这次审计现在被钉住,而不再是被假定。

探测真正暴露出来的东西在再往前一步的地方。一次运行的多次调用排成一列,而队列中的位置是在关闭被放弃调用的源**之后**才让出的。而关闭是可能失败的:一次被取消的调用关闭的是一个本身正在失败的源,而一个拆解时抛出的提供方——收割一个不肯死掉的进程——会让那次关闭以拒绝告终。于是这一列再也没有被让出,该运行之后的每一次调用都会在它上面一直等到这次运行结束。

## Decision

这一列在 `finally` 里被让出。关闭仍然会被等待,它的失败仍然会抵达调用方;改变的是那个位置无论如何都会被释放。

## Consequences

一次失败的拆解,代价是它所发生的那次调用,而不是整次运行。

反向对照——在关闭之后释放而不是在 `finally` 里释放——恰好让那个关闭一个正在失败的源的测试失败,而且是以挂满整个测试超时的方式失败,那正是这个缺陷以时长表达出来的样子。

## Alternatives considered

**吞掉关闭的失败。** 让出这一列而什么都不报告同样能修掉这次挂起,而它会藏起一个无法被收割的提供方进程——而那恰恰是边界文档最希望运维人员听到的事。

**在关闭之前释放。** 那样下一次调用会在上一次仍在拆解时就开始,于是同一次运行的两个提供方进程可能重叠——与这一列的用途正好相反。

## A note on the probes

在这一次之前有两个看似的发现,其实是探测本身的缺陷,而不是产品的:一个在信号已经触发之后才注册的 abort 监听器,以及一个对任何不带信号的调用都会挂住的假适配器。两者看起来都与一次取消缺陷一模一样——一条永不结束的流,以及一次运行的下一次调用永不开始。每一个都是靠加探针而不是靠对着代码推理找出来的:统计适配器被调用的次数,显示第三次调用已经抵达提供方,因此没有任何东西在队列里等待。一次探测,是关于它实际度量了什么的证据,而那并不总是它被写下来时想度量的东西。
