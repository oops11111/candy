# Agent Note：只有一个进程看到的撤销

状态：已实现

[English](2026-09-12-a-revocation-only-one-process-saw.md) | 中文

## 问题

设备栈承诺撤销会阻止下一次运行，但它的存储从 Candy 进程启动时加载的快照读取 `DeviceId` 与配对码记录。在双进程部署中，一个存活进程发出的配对码对另一个进程仍是未知；一个进程撤销的设备仍能通过另一个进程的运行准入路径继续使用。已有并发测试没有覆盖这个顺序，因为它在启动第二个进程之前就写入了配对码。

设备令牌认证也有相同的发现缺口。它会从介质重新读取匹配设备，但首先只在旧内存快照里寻找匹配项。因此，进程启动后创建的设备会被认证为未知，直到其他读取碰巧用该设备 id 刷新快照。

## 决策

安全决策从持久介质重新读取按键定位的记录。`findDevice`、`findPairingCode` 与 `claimPairingCode` 的第一步使用 `KvTable.getCurrent`，不再信任启动时快照。

对于无法预先知道键的查询，`KvTable.entriesCurrent` 通过现有 `KvUnit.loadAll` 约定重新加载并校验完整的一张表；只有全部记录都通过校验后才替换该表的本地快照，并返回新的稳定条目。设备令牌查询，以及租户的设备与配对码列表使用这条显式路径。普通 `get` 与 `entries` 保留同步快照语义，也不引入第二套变更通知系统。

## 考虑过的替代方案

**只刷新已知 id 与配对码摘要。** 拒绝，因为设备令牌认证在完成认证前并不知道设备 id，而管理列表也不知道另一进程新增了哪些键。这样只能修好准入，配对与认证仍取决于请求被路由到哪个进程。

**增加令牌二级索引与逐租户设备清单记录。** 对这种数据形状不采用。存储接缝能原子替换一条记录，却没有跨表事务；设备创建会因此依赖多个可能只落下一部分的索引。重新加载权威表能继续让单条设备记录作为事实。

**强制每个数据库只能有一个进程。** 拒绝，因为仓库的 canary 与回滚设计明确验证两个存活 Candy 进程共用同一个 SQLite 控制面。把可修正的读取路径变成部署禁令，会与该发布形态冲突。

## 后果

负载均衡后的配对交换可以发现其进程启动后才发出的配对码。运行准入能够看到另一进程创建或撤销的设备；设备令牌认证也不再依赖无关的 id 查询先替它预热快照。

刷新仍是拉取式的。`domain/changed` 仍只在进程内生效；需要当前跨进程枚举的消费方必须明确调用 `entriesCurrent`。该方法不伪装成推送失效机制，也不提供跨表事务。

## 验证

控制面存储测试在任何设备记录存在前先启动两个运行时。一个运行时写入配对码与设备，另一个发现并认领该码，把令牌认证作为第一次设备读取，再解析设备 id。在未修正实现上，用例先在配对码查询处失败；修正按键读取后，又在令牌查询处失败。

存储领域测试修改一个已打开领域背后的共享介质，证明普通迭代保持旧的稳定快照，直到 `entriesCurrent` 用经过校验的当前表替换它。
