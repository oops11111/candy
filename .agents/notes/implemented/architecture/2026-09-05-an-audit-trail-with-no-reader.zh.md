# Agent Note: An audit trail with no reader

Status: implemented

[English](2026-09-05-an-audit-trail-with-no-reader.md) | 中文

## Problem

`admitRun`被改成在每一种结局上都返回它的保险库记录，而断言之后的每一次拒绝也被改成指名它所拒绝的租户、账户与运行。两者都是对的修复，而两者都没有把事情做完：那些记录被返回给了一个把它们丢掉的调用方。`RunScheduler.start` 把 `audits` 交回去，然后什么都不写。

这与计量那一片在 `charge` 上发现的缺陷是同一个 —— 一份没有人读的报告 —— 只是高了一层。边界页要求运营方能够发现、遏制并审计跨租户尝试；而一次被拒绝的运行产出的记录抵达不了任何人，R1 与 R3 的要点也都收在同一句话上：持久化它们的那个存储仍未建成。

最要紧的那次拒绝还有第二个问题。`dsh-run-start` 里 `ledger` 阶段的拒绝只携带理由。拨款发生在准入之后，因此那时身份已经是已知的，而这次拒绝把它丢掉了 —— 一次被拒的运行，却说不出是谁的。

## Decision

`ControlPlaneStore` 为每个主体保留一条踪迹，而 `RunScheduler` 归档一次调度尝试所产出的一切。

踪迹是一扇看向近期活动的窗，不是一个档案库。域把它持有的每一条记录都放在内存里，因此一份无界的日志会让运行时无界地增长；`recordAudit` 为一个主体保留最近的 `retain` 条记录，其余的就没了。上限由调用方决定，因为一个部署保留多少历史是它自己的选择，而不是介质的属性；它以调度器的 `auditRetention` 配置字段的形式到达。

主体在尝试指名了租户时是那个租户，没有指名时是那个运行时。断言之后的每一个步骤都基于已验证的声明。一份验证不通过的断言指名不出任何这个运行时可以相信的租户 —— 而它偏偏是运营方最想要的那条记录 —— 因此它被归到拒绝它的那个运行时名下，而不是被丢掉或被猜测。`t_` 与 `r_` 前缀让这两个键空间不会相撞。

`RunStartRejection` 的 ledger 变体现在携带已验证的声明，理由与 `dsh-run-admission` 自己的那些拒绝相同。

记录在写入之前先按主体分组，因此一次尝试对每个主体是一次写入，而不是每条记录一次 —— 踪迹是一份完整文档，每一次追加都会重写它。

## Consequences

一次被拒绝的运行被记录在运营方读得到的地方：`auditsOfTenant` 用于一个租户自己的那些尝试，`auditsOfRuntime` 用于这个运行时在还不知道是谁的之前就拒绝掉的那些令牌。两者都能挺过重启，因为它们与账户和运行记录在同一个域里。

踪迹记录的是控制平面所观察到的东西，不多不少：一次运行启动了、一次运行被哪个步骤拒绝了，以及这次尝试产出的那些保险库操作。路由、委派、工具授权与终止状态在边界页里被点名，而不在这里，因为仓库里还没有任何东西产出那些记录。

保留期是那条诚实的限制。必须保存证据的部署会读取踪迹并把它送到一个真正是档案库的地方；掉出窗口的东西就没了，而 README 就是这么说的，而不是暗示一种介质并不提供的持久性。

## Alternatives considered

**每条记录一份文档，按时间做键。** 那才是一份追加日志的样子，而且一次写入只加一条记录，而不是重写一份文档。域会把每一条记录都载入内存，因此增长是运行时的，而清理仍然会是一次扫描。一条有界的踪迹，就是把同一个界限提前说清楚。

**丢掉那条无法验证的令牌记录。** 没有可以归档到的租户，而发明一个会把攻击者选定的身份放进某个租户的踪迹里。把它归到运行时名下，既保住了记录，又不相信那份令牌说的任何东西。

**给存储缝隙扩展一种追加型单元。** 那对档案库来说是正确的介质，而且是比这一次大得多的改动，也不该由 Candy 独自设计：`dsh-storage` 的 KV facet 就是今天各后端所实现的全部。

**把每条记录写成一次独立的存储调用。** 代码更简单，每个保险库事件一次介质写入，再加结局一次。按主体分组的代价是一个 `Map`，而它把一次已启动运行的两条记录变成一次写入。
