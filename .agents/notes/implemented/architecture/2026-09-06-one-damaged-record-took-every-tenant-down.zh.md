# Agent Note: 一条被损坏的记录让每个租户都停摆

Status: implemented

[English](2026-09-06-one-damaged-record-took-every-tenant-down.md) | 中文

## Problem

`RunLedger.restore` 拒绝一片不完整的森林:一条指名了没有任何记录能提供的父运行的记录会抛出。恢复在 `Service.init` 期间调用它,于是那次抛出让插件失败,运行时也就起不来。

一次探测写入了一条子运行记录,而它的父运行随后消失了——一次部分写入,或者一次带走了父运行却留下子运行的删除——然后启动:

`threw: failed to apply loader entry run-scheduler: restored run 'run-orphan' names parent 'run-gone', which no record supplies`

这个运行时上的每个租户,都因为一条被损坏的记录而停摆。拒绝背后的推理在它自己的范围内是成立的——对一个并不存在的父运行的占用,是没有任何东西能结算的,而悄悄丢弃它会丢掉账目——但拒绝并不是"丢弃"之外的唯一选择。

## Decision

一条其父运行不被存储持有的记录,会被收养为一个根,并像任何别的根一样被结算。

这不损失任何账目,因为恢复本来就会结算它所恢复的每一个根。这次运行无论如何都会在片刻之后被结算,唯一悬而未决的问题是"它花掉的东西记在谁头上"。而记录指名了它的租户,那也正是它父运行自己的结算本会把这笔账带到的地方。

父运行是在存储里被清空的,而不只是在被恢复的账本里。随后的结算会把记录从存储读回来,而一条仍然指名着那个缺失父运行的记录会把账记到那个父运行头上——也就是记到没有人头上。这个改动的第一版只在内存里清空,启动成功了,却让那个花掉了四十个 token 的运行的租户一分未记:与拒绝所要防止的,是同一种悄无声息的丢失,只是从另一个方向抵达。

这次收养会被记录到日志,指名那次运行、缺失的父运行,以及现在被记账的租户。

## Consequences

一条被损坏的记录,代价是它自己那次运行的账目精度,而不是整个运行时。

启动是在修复存储而不是在报告它:被收养的记录会被结算并删除,因此这处损坏不会撞上下一次启动。

有一个既有测试钉住了那次拒绝,它被删除而不是被保留。它构造的记录与这次的完全相同,并断言启动会被拒绝,而那正是被有意改变的行为;取而代之的测试断言账目得以保全,并且该租户可以重新开始。

它没有指名的损坏仍然会让启动失败——一条通不过 schema 的记录、一份已经消失的租户额度——而且没有修复路径。

## Alternatives considered

**丢弃这个孤儿。** 最初的决定拒绝了它,而且是对的:这次运行持有一份预留,并且已经花掉了一些东西,悄悄丢弃它会把两者都丢掉。收养保住了丢弃会丢掉的东西。

**只拒绝那个租户的运行。** 那能收住影响面,却对这条被损坏的记录不做任何决定,而运行时随后会持有一个它拒绝服务的租户,除了运维人员手工改存储之外没有回头路。

**离线修复。** 一个读取存储并重写它的独立工具,是面对损坏的通用答案,而它是一个没有人拥有的工具。这种形态在启动时就可以用记录本就携带的信息判定,因此不需要它。
