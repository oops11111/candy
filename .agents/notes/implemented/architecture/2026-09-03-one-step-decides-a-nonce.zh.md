# Agent Note: 一个步骤决定一个 nonce

Status: implemented

[English](2026-09-03-one-step-decides-a-nonce.md) | 中文

## Problem

`dsh-execution-assertion` 把 nonce 绑进签名并返回它，却不消费它，这是有意的：它不拥有任何持久的东西。`dsh-run-admission` 要求一个 `spendNonce` 端口，并且从不重试一个被报告为已消费的 nonce。在两者之间，这个端口就是 Candy 重放防护的全部，而它没有任何实现 —— 仓库里的每一个调用方提供的都是测试替身。

把它留给各个部署并不是中立的，因为最显然的那种实现是错的。端口返回的是 promise，因此它诱使人写成「先查这个 nonce，再插入它」。同一个令牌的两次并发准入，会在任何一次记录下来之前各自看到 nonce 是新的，于是两者都抵达凭据。那正是该端口存在所要阻止的失败，而在任何按先后顺序出示两次令牌的测试里，它都是看不见的。

还有两个选择既容易做错，做对又不花什么代价。用固定定时器而不是断言自身的过期时刻来界定保留期，要么会在断言仍可被准入时就遗忘 nonce —— 从而在 nonce 所关闭的那个窗口之内重新打开重放 —— 要么会留下已经无法拒绝任何东西的记录。而一个只以 nonce 为键的存储，会让一个租户通过抢先消费某个值来拒绝另一个租户的运行。

## Decision

`RunReplayStore.spend(claims, now)` 在一个同步步骤里完成读与写，并返回这个 nonce 是否是新的。调用方把它包进端口所返回的 promise 里；契约是：在询问与记录之间不得有任何 `await`。持久化实现用一条语句而不是先读后写来保持这一点 —— 一次在唯一性冲突时失败的插入，其受影响行数就是答案。

一条记录在其断言仍可被准入期间被持有，之后被视为不存在。那条界限属于断言，而不是某种策略：`admitExecutionAssertion` 会在准入抵达本存储之前拒绝一个过期断言，而两者在同一毫秒拒绝，因此一条记录恰好在它不再被需要时停止计数。

键是租户与 nonce，且带长度前缀，因此没有任何一对值能伪造它们之间的边界。分区不削弱任何东西，因为被重放的令牌携带其签名所绑定的那个租户，算出来的是同一个键。

`evict` 与 `spend` 分离，并且不改变任何决定。它回收内存，而它是一次调用而不是一个定时器，理由与 `RunLedger.expire` 相同：本存储不拥有时钟，而驱动其中一个的调用方也会驱动另一个。

## Consequences

单进程部署有了一个正确的重放存储。运行多于一个运行时进程的部署仍然需要一个持久化的，而现在那三项义务是被写下来的，而不是靠推断的。

本存储没有规模上限，这是刻意的：面对一个满了的存储，两种答案都是错的。遗忘一条记录会重新打开重放；拒绝一个新的 nonce 会拒掉一次合法运行。数量由一个最大断言生存期之内被准入的量界定，而部署会按它自己的签发速率来估算它。

## Alternatives considered

**基于 `storage-domain` 与 SQLite 后端来构建它。** 那是真实部署所需要的形状，而它是一个 Cordis 插件，带真实组合测试、schema 与迁移。它同时也是错误的第一步：持久化版本必须满足一份契约，而缺的正是那份契约。先写底座只会产出一个带着同样「先查后写」缺陷的持久化存储。

**把这个存储作为默认值折进 `dsh-run-admission`。** 那样一来，一个什么都没提供的部署会在跑着四个进程的同时，悄悄得到进程内的重放防护。端口是必填的，这一点才迫使部署回答这个问题；一个默认值则会又错又静地替它回答。

**给 `spend` 加一把显式的锁或队列。** 没有任何东西需要串行化：这个决定本来就不可分割，因为它不让出执行权。一把锁只会为一个根本无法交错的步骤，添上一种新的失败方式 —— 一个永远不释放的持有者。
