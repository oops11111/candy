# Agent Note: Candy 凭据保险库

Status: implemented

[English](2026-09-02-candy-credential-vault.md) | 中文

## Problem

Candy 保管每个租户的提供方账户密钥——DeepSeek API 密钥、Claude 或 Codex CLI 登录态——而 [Candy 运行时边界](../../../../docs/candy-runtime-boundaries.zh.md) 把凭据窃取与租户混淆列为必须持续关闭的滥用场景:加密信封、脱敏读取、按调用注入,以及立即阻止新工作的吊销。harness 自身的 `dsh-credentials` seam 无法承担这一职责。它以 `scope/id` 寻址记录,没有租户维度,而其本地提供方把记录以明文写入 `$DSH_HOME/.credentials.yaml`——这对单个操作系统用户自己的 harness 是合适的,对共享服务器上多个租户的密钥则是错误的。

## Decision

`@deepseek-ai/dsh-credential-vault`(`packages/control-plane/credential-vault`)把密钥封装为带版本 `CredentialEnvelope` 中的 AES-256-GCM 密文,并暴露 `sealCredential`、`openCredential`、`rewrapCredential`、`revokeCredential` 与 `redactCredential`。它没有 Cordis 服务,也没有存储;密钥环是参数,与 `dsh-execution-assertion` 接收签名密钥的方式一致。

**两种机制让密钥留在它的租户处,并且各自拦截不同的攻击。** `openCredential` 把信封中记录的 `userId` 与 `accountId` 同调用方指明的 `CredentialBinding` 做比较,拒绝那些放错记录、但存储字段仍然完好的信封。这些字段同时进入 GCM 附加认证数据,从而拒绝那些既被移动、其存储字段又被改写为与新记录一致的信封——这种改写是比较无法察觉的,因为此时每个存储字段都与攻击者的绑定一致。进入附加数据的字段带有长度前缀,因此任何不透明 id 都无法伪造字段边界。

附加数据取自调用方的绑定,而不是信封的字段。一次负向对照运行证明:通过公开 API 无法区分这两种取法——比较先行执行,因此在每一条抵达解密的路径上,信封字段已经等于绑定。这个选择因而是针对将来某次调整或删除该比较的改动的纵深防御,而不是本包任何测试所能观察到的行为。模块文档与包 README 都写明了这一点,并写明不要把它简化掉。

**吊销采用销毁而不是标记。** `revokeCredential` 会清空 nonce、密文与认证标签。标记的可靠程度只取决于遵守它的打开方,而且密文会在标记写入之前的每一份备份中存活;销毁密文使吊销成为记录本身的属性,而不是读取它的代码的属性。记录被保留以便元数据仍可审计,而再次吊销会保留最初的 `revokedAt`。

**轮换由密钥环驱动。** `CredentialKeyring` 指明一个当前版本,并保留打开尚未重新封装的信封所需的每个版本。轮换的步骤是:加入新密钥、设为当前、重新封装,然后不再保留旧版本——此后未被重新封装的信封将永久为 `unknown-key`。重新封装会保留原有的 `sealedAt` 并记录 `rewrappedAt`。

**每次操作都在结果旁返回一个 `CredentialAuditEvent`**,因此调用方无法在不同时取得该记录的情况下获得密钥。保险库产出审计记录,但不持久化它们。

## Alternatives considered

**扩展 `dsh-credentials` 使其加密,而不新增一个包。** 予以拒绝,因为该 seam 的键空间没有租户,无法在其中表达跨租户隔离;而且对每一条 harness 凭据记录加密,会改变浏览器会话密钥与提供方密钥的行为——这些内容刻意存放在运维人员自己拥有的可读文件中。

**存储一个吊销标记并保留密文。** 予以拒绝:这会让吊销依赖将来每一个打开方都遵守该标记,并使密钥可以从任何早于它的备份中恢复。销毁密文的代价是无法撤销吊销,而这并不是边界页面希望具备的能力。

**用密钥环密钥包装每条记录的数据密钥(完整的信封加密)。** 这层额外间接可以带来低成本换密——只需重新包装小小的被包装密钥,而不是整个密钥。目前予以拒绝,因为提供方密钥足够小,重新封装密文的成本不值得引入第二层密钥,而这层间接还需要自己的格式与失败模式。

**接收密钥管理服务句柄而不是原始密钥字节。** 予以拒绝,因为没有消费者:尚未选定任何部署目标,该接口将是被发明出来的而不是被推导出来的。密钥环参数保留了这一选择空间。

**在保险库内部把信封作为不可信 JSON 校验。** 予以拒绝,因为保险库没有读取方:从存储中加载信封的一方负责解析它们,而在这里重复这项工作等于臆测 R1 尚未构建的持久化格式。字段畸形仍会以 `corrupt` 快速失败。

## Consequences

Candy 现在可以保管、轮换并销毁租户密钥,且跨租户读取会快速失败,这正是 R1 退出证据中加密的那一半。单元覆盖固定了被移动的信封、已退役的密钥、同版本下的错误密钥、被翻转的密文字节、非规范字段、两种绑定不匹配、吊销拒绝后续读取,以及脱敏视图不携带任何被封装的内容。

边界页面归于凭据处理的三项属性在这里并未交付,并已记录在包 README 中。审计记录只被返回而不被持久化,因此在按租户分区的存储出现之前,没有任何东西持久记录一次读取。密钥的存储、分发与轮换排期属于部署方;保险库只校验密钥为 32 字节,无法区分已轮换的密钥与已泄露的密钥。而 `openCredential` 返回的 `Uint8Array` 是 JavaScript 无法可靠清零的,因此解密后的密钥会一直留在堆中可读,直到被回收——边界页面同样要求的"按调用注入提供方进程"必须在进程边界上限制这一暴露窗口。
