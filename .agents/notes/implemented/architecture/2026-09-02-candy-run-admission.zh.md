# Agent Note: Candy 运行准入

Status: implemented

[English](2026-09-02-candy-run-admission.md) | 中文

## Problem

R1 产出了四个包——[标识符](2026-09-02-candy-control-plane-identifiers.zh.md)、[执行断言](2026-09-02-candy-execution-assertions.zh.md)、[凭据保险库](2026-09-02-candy-credential-vault.zh.md) 与 [运行时池分区](2026-09-02-candy-runtime-pool-partitioning.zh.md)——每一个都只被单独测试过,且都没有消费者。它们能否契合只是一种假设,而它们各自强制执行的混淆代理规则,恰恰属于那种"每个部分都成立、却在接缝处失效"的性质:如果调度器用*请求*所指明的租户去打开凭据,却使用认证了另一个租户的断言,它会同时满足这四个包,又同时击败这四个包。

## Decision

`@deepseek-ai/dsh-run-admission`(`packages/control-plane/run-admission`)是调度器所做的那一次调用。`admitRun` 校验断言、消费其 nonce、打开凭据并解析池,返回一个 `AdmittedRun`,或一个标注了拒绝阶段的 `RunRejection`。

**`RunRequest` 只携带一个令牌,别无其他。** 它上面不存在租户、账户、提供方或池字段,而凭据绑定与池身份都读自已准入的声明。那种会击败组合的配对根本无法被表达——这与断言包所使用的"由参数列表强制执行"是同一手法,只是延伸到了接缝之上。

**顺序就是约定。** 断言在两个端口中的任何一个被调用之前就完成校验,因此不会有未经认证的声明抵达任何存储。nonce 在读取凭据之前被消费,因此被重放的令牌无法驱动重复的凭据读取。池最后解析,因为它不需要任何密钥。

**R1 记录的两个缺口变成了必填参数。** `spendNonce` 与 `findCredential` 是 `RunAdmissionPolicy` 上的端口。这两个存储在本仓库中都不存在,而把它们作为参数意味着:在部署方回答了重放与凭据查找之前,运行无法开始——断言包所记录的 nonce 缺口,如今成了调用方必须提供的东西,而不是调用方可能遗忘的东西。

## What integrating found

这个组合无法通过类型检查。`ExecutionAssertionClaims` 不携带 provider,而池键是 `userId + provider + accountId`,因此把两者组合起来将要求*调用方*指明提供方——正是边界页面所禁止的、由客户端选择的值,而控制平面本就知道它,因为提供方账户是与提供方绑定的。

由此引出两项改动。`provider` 加入了被签名的声明集合,并像其他 wire 字段一样在解码时对照封闭的提供方集合接受检查。而 `ProviderKind` 从 `dsh-runtime-pool` 移到了 `dsh-control-plane`,因为账户、断言与池都会命名它,而一个字符串字面量联合类型不会让该包失去它所宣称的任何"无外部依赖"性。[池的 Agent Note](2026-09-02-candy-runtime-pool-partitioning.zh.md) 曾把它放在池包中;那个放置位置在此被取代,两个包的 README 现在都指向新的归属地。

在不签发 `v2` 的情况下扩展被签名的声明集合是刻意为之:尚无任何 v1 令牌被持久化,而本仓库的预发布立场更倾向于正确的声明集合,而不是兼容性垫片。

## Alternatives considered

**让请求指明提供方。** 这是更小的改动,而它会重新打开断言包本要关闭的混淆代理路径:调用方可以把一个针对 DeepSeek 账户的有效断言与 `claude-cli` 配对,把运行落到一个控制平面从未组合过的池中。把它签名只需要一个字段的代价。

**把 `ProviderKind` 留在 `dsh-runtime-pool`,让断言包依赖该包。** 这保留了先前的放置位置,但会让断言包为了描述一次运行而依赖池键推导,这是本末倒置:断言位于池的上游。

**在每条调度路径中各自组合,而不是提供一次调用。** 每条路径都会重复这个顺序,而第一条搞错的路径——在校验之前、或在消费 nonce 之前就读取凭据——将会静默地出错。一次调用让这个顺序可以在单一位置被评审。

**同样用一个 sink 端口收集审计记录。** 目前予以拒绝:保险库已经返回它的记录,存储由调用方拥有,因此第三个端口只会增加一个参数,而不会增加任何由类型系统强制的义务。它被记录为一条限制。

这条理由本身成立，但最初写下的那条限制并不成立：它说拒绝时不返回任何审计记录，并把这当成一条边界而不是一个缺陷。`openCredential` 在失败分支上与成功分支上一样会返回记录，而本模块把失败的那条丢掉了 —— 丢掉的恰恰是保险库刚刚检测到的跨租户访问尝试。现在每一种结果都携带 `audits`（[run-admission 为每一种结果留下审计](2026-09-03-run-admission-audits-every-outcome.zh.md)）。

## Consequences

R1 的四个包现在有了消费者,它们的契合从假设变成了测试:单元覆盖固定了令牌变成凭据与池、由提供方决定落入哪个池、同一租户与账户下两个提供方相互分离、在触碰任何存储之前即被拒绝、被重放的令牌在第二次使用时被拒、nonce 在读取凭据之前被消费、凭据缺失、凭据已被吊销、属于另一租户的信封,以及被改标为与调用方一致的信封。

准入仍然止于一个决定。启动提供方进程、注入密钥、限制输出与取消属于 R2,而配额、并发与父级子集授权属于 R3——这些都记录在包 README 中,以免该边界被误认为强制执行。在打开凭据之前消费 nonce,意味着在凭据一步被拒绝的运行已经消耗掉了它的断言;这是安全的方向,并且会促使客户端重新签发断言,而不是重试一个已被消耗的断言。
