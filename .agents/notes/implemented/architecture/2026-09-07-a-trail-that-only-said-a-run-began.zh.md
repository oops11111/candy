# Agent Note: 一条只说了运行开始过的踪迹

Status: implemented

[English](2026-09-07-a-trail-that-only-said-a-run-began.md) | 中文

## Problem

一次完成的委派在租户的审计踪迹里留下四条记录:父运行的一条 `credential`/`open`/`ok` 与一条 `started`/`start`/`ok`,然后是子运行那次铸造出来的运行的同样两条。运维人员会就这两对记录问出的两个问题,一个都不在里面。

没有任何东西说第二次运行是第一次的子运行。血缘是存在的 —— `ExecutionAssertionClaims.parentRunId` 把它带进准入,`DurableRunRecord.record.parentRunId` 在运行开着期间持有它 —— 但审计记录没有承载它的字段,而持久运行记录在结算时就被删除了。于是一个委派了三个子代的 agent,它的踪迹读回来就是同一租户下四次恰好重叠、彼此无关的运行,而从中重建那棵树根本做不到,不是不方便而已。

也没有任何东西说一次运行已经结束。`RunScheduler.settle` 删除运行记录;没有记录接替它。因此一条踪迹显示的是一次运行开始了,然后就什么都没有了,永远如此;而一次运行结束的四种方式 —— 调用方关闭它、租约失效、账户被吊销、运行时重启 —— 彼此之间、以及与一次仍在工作的运行之间,都无从分辨。租约与吊销这两条路径,恰恰是一个在排查某个提早停下的 agent 的运维人员要找的东西。

## Decision

`RunAuditRecord` 增加 `parentRunId`,`event` 增加 `settled`。

关于某次运行的每一条记录都带上它当时的血缘:`started` 记录取自 `claims.parentRunId`,拒绝取自同一份声明,启动与被拒调用取自该运行的持久记录,新的终态记录取自删除前读到的那份记录。根运行不贡献该字段,而不是贡献一个显式的缺失,这样记录穿过介质来回一趟仍是它被写下时的那个值。

`RunScheduler.settle` 从它的调用方接过结算的成因,并在 `event: 'settled'`、`action: 'settle'` 之下归档一条记录,以该成因作为结果:`close` 给出 `closed`,`sweep` 的两个分支给出 `expired` 与 `revoked`,`recover` 给出 `recovered`。清扫只计算一次 `spent(runId)`,并把它走的是哪个分支传下去,而不是在写记录的地方再判断一次 —— 调用方是唯一知道成因的地方。

只有结算所针对的那一次运行会被记录。随其祖先一同关闭的后代留下了一条指名该祖先的 `started` 记录,因此那棵树可以从这一端读出来;而一个被委派的子代通常是以自己的名义结束的 —— 经由 `subagent/end` 走 `closeSessionRun`,它作为被询问的那次运行抵达 `settle`。为每一个被关闭的后代归档一条记录,需要在删除前把它们各自的持久记录读回来,而这件事血缘已经回答了。

记录是在费用落账、运行记录删除之后写的,因此它描述的是一次已经发生的结算;写入会被等待,其失败被记入日志而不是抛出,因为一个接不下这条记录的存储不该把一次已完成的结算变成一次失败。

`parentRunId` 不参与 `sameEvent` —— 那个把重复记录折叠成计数的比较。它是 `runId` 的一个属性,而 `runId` 已经在比较之列:两条指名同一次运行的记录指名同一个父运行,而一条不指名任何运行的记录,是在任何血缘被相信之前就被拒绝的。

终态记录现在也携带 `spent`:也就是结算在向出资方扣费之前算出的精确 `RunSpend`,其中包括从后代吸收的花费。折叠会逐值比较全部三个维度,因此两条除此之外完全相同、但 token、墙钟时间或微美元费用不同的终态记录,不会被合并成一条。

持久声明升到版本 5。在预发布立场下,版本 4 的介质不再被当作本版本读取,理由并不是它的记录形状不对 —— 它们能解析 —— 而是它们会把两个新问题都答错,而不是答不出来:旧踪迹里的每一次运行都读作没有父运行,每一次已完成的运行都读作仍然开着。

## Consequences

读 `auditsOfTenant` 的运维人员,可以从比运行本身活得更久的记录里,重建一个委派型 agent 的运行树,并看到其中每一次运行是怎么结束的。这是控制面里第一样能在结算之后留存下来的东西:额度保留一个聚合值,而关于一次运行的其余一切都随它一起被删除。

踪迹是一扇窗,不是一个档案库,而每次结算多一条终态记录,意味着在同样的 `auditRetention` 下它填满的速度大约快一倍。为查看近期活动而读踪迹的部署不受影响;想要历史的那种,本来就已经被告知要把记录送去一个真正的档案库。

一次运行花了多少,现在会与它为什么结束一起留存在同一条终态记录中。持久声明升到版本 9:版本 8 的踪迹虽能在没有 `spent` 的情况下解析,但若把它当作当前版本接受,会悄悄让运维人员的运行费用查询得到缺失答案。

`dsh-run-delegation` 里一个真实组合的测试端到端地钉住了委派这一情形:一个真实的调度器、一个真实的 SQLite 后端存储与一个真实的 subagent 运行时产出一个子代,它的 `started` 与 `settled` 两条记录都指名父运行,而父运行自己的记录一个都不指名。`dsh-run-scheduler` 里四个测试各钉住一种成因,一个钉住最终花费,还有一个钉住踪迹接不下记录时结算照样完成。存储测试证明不同花费数字不会被折叠到一起。变异检查确认了用量接缝:从终态记录中移除 `spent`,聚焦的关闭测试就会失败。

## Alternatives considered

**从运行记录的缺失推断结束。** 对于一次踪迹说它开始过的运行,`findRun` 什么都答不出来,确实意味着它结束了,而且这不需要改 schema。被否决:它只说出了*结束了*这一半,也是最没用的一半。成因才是把一个跑完的 agent 与一个被吊销账户切断的 agent 分开的东西,而缺失承载不了成因。它在重启之后也什么都答不出来 —— 那时两次运行的记录都已经不在了。

**把血缘放进 `action` 或 `outcome`,而不是放进一个自己的字段。** 被否决:这两个都已被占用 —— `action` 指名步骤,`outcome` 指名其结果 —— 而把一个 id 塞进任一个,都会让 `sameEvent` 把血缘当作事件身份的一部分来比较,而这恰恰是它不该做的。

**为一次结算所关闭的每一个后代都归档一条终态记录。** 在本次切片中被否决:每一条都需要在删除循环之前把它的持久记录读回来,而这一情形很窄 —— 父运行在子代仍开着时关闭,而委派路径通过在子代结束时就结算它们避开了这一点。子代自己的 `started` 记录已经指名了那个把它一并带走的祖先。

**把 `event` 保持在四个值,把结算按 `refused` 的样式归档为一个不同的 action。** 被否决:`refused` 意味着一次没有进行下去的尝试,而结算恰恰相反。复用它会让每一个按 `event` 过滤的消费方都出错,而换来的只是避开一次版本升级 —— 而预发布立场并没有要求我们避开它。
