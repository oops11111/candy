# Agent Note: 没人记录的那些拒绝

Status: implemented

[English](2026-09-05-the-refusals-nobody-recorded.md) | 中文

## Problem

交付计划要求运维人员能够发现并审计额度违规与跨租户尝试。准入会为每一次调度尝试归档一条记录,而一次探测在一个存活运行的账户被吊销、下一次调用被拒绝之后读取了该租户的踪迹:

`{"before":2,"after":2,"events":["credential/open/ok","started/start/ok"]}`

只有凭据打开与启动,关于那次拒绝什么也没有。准入永远看不到这些:一次运行只打开一次凭据,随后就一直发起调用,因此所有按次调用做出的判定——一个被吊销却仍在花费的账户、一个已用尽额度的运行、一个没有任何开着的运行认领的会话——都发生在没有写下任何记录的地方。这三者中最清晰的信号是一份被吊销的凭据再次被使用,而它恰恰是最不可见的。

## Decision

这个运行时拒绝的每一次调用都会被归档,记在 `event: 'refused'` 与 `action: 'meter'` 之下,并以失败码作为其结果。

调度器自己做出的拒绝就在它做出的地方归档。`dsh-run-metering` 内部的那些则通过一个新的可选 `refused` 端口上报,与出于同样理由而可选的 `now` 端口并列:手工计量的调用方两者都不传,也不会因此失去它原本拥有的任何东西。

记录在调用方被告知之前就已持久。该端口会被等待,而调度器自己的拒绝也在产出块之前等待其写入,因此读取踪迹的运维人员绝不会落后于一个已经据此行动的消费方。

该端口的实现自行了结自己的失败,绝不拒绝。一次拒绝会让流缺少本缝隙所承诺的那唯一一个终止块,而那比一次未被记录的拒绝更糟——有一个测试断言:即使存储无法接收记录,调用方仍会拿到它的终止块。

一次其会话指名不出任何本运行时仍持有的运行的拒绝,会被归档到运行时名下,理由与无法验证的断言相同:没有任何这个运行时可以相信的租户。

## Consequences

`auditsOfTenant` 现在能回答一个租户的运行被阻止做了什么,而不只是它们被允许开始做什么。

反向对照——去掉两条归档路径——恰好让那三个断言记录的测试失败,而不会让任何断言拒绝本身的测试失败。

踪迹仍然是一扇窗:落到 `auditRetention` 之外的东西就没了,而一个被反复拒绝的运行会把自己更早的记录挤出去。没有任何东西对一个不断重试而写入踪迹的调用方做限流。

## Alternatives considered

**归档记录但不等待它。** 这正是第一版实现的做法,而针对它的探测读到的踪迹仍然只有两条记录——调用方先看到了拒绝。对于一个其全部意义就在于被某个要作出反应的人读到的信号来说,落在反应之后是错误的顺序。

**让 `dsh-run-metering` 自己写踪迹。** 那需要存储、主体规则与保留策略,而这些都不该由一个只计量一条流的包拥有。端口把这个事实交给本就拥有它们的那一方。

**把拒绝记为一种新的事件种类。** `refused` 在存储的枚举里本就存在,用于准入自己的拒绝,而在计量处被拒绝的一次调用是同一件事只是晚了一层——另设一种会把同一个问题拆到两个名字下,并且白白提升一次 schema 版本。
