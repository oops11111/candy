# Agent Note: 六个早已存在的操作

Status: implemented

[English](2026-09-08-six-operations-that-already-existed.md) | 中文

## Problem

Candy 需要一个提供方账户管理 API:列出、创建、验证、设为默认、吊销、删除。这六个操作全都早已存在。`dsh-provider-accounts` 会创建账户并密封其凭据、列出一个租户的账户、移动默认项、通过一个由调用方提供的端口做验证、吊销与删除 —— 而它们每一个都接收租户,并拒绝那个租户并不拥有的 id,对别的租户的记录与一个从未签发过的记录一视同仁地回答 `not-found`。

缺的是一层传输,以及它必须做对、而现有任何一块都做不了的两件事:

租户。上述每一个操作都把 `UserId` 当参数接收,因此谁调用它们,谁就决定动谁的账户。还没有任何东西让这个决定无法被伪造。

验证器。`validateProviderAccount` 接收一个 `ProviderAccountValidator` 端口,而整个仓库没有它的任何实现 —— 检查一份凭据意味着与那个提供方对话,而只有它的集成知道该怎么做。

## Decision

两个包:一个装那个端口的注册表,一个把六个操作挂到信封上的插件。

**`dsh-provider-credential-checks`** 是验证器的缝隙。管理 API 索要一个裁定,而从不得知端点、请求或响应体;集成作答时也不知道这份密钥来自哪个租户、哪个账户。没有任何东西为之注册过的提供方,回答 `unsupported-provider` 而不是 `invalid-credential`,因为一个没有组合任何集成的部署,根本无从知道那份凭据是坏的。为某个提供方注册的第一个作答:第二个会是关于同一项事实的两种意见,而没有任何被陈述过的选择规则。

它之所以是一个独立的包,是因为 `dsh-provider-account-api` 是一个 function plugin,而一个包不能既 default 导出一个服务又具名导出一个 function plugin —— Loader 会丢掉 function plugin 的命名空间,本次改动在拆分之前就撞上了这一点。

**`dsh-provider-account-api`** 只补传输。抵达每一次领域调用的租户是 `actor.userId`,而 `dsh-control-plane-api` 不给处理器任何别的来源;因此想认可请求里的 `userId`,就得发明一次查找,而不是忘掉一次检查。

账户 id 在这里铸造,而不是接收。一个由调用方挑选的 id 可能与另一个租户的相撞,而领域会以 `account-already-exists` 拒绝一次相撞 —— 那就报告了另一个租户的账户存在。

这一层验证的,是传输层该负责的东西:提供方是那三个之一,密钥是不超过上限的非空字符串,`isDefault` 若存在则是布尔。密钥的上限之所以要紧,是因为它会抵达一次密封操作,而没有别的东西会为它设界。标签的规则留在 `dsh-provider-accounts` 里并被转发,因为重复它就是两个地方要改而只会记得改一个 —— 领域错误自身的消息被明确记为可安全返回。

API 的那些操作,与保险库自己的密封与打开记录,都抵达发起者的踪迹,连成功也包括在内:一个在排查某个被吊销账户的运维人员,需要看到是谁吊销的。两次写入都不能让它们所描述的操作失败。

密钥环的组装被挪进 `dsh-credential-vault`,成为 `assembleKeyring`。两个组件出于同一个理由读同一批变量 —— 一个打开租户凭据的运行时,与一个密封新凭据的管理 API,必须对"哪个版本意味着哪把密钥"达成一致 —— 而让它们各自组装,正是它们分歧的途径。

## Consequences

一个已登录的租户可以持有提供方账户,而要紧的那些性质是被钉住的,不是被断言的。二十六个测试启动一个 Loader 组合:真实的存储栈、持久存储、真实的 `dsh-host-webserver` 与本插件,全程存在两个租户,而会话正是像 OAuth 回调那样经由存储建立的。

其中包括:凭据从不出现在任何操作的任何回复里;同一提供方上的两个租户只看得见自己的;指名另一个租户真实的 id,在全部四个接收 id 的操作上,回答得与一个编造的 id 一字不差,并且让那个账户毫发无损;在创建请求体里塞一个 `userId`,不改变账户被创建给谁;一个被吊销账户的信封不再能打开,而其后对它的每一个操作都拒绝;一个抛异常的提供方检查回答 `500` 且不带它的任何一句话;而这一切在重启之后连同归属一起留存。

变异检查确认这些测试确实承重:可区分地回答 `not-found` 会让四个跨租户用例失败,去掉密钥上限会让它自己那个失败。

它没有补上的:没有管理员查看别的租户账户的视图,没有把每一个已密封信封重新包装到当前密钥上的界面,没有分页,而且 —— 在有集成组合进来之前 —— 没有任何 `validate` 真正问得到的提供方。

## Alternatives considered

**把凭据检查放在一个由配置提供的函数背后。**最简单,也不可能:`cordis.yml` 载不了函数,而一个指名模块的配置字段,会让 API 去解析并信任一次任意导入。

**从客户端接收账户 id。**REST 里常见,被否决:一个被挑选的 id 可能与另一个租户的相撞,而那次相撞的拒绝就报告了对方的账户存在。铸造不花任何代价,并且消除了这个问题。

**在这一层也验证标签,和领域各验一次。**被否决:那是领域的规则,它已经报告一个可安全转发的拒绝,而重复它会让两者有能力互相矛盾 —— 而这一层的副本正是没人会去更新的那一份。

**用 `PUT`/`DELETE` 并把 id 放进路径。**更符合惯例,目前被否决:信封注册的是精确路径,而路径里的 id 会毫无收益地被公布进日志与浏览器历史 —— 会话已经指名了唯一能行动的租户,而请求体承载这个 id 一样好用。

**让两个组件各自组装自己的密钥环。**在第二个组件需要它时被否决:它们必须对"哪个版本意味着哪把密钥"达成一致,而那段逻辑的两份副本,正是它们不再一致的方式。
