# Agent Note: 池根目录是被设为私有的，而不是被请求设为私有

Status: implemented

[English](2026-09-03-a-pool-root-is-made-private.md) | 中文

## Problem

`dsh-runtime-pool` 推导出一个池的目录就到此为止，它的 README 也是这么写的：路径只被推导，从不被创建。创建这件事被留给了「管理池的运行时」，而那个运行时还不存在。于是每一个真正启动提供方进程的调用方都自己创建目录，`dsh-claude-cli-binding` 里的四个进程测试各自长出了同一行代码，并附带一句点明该缺口的注释：启动到一个没人创建过的目录里，会在 spawn 处失败。

它们写下的那一行错在同一处。`mkdir(root, { recursive: true, mode: 0o700 })` 只对它自己创建的目录施加模式。一个已经存在的池根目录 —— 由先前的运行留下、由运维人员创建、在不同的 umask 下创建 —— 会保留它已有的权限，而 `mkdir` 会静默成功。池根目录正是提供方的已认证 home，因此下一次运行会把租户的 API key 写进一个另一个本地账户可能读得到的目录里。没有任何东西报告这件事，因为没有任何东西失败。

`recursive: true` 是另一半。它会凭空造出每一个缺失的祖先目录，因此一个写错的池基目录也能产出一个能用的池，位于一条没人准备过的路径下，权限则由那些祖先目录决定。fixture 正是依赖着这一点：它们中没有一个曾经创建过自己的池基目录，而加上这道守卫，正是把这件事暴露出来的原因。

这套代码本来就知道正确的形状。`dsh-attachment-local` 与 `dsh-fs-local` 都为此把 `mkdir` 与一次显式的 `chmod` 配成一对。唯独持有凭据的池根目录没有。

## Decision

`openRuntimePool(base, key)` 创建一个池根目录并把它设为 `0o700`，在创建之后用 `chmod` 施加模式，因此该模式是它所返回的那个目录的事实，而不只是它恰好创建了的那个目录的事实。打开一个已存在的池正是第二次运行加入它的方式，因此该调用是幂等的，并保留池中已有的内容。

基目录从不被创建。一个不存在的池基目录意味着部署从未准备好它的存储，现在缺失的基目录会抛出异常，而不是被凭空造出来。

不检查基目录自身的权限，这是一处限制而非疏漏。一个另一个本地账户可写的基目录，会让该账户在本包见到之前就创建或替换掉某个池根目录，而此后设置的任何模式都无法从中恢复。检查它意味着读取 POSIX 模式位，而那根本不描述 Windows 的访问控制 —— 那个平台的答案是 `dsh-sandbox-windows-acl`。在一个本包并非在所有运行平台上都能解释的值上做拒绝，等于一道在 Linux 上有含义、在 Windows 上毫无含义的检查，因此这项义务被写进文档，留给部署。

`runtimePoolRoot` 仍是一次纯推导。Linux 上的控制平面要在不创建任何东西的情况下解析一台 Windows 主机的池根目录，而那个调用方不能被迫去触碰文件系统。

## Consequences

四份手写副本没有了；进程测试调用的就是部署会调用的那个函数，因此它们关于租户隔离所证明的东西，是已交付代码的性质。

部署必须准备好它的池基目录。这是首次运行时的一处新失败，而它正是我们要的那一处：它点名了基目录，而那正是运维人员需要修的东西。

## Alternatives considered

**保留 `mkdir` 上的模式，去掉 `chmod`。** 那正是每一个调用方早已写下的代码，也正是那个洞：模式永远到不了一个已经存在的目录，而那恰恰是要紧的情形，因为一个已经存在的池根目录，正是先前某次运行往里放过凭据的那一个。

**用一次 `stat` 校验模式，并拒绝错误的模式。** 拒绝留给部署的是一个坏掉的池加一条消息，而纠正留给它的是一个能用的私有池。这里没有任何两个观察者可能产生分歧的东西，因此也没有可供检查捕捉的分歧。

**把基目录也一并创建，用 `recursive: true`。** 那正是 fixture 所依赖的做法，而它会把一条写错的路径变成一条静默可用的路径。大声失败的代价是部署首次运行时的一个错误；另一种做法的代价，是租户的 home 落在一条没人想要的路径下。
