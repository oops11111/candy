# Agent Note: 一份在量自己 fixture 的约定

Status: implemented

[English](2026-09-04-a-contract-that-measured-its-fixtures.md) | 中文

## Problem

共享的适配器约定套件断言：一次失败的运行不会发出任何携带适配器凭据的 chunk，而 `dsh-llm` 缝隙上的三个适配器都在跑它。每一个都通过了。

它们一个都没有在做脱敏。每一个 `failingRun` 都是照着行为良好的提供方写出来的 —— `Authentication Fails`、`Incorrect API key provided`、一次录制到的 CLI 认证失败 —— 而这些文本里都没有密钥。那条断言量的是 fixture，不是适配器；而它会一直通过下去，直到某个提供方改了它的错误文本，那时凭据抵达的是生产环境里的会话日志，而不是 CI 里的一次失败。

只修 Claude CLI 那条路由，会把同样的洞留在另外两个身上。这条性质属于缝隙：每个适配器都握着凭据，每个适配器都把提供方的文本变成失败，而这些失败去的是同样的地方。

## Decision

`LlmAdapterContractSubject` 增加一个必填的 `leakingRun`：一次失败的运行，其提供方在自己的输出里把凭据引述了回来。于是同一条断言量的就是适配器了。把它加到三个适配器上，当场就让其中两个失败 —— `dsh-llm-deepseek` 把一份拒绝凭据的响应体同时转发进了失败消息与它的 cause，而 `dsh-llm-pi-ai` 原样转发了 SDK 的文本。

`redactApiKey` 与 `redactChunkApiKey` 从 `dsh-llm` 作为普通函数导出，方式与 `dsh-subprocess` 导出 `scrubbedParentEnv` 相同：一份被每个适配器共享的定义，而不是每个适配器一份副本。只有适配器能施加它，因为唯有它同时握着凭据与提供方的原话 —— 一个已经离开适配器的失败，不再说得出它是用哪个秘密造出来的。

匹配的是字面密钥，而不是某个模式。模式需要知道每一家提供方的密钥形状，而且仍然会漏掉它不认识的那一种。空密钥会被拒绝而不是被搜索，因为按它切分会把文本围着占位符重新拼起来。

只有失败文本会被改写。模型输出是调用方自己的内容，悄悄改写会毁掉一个恰好在讨论密钥的合法回答。

## Consequences

三个适配器都会移除被引述的凭据，而第四个适配器要加到这条缝隙上，就必须先回答同一个用例 —— `verify-llm-adapter-contract` 会让一个实现了 `LlmAdapter` 却不跑该套件的包失败，因此这一点是被强制的，而不是被记住的。它的豁免名单上只有一条，属于那个不接触任何提供方的无密钥回放适配器。

回退三处修复中的任何一处，失败的恰好是它自己那条约定用例，因此每个适配器的脱敏都是被单独钉住的，而不是靠整个套件笼统地钉住。

## Alternatives considered

**在 `LlmRuntime.stream()` 里脱敏 —— 每个适配器的 chunk 本来就在那里汇合。** 运行时从来不知道那个凭据 —— 解析它是适配器的事，而把秘密往上交好让运行时去擦洗，等于把凭据多放进一个可能泄漏的地方。

**改为匹配一个凭据形状的模式，而不是字面密钥。** 那正是 `dsh-subprocess` 对环境变量名所做的，而它在那里是对的，因为那些名字可以猜，值却拿不到。这里确切的值就在手上，因此匹配它不需要任何启发式，也不会漏掉某个没人枚举过的密钥形状。

**只修适配器，不动套件。** 正是那个套件让这个缺口显形，也正是它为尚未写出的适配器把缺口继续关着。让一条安全断言搁在 fixture 的内容上，才是缺陷本身，而不是它所掩盖的那几处泄漏。
