# Agent Note: 有配对 API 却没有页面

Status: implemented

[English](2026-09-13-a-pairing-api-with-no-page.md) | 中文

## 问题

Candy 已能签发、列出、兑换、认证并撤销设备身份，`candy-host` profile 也能消费配对码。但已登录租户启动这条链路的唯一办法仍是手工 HTTP 调用。虽然 DSH 已提供设置外壳与响应式布局，随发的浏览器界面却无法完成属于 Candy 的身份步骤。

## 决策

通过现有 `settings.section` 插槽，在 `dsh-client-ui-settings-candy-account` 中贡献“设备”页。它使用浏览器会话 Cookie 调用同源 Candy 设备 API，并沿用现有的双提交 CSRF 请求头。该页面签发配对码、显示可复制的 `candy-host pair` 命令、列出设备与邀请元数据，并撤销选中的设备。

明文配对码只存在于控制器的易失 store 中。租户关闭提示或页面卸载时就会清除；后续列表读取只含元数据，绝不恢复配对码。每个浏览器侧类型都不含设备令牌。该页面继承 DSH 的导航、主题和手机宽度行为，而不创建另一套 Candy 表层。

## 考虑过的替代方案

- 构建 Candy 专用 Web 或手机应用。拒绝，因为 DSH 已拥有浏览器表层和响应式设置框架。
- 把设备管理放入 Windows profile。拒绝，因为签发和撤销租户自有身份需要已登录 Candy 用户；Host 只拥有配对码消费与本地绑定。
- 持久保存或重新获取明文配对码。拒绝，因为 bearer 邀请只应披露一次，而设备 API 有意让它不可恢复。
- 把设备并入服务商账户表单。拒绝，因为账户凭据与 Host 身份的生命周期和操作不同；独立设置页能在不新增外壳的情况下明确边界。

## 后果

已登录租户现在可以从现有桌面或手机设置面板完成 Windows 配对的浏览器一半，并撤销设备。该页面不增加传输或文件系统能力。DSH 仍需构建在连接与重连时消费已存绑定的远程 Host 传输；Candy 也仍需租户设备数量上限和已消费配对码清理策略。
