# Agent Note: 没有任何部署够得到的登录

Status: implemented

[English](2026-09-08-sign-in-that-no-deployment-could-reach.md) | 中文

## Problem

Candy 的浏览器登录既完整又够不到。`dsh-oauth-sign-in` 拥有 PKCE 回调、那四条路由、会话与 CSRF cookie,以及精确 origin 的钉定;`createOidcUserInfoProvider` 对着一个被钉住的密钥集校验 ID Token;`ControlPlaneStore` 持有那些尝试、会话与身份目录;`dsh-host-webserver` 持有那个套接字。在整个仓库里,`registerOAuthHttpRoutes`、`createOidcUserInfoProvider` 与 `enrollOAuthIdentity` 的调用点只存在于它们自己的测试中。没有任何东西把它们组合起来,因此没有任何部署能让一个人登录进来。

目录让情况比"少接一根线"更糟。登录要通过 `ControlPlaneStore.resolve` 把已验证的 issuer 与 subject 解析出来,而一个空目录谁也解析不出来。一个正确组合了路由并启动起来的部署,会拒绝每一个到来的人 —— 包括那位本该去登记其余所有人的运维人员。组合与第一个席位是同一个问题:任一单独存在,留下的都是一台无法接纳它第一个用户的服务器。

## Decision

`dsh-oauth-sign-in-web` 是那张部署面:它陈述提供方事实,把路由挂载到 `ctx.webServer` 上,并在任何路由存在之前登记好配置中的管理员。

**密钥集是一个文件路径,不是内联密钥,也不是发现。**它是每一份 ID Token 的信任锚,而一个能给服务器递上新签名密钥的端点,也能递上伪造的。路径同时把一大团密钥挡在一个因别的原因而被阅读的配置文件之外,并让轮换成为一个运维动作:把新密钥与旧密钥并排发布(由 `kid` 选择)、重新加载条目、在提供方停止用旧密钥签名后把它去掉。重新加载会重新读取文件,因此一次轮换不是一次重启。读不出来、不是 JSON、或者为空,都会让加载失败。

**客户端密钥按每次交换解析,走凭据缝隙并以环境变量兜底。**该缝隙自己的规则是消费方在每次操作时重新解析、绝不缓存,正是这一点让一次被轮换的密钥能抵达下一次登录。一个把密钥作为环境变量注入的部署不会组合凭据提供方,因此 `ctx.get('credentials')` 是那次可选读取,而在无人作答时由 `process.env` 回答。空值会大声失败,而不是不带认证地去交换授权码。

**管理员是配置,不是路由。**一个通过 HTTP 建立的席位,就是先到者可以认领的席位。这一个是两个配置字符串 —— 提供方精确的 `sub`,以及它所登录的那个 Candy 用户 —— 在加载时对着本部署本就信任的 issuer 生效。用 `sub` 而不是邮箱或姓名,因为后两者在多数提供方那里可被重新指派,而一个可被重新指派的身份就是一个可被继承的管理员席位。

三种状态,而规则正是为第三种而存在。未登记则创建。已按同一用户同一角色登记,是幂等的那一种 —— 重新部署、重启、第二次启动 —— 什么都不改变。登记成别的任何人,或同一个人但角色更低,则让加载失败,并把 `refused` / `administrator-bootstrap` / `already-enrolled` 归档到那个租户名下。`enrollOAuthIdentity` 在冲突时什么都不写,因此没有那条记录,这次尝试将不留任何痕迹;而"同一个人、更低角色"是其中最要紧的一种,因为悄悄把它抬上去,就是靠编辑一个没人当作授权批准来审阅的文件,把一个成员提升成了管理员。

引导用的那两个键要么都写、要么都不写:只写一半会让加载失败,因为那会在"读起来像是登记过了"的同时谁也没登记。

## Consequences

一份 `cordis.yml` 现在能产出一台人可以登录进去的服务器。十八个测试钉住了它,其中十二个针对由 Loader 启动的真实组合 —— 真实的存储栈、真实的持久存储、真实的 `dsh-host-webserver` 与本插件 —— 并通过 HTTP 对着监听端口断言;用的是 `node:http` 而不是 `fetch`,因为那些路由是靠 `Host` 头钉在精确的公开 authority 上的,而 `fetch` 禁止设置该头,否则每一个用例都会因为一个与任何断言都无关的理由被拒绝。

别的什么都没变。没有任何路由、cookie、校验步骤或存储操作被搬进这个包;它持有的是配置、一次文件读取、一个登记判定与一个密钥加载器。

它不做的事:没有发现,因此提供方挪动端点时需要更新配置;每个部署一个 issuer,因此联合两家提供方无从表达;而登记只做引导 —— 添加第二个人、改变角色、移除身份都没有界面,运维人员想撤掉某个会话同样没有。那些属于已认证的管理 API,那是下一步,目前还不存在。

变异检查确认这些测试确实承重:把任何已存在的登记都当作幂等,会让冲突用例失败;接受一个空密钥集,会让信任锚用例失败。

## Alternatives considered

**在加载时从提供方的 `jwks_uri` 取密钥集,或者跑完整的 OIDC 发现。**在本步骤中被否决:发现让提供方的元数据端点有能力改写一台已经启动的服务器的校验方向,并把一次启动变成一个网络依赖。配置出来的路径是更窄的那种信任关系,而它所需要的轮换流程,是一个写下来的运维动作,而不是一个隐含的动作。

**在加载时解析一次客户端密钥并把它捕获下来。**更简单,被否决:它悄悄破坏了凭据缝隙的重新解析规则,于是一次被轮换的密钥会持续让交换失败,直到有人重启进程 —— 而且没有任何信号说明原因。

**开一条首次运行的登记路由,用一次性令牌把守。**被否决:它把一个管理员席位放到了网络上,而那个令牌又变成第二个需要分发与撤销的秘密。运维人员本来就要在那台服务器上写的配置,不额外花任何代价,而且没法被抢跑。

**把引导放在与路由挂载不同的插件里。**被否决:它们是同一项事实 —— 这个部署能不能接纳任何人 —— 而拆开它们会让"组合出一台挂载了登录却拒绝所有人的服务器"重新变得可能,而那恰恰是本记录存在要消除的状态。
