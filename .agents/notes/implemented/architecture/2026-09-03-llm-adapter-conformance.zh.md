# Agent Note: 提供方适配器的一套一致性套件，以及它发现的泄漏

Status: implemented

[English](2026-09-03-llm-adapter-conformance.md) | 中文

## Problem

[多租户运行时计划的 R2](../../proposed/architecture/2026-09-02-multi-tenant-cli-agent-runtime.zh.md) 要求建立一套提供方契约套件，覆盖成功、畸形输出、超时、配额、取消、崩溃与密钥泄漏。其中一部分已经被强制执行：`dsh-llm/invariant` 包住每一条已注册的提供方流并检查 chunk 文法 —— 块的配对、唯一的 usage、唯一的终止 finish、其后不得再有内容。没有任何关卡覆盖的，是文法无法表达的那些行为。被取消的运行会落定吗？被放弃的运行会释放它启动的进程或打开的套接字吗？适配器持有的凭据能通过一条错误信息到达调用方吗？

这些性质此前都是各个适配器的私事，也就意味着它们都是各个适配器的私下假设。没有任何东西要求新适配器把它们讲清楚，也没有任何东西检查既有适配器是否仍然守住它们。

## Decision

`@deepseek-ai/dsh-llm-adapter-contract` 把它们讲清楚一次，形式是一套由适配器自己的 spec 文件对自身运行的套件。它提供八个用例：正常运行恰好一个终止 chunk、失败运行也有终止 chunk、在运行开始前与运行途中被取消都会落定、被放弃的运行会被释放，以及任何 chunk、报告出的失败或抛出的错误中都不含原样的凭据。这条缝隙上的每一个适配器都运行它 —— `dsh-llm-deepseek` 与 `dsh-llm-pi-ai` 走 HTTP，`dsh-llm-claude-cli` 走被启动的进程 —— 这正是它成为共享契约、而不是把某一个适配器的私有测试写三遍的原因。

### 它跑在缝隙上，而不是适配器上

被测对象提供的每一条流都来自 `LlmRuntime.stream()`，绝不来自适配器自己的 `stream()`。这是一次修正而非最初的设计：第一版直接驱动适配器，对 `dsh-llm-deepseek` 八个用例中失败了五个。读运行时的代码给出了答案 —— `adapterFailureChunk` 把适配器的抛出转换成终止的 `error` 或 `aborted` finish，因此「恰好一个终止 chunk」的保证属于运行时。DeepSeek 选择抛出；Claude CLI 适配器选择产出 finish；两者都合规，而只有在缝隙这一层它们才等价。一个对着原始适配器运行的套件，会让合规的代码失败，同时测试一份没有调用方依赖的契约。

### 它发现了一个真实的泄漏

把放弃用例跑到 `dsh-llm-claude-cli` 上失败了：一个停止读取的消费方会让 CLI 进程继续运行。该适配器的生成器没有 `finally`，因此半途关闭它只销毁了 stdout，什么也没有回收。修复方式是跟踪生成器是否走完了自己的协议，若没有则终止进程树 —— 是精确而非无条件的，这样正常结束的运行不会收到一个它并不需要的信号。这正是 R2 所要求的进程树清理，而在一套共享套件提出要求之前，它并不存在。

### 释放采用轮询，而这个区分是挣来的

同一个用例随后在 `dsh-llm-deepseek` 上失败了，看起来像第二个泄漏，其实不是。那个适配器在 `finally` 中中止了它的消费方信号；只是套接字要在之后的一个 tick 才关闭，而套件却立刻做了断言。现在释放会轮询到一个截止时间 —— 及时的释放依然很快，而从不释放的适配器是失败而不是挂起。这段插曲正是套件自己的测试之所以存在的原因：一致性套件内部的一个时序假设，会报告出并不存在的缺陷。

### 套件测试它自己

一个不会失败的一致性套件比没有更糟，因为它报告了自己并未挣得的信心。它的 spec 用刻意不合规的被测对象来驱动它 —— 一个永不结束的运行、一个结束两次的运行、一个从不释放的适配器，以及把密钥分别放进 chunk、放进报告出的失败、放进抛出的错误、放进没有 stack 的错误 —— 并断言是哪个用例拒绝了它。Claude CLI 的那处修复也通过回退它、确认恰好是放弃用例失败来做了检验。

### 泄漏搜索遍历一切，而不只是 message

凭据会从适配器没有想到的那个字段抵达调用方，因此搜索会把每个值完全摊平：错误的 message、name、stack 与 `cause` 链，以及每个嵌套对象的每个属性，并带环路保护。`secret` 必须是适配器构造时所用的那个确切值；给占位符的套件会通过，却什么也没有证明，接口文档就是这么写的。

## Consequences

现在这条缝隙上的每一个适配器在每次运行该套件时都会断言这些性质。`dsh-llm-pi-ai` 是最后接入的，八个用例一次通过、无需改动，而这正是共享契约想要的结果：套件讲清楚的是一个没有它也已经具备的性质，而不是把与它一同写就的那个适配器碰巧做了什么固化下来。它的被测对象只让该包的模拟服务器多了一项能力 —— 把响应保持打开而不是结束它 —— 因为放弃用例是普通提供方替身不会编排的那一个场景。

计划中点名的三种夹具 —— 超时、配额、崩溃 —— 合并成了一个用例。它们到达适配器时都是一次失败的运行，而套件断言的是适配器必须拿一次失败怎么办，而不是它由什么引起。要区分它们的适配器需要为该区分自备测试。畸形输出同样不在这里：它是每个适配器针对自己线格式的解析问题，而 `dsh-claude-cli-protocol` 已经为 CLI 覆盖了它。

泄漏搜索只能发现原样出现的凭据；经过编码、哈希或截断后到达的则能通过。这针对的是「值被原样透传」这一常见情形，而不是对抗性的编码者，README 也是这么写的，而没有暗示更强的覆盖。

## Alternatives considered

**改为扩展 `dsh-llm/invariant`。** 它已经包住每一条提供方流，因此取消与释放原则上可以在那里检查。被否决是因为不变量伴生模块观察的是生产流，只能报告一次真实运行恰好做了什么；它无法取消一次运行、放弃一次运行，或安排一次失败。这些性质需要一个能*制造*出该情形的测试，那是套件，不是观察者。

**让每个适配器自己测试自己的生命周期。** 这正是本仓库此前的做法，也正是 Claude CLI 那处泄漏存在的原因。私有测试编码的是私下假设：没有任何东西把该性质摆到明面上，因此也没有任何东西注意到它的缺席。

**同步断言释放。** 更简单，也是错的：它会因为一个在下一个 tick 才正确关闭的套接字而判 `dsh-llm-deepseek` 失败。轮询到截止时间，才使一套套件既能覆盖被终止的进程，也能覆盖被关闭的连接。
