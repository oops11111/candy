# Agent Note: 主机无法消费的配对码

Status: implemented

[English](2026-09-12-a-code-the-host-could-not-spend.md) | 中文

## Problem

服务端已经能签发并兑换一次性设备配对码，主机也能保存由此得到的凭据，但没有任何主机侧操作把这两半接起来。运维人员只能通过临时胶水代码提交配对码再调用 `bind`，使回复校验和秘密传输策略散落到每个调用方。

## Decision

`dsh-device-binding.pair` 归一化运维人员输入的部署 origin，在发送一次性配对码前拒绝已有绑定，把配对码提交到 `dsh-device-api` 的既有兑换路由，校验返回设备凭据的每一个字段，再通过已有的唯一 `bind` 操作安装它。

配对码请求与 Bearer 令牌请求都设置 `redirect: 'error'`。部署必须在运维人员选定的 origin 直接回答；两种凭据都不能经由重定向被携带出去。`400` 是部署对配对码的拒绝判定，未约定状态和畸形凭据是协议错误，网络失败则原样传播，交给调用方或继承的连接所有者分类。

此方法只执行一次兑换。它不增加命令、设置页、重试计划、连接状态、Remote Gateway 或 WebSocket 协议。

## Alternatives considered

- 把配对放进新的 Candy 桌面页面。拒绝，因为 DSH 拥有设置框架，Candy 不得建立第二套桌面／手机表面。
- 让每个传输调用方自行提交配对码并调用 `bind`。拒绝，因为凭据校验与重定向策略必须只有一个所有者。
- 在网络请求期间一直持有凭据存储的变更锁。拒绝，因为不可达服务器会阻塞无关凭据操作；剩余的双进程竞态可以消费失败方的配对码，却无法安装第二条绑定。

## Consequences

主机有了一个可复用的服务入口来完成配对，不完整或被重定向的回复永远不会进入持久存储。两次同时发起的配对仍可能都先花掉服务端配对码，再由凭据接缝选出唯一绑定；失败调用会以 `already-bound` 被拒绝。命令表面与传输消费仍是明确的 R5 后续工作。
