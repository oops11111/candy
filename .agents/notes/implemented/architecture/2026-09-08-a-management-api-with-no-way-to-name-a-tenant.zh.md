# Agent Note: 一个无从指名租户的管理 API

Status: implemented

[English](2026-09-08-a-management-api-with-no-way-to-name-a-tenant.md) | 中文

## Problem

Candy 的管理操作决定谁拥有一个提供方账户、一个租户可以调用哪些路线、一台设备授予了哪个工作区。它们每一个都需要一个租户,而租户可以来自三处:路径或请求体里的 `userId`、Harness Host 访问令牌,或者一个浏览器会话。

前两者不是身份。路径参数是调用方自己的主张。Host 令牌授权的是一个进程 —— 那是一个被启动的应用为够到自己的载体所出示的东西 —— 而那个载体上的每一个会话共享它,因此一个据以确立租户的令牌,会让这个部署的每一个用户都成为那个租户。边界页早已把两者都排除掉,并且在没有第三个选项被建起来的情况下断定:"账户、路线策略、设备与工作区授权的变更端点,在那份会话权威存在之前保持不可用。"

那份权威现在存在了。不存在的是任何能让它成为**唯一**选项的东西:没有任何东西阻止一条路由去读 `body.userId`,而每条路由否则会各自决定"记录不存在""记录属于别的租户""角色不足"分别回答什么。

## Decision

一个信封 `registerApiRoute`,以及一个调用方够不到任何构造方式的 `Actor`。

处理器拿到的是 actor 与已解析的请求体,别无任何能携带租户的东西。持有一个 `Actor` 的唯一途径,是出示了一份存储认证过的会话 cookie;因此一条想要认可 `body.userId` 的路由,必须自己发明一次查找,而不是仅仅忘掉一次检查。

**次序即契约。**origin 最先,因此一个不指向本部署的请求永远到不了会话查找。方法第二,因为一条不服务该方法的路由没有什么需要认证。会话第三 —— 身份的唯一来源 —— 而 CSRF 在同一次调用里被证明。角色第四,因此一个角色不足的已认证者拿到 `403` 而不是 `404`。请求体最后,有界,并且只对一个已经确立为可以发送它的调用方读取。

**写操作必须声明它的 origin。**`Host` 在每一种方法上被检查,`Origin` 在写操作上额外被检查,因为浏览器在跨站写操作上会发送 `Origin`,而精确匹配正是把这个租户自己的页面,与一个仅仅知道该 URL 的页面分开的东西。一个不带 `Origin` 的写操作会被拒绝,而不是被假定为同站。会话缺失与 CSRF 证明失败作答一致:说出是哪一个,等于报告了调用方手上的 cookie 是不是一个活着的会话。

**别的租户的记录就是一条不存在的记录。**`notFound` 是处理器报告一条 actor 不该持有之记录的唯一方式,并以 `404` 作答、不带细节。一个把"不是你的"与"没有这个 id"分开的错误,会向猜到它的人确认这个 id 存在。角色拒绝是刻意的例外:这个人是已知的,这条路由是存在的,因此 `403` 告诉他们一件真事,而不确认任何记录。

**每一次回复都是 `no-store`**,并连同否定内嵌框架、类型嗅探与 referrer。它们每一份都是一个租户的数据、在一次会话上作答的;一个共享缓存或一个被还原的前进后退页面,会把它交给下一个拿着这个浏览器的人。

请求体上限是停止读取而不是关闭套接字,而且拒绝在未读余量被丢弃之前先作答 —— 先销毁它会把一个 `413` 换成一次客户端无法与崩溃区分开的挂断。

## Consequences

第三步的端点,以及在它们之后的每一条管理路由,声明的是一个路径、一组方法、一个最低角色、一个操作名与一个处理器。它们无法回答信封没有定义的状态,无法可区分地报告一条跨租户记录,也无法从请求里读出一个租户。

二十二个测试钉住了它,多数针对一个真实的 `node:http` 服务器:身份来自会话,处理器看不到别的租户;没有会话是 `401`,处理器一次都没跑,也没有任何东西被归档到某个租户名下;成员访问管理员路由是 `403`;外来的 `Host`、外来的 `Origin`、缺失的 `Origin`、不匹配的 CSRF 头与缺失的头,各自都被拒绝;超大请求体是 `413`,无法解析的 JSON 是 `400`;空的写请求体不算格式错误;路由不服务的方法在认证之前就是 `405`;而不论一个请求以何种方式结束,`no-store` 都成立。四种 HTTP 客户端造不出来的情形 —— 没有 `Host`、非法的 `Host`、重复的 `Host`、没有方法 —— 直接调用处理器覆盖。变异检查确认了最要紧的三条:去掉 `Origin` 检查、让成员通过管理员路由、可区分地回答 `notFound`,各自只让自己那一个用例失败。

信封自己没有任何路由,只有一条没有按操作授予的角色阶梯,也没有限流 —— 那属于部署前面的反向代理。审计汇聚点是一个参数,因此一个不提供它的部署什么也不记录。

## Alternatives considered

**让每条路由自己用 `authenticateOAuthHttpRequest` 认证。**这个函数已经存在并返回会话,一条路由用三行就能调它。被否决:它让每条路由都要为同样的六项检查、同样的次序负责,而失败模式并不对称 —— 在某一次写操作上忘掉 `Origin`,或者在一处回答 `403` 而另一处回答 `404`,在有人把两处都读一遍之前是看不见的。把它们集中起来,意味着一条新路由靠构造就得到了它们。

**让处理器自己写响应。**更灵活,并因同样的理由被否决:这里的状态码**就是**安全面。一个能调 `response.writeHead` 的处理器,能为一条本该读作不存在的记录回答 `403`。

**从路径取租户,再与会话核对。**一种常见形状,被否决:它让调用方的主张一开始就成为请求的一部分,于是那次核对可以被忘掉;而且它毫无收益地把租户 id 公布进 URL 与日志 —— 会话已经恰好指名了一个租户。

**对别的租户的记录回答 `403`。**听起来诚实,被否决:对一个具体 id 回答 `403`,就确认了这个 id 存在。唯一安全的答案,是一个从未签发过的 id 会得到的那个答案。
