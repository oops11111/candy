# Agent Note: A grant that funded every run

Status: implemented

[English](2026-09-04-a-grant-that-funded-every-run.md) | 中文

## Problem

`dsh-run-admission` 通过一个 `findBudget` 端口读取一次运行的额度，而 `dsh-control-plane-store` 对其中根运行那一半的回答，是返回该租户存下来的预算。那个回答界定的是一次运行，不是一个租户。

没有任何东西消耗那条记录。一个被授予一百万 token 的租户针对一百万启动一次运行、把它们花掉、关闭它，然后针对同一个一百万启动下一次 —— 存储每一次都返回同一个值，因为没有任何一步向它写入过。两次运行同时存活则更糟：每一次都是针对整份授予额度被准入的，因此它们合起来可以把它花掉两遍。

调度器自己的 README 把这个缺口叫作「没有花费回写」，而交付计划 R3 的那条要点正是收在它上面：「运行记录是普通数据而没有任何东西存储它们，因此一次重启仍然丢失每一个开启中的运行，而且没有任何花费被折回租户的持久额度」。边界页所要求的那个租户级界限并不存在；存在的是一个挂着租户名字的按次运行上限。

## Decision

租户是每一棵委派树所悬挂的根，并且它的记账方式与父运行完全相同。

`dsh-tenant-allowance` 持有这条记录：运营方设定的 `grant`，以及其已结算运行从中取走的 `consumed`。`remainingAllowance(allowance, held)` 同时减去消耗，以及该租户每一次仍然开启中的运行的预留；并且为一次被扣住的运行收取一个属于它自己的并发名额，外加它可以下发的每一个名额 —— 这正是 `reserveChild` 在低一层所做的算术。于是 `grant.children` 界定的是该租户的整片森林，而不是其中任何一棵树，这正是 `RunScheduler` 此前拒绝擅自发明的那个租户级并发上限。

授予额度与消耗并排保存，而不是就地递减。单一的递减数字同样能回答准入，却会丢掉运营方授予了什么 —— 而那是任何配额报告的一半 —— 并且让修改授予额度变得含糊。同时保留两者让它变得确定：`setTenantGrant` 替换授予额度并保留消耗，因此在周期中途把配额翻倍，是让该租户总共可以花两倍，而不是抹掉它的历史。

消耗被记录而不是被封顶，理由与 `RunLedger` 如实记录一次超支运行相同：提供方账单是多少就是多少。只有「现在可以启动什么」这个答案被夹在零上。

`RunScheduler` 是持久的那一半与存活的那一半相遇之处，而它现在持有两者都不曾有的那个事实：一棵树属于哪个租户。`RunRecord` 指名的是一次运行和它的父运行，而不是一个身份，因此调度器保存一张从根运行到 `UserId` 的映射。表里只有根 —— 子运行结算进它父运行的记录，并在那个父运行的根关闭时抵达租户 —— 因此一棵树只被记账一次，而不是每次运行各记一次。对于本实例从未作为根开启过的运行，结算不记任何账，因为没有可以记账的租户，而猜一个会把账算到错误的账户上。

域版本从 0 走到 1，且不列出任何兼容版本，因此打着 0 戳记的记录被丢弃。一份光秃秃的预算说不出它自己已经被花掉了多少，而接纳它会把租户的整份额度恢复回去，而不是迁移它。

## Consequences

租户的授予额度现在为一个租户拨款。一次把授予额度花光并关闭的运行，会让下一次运行在预算这一步被拒；而一次仅仅开启着的运行，会把它的预留从该租户下一次运行所针对的额度里扣住。

结算是租户持久额度移动的地方，因此 `close` 与 `sweep` 是异步的。清扫由本服务自己的时间间隔驱动，而一次被拒绝的写入会被记录日志，而不是任其变成未处理的 rejection：它未能记账的那些占用已经被释放了，而下一次清扫无论如何都会跑。

那也正是剩下的缺口，而且它是明确的。结算写在它的占用已经在内存里被释放之后，因此两者之间的一次崩溃会丢掉那棵树的花费，一次失败的写入同样如此。要把损失压到零，需要持久的运行记录，那是下一块，本备注不声称做到了它。

对既有调用方有两处行为变化。`RunScheduler.close` 与 `RunScheduler.sweep` 返回 promise。以及默认的 `share` —— 准入所回答的整份额度 —— 现在意味着一个租户同时只能开启一个根运行；想要并发的树的部署传入一个显式的份额，组合测试正是这么做的。

## Alternatives considered

**在结算时递减存下来的预算。** 一个字段，不新增包。它在第一次运行之后就丢掉了授予额度，于是产不出任何配额报告，也让周期中途修改授予额度变得没有定义。

**在预留时向租户记账，在结算时退回剩余。** 那是账本的模型，并且在崩溃时向安全的方向失败。它也让消耗不再单调，而一次因崩溃丢失的退款会永久地悄悄吃掉租户的配额。在运行开启期间扣住它的预留，能达到同样的界限，而不需要一次可能朝错误方向丢失的写入。

**每次 `charge` 都折进租户。** 那会让消耗保持当前而不是滞后一棵树，但它会重复计数：那次运行的预留已经被从租户的剩余里扣住了，因此在它开启期间它的花费会被减去两遍。

**把这条记录放进 `dsh-run-budget`。** 那个包是一棵委派树的算术，而租户在其中不是一次运行。把租户记录分开，让账本保持为一个不知道谁拥有它的值。
