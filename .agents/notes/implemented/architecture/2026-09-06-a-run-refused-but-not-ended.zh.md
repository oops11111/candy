# Agent Note: 被拒绝却没有被结束的运行

Status: implemented

[English](2026-09-06-a-run-refused-but-not-ended.md) | 中文

## Problem

吊销一个提供方账户,已经能阻止一次存活的运行继续花钱:它发起的每一次调用都会在触及提供方之前被以 `CREDENTIAL_REVOKED` 拒绝。

但它并没有阻止这次运行本身。一次探测先给一次存活的运行记了四十个 token,再吊销它的账户,然后在远早于租约到期时清扫:

`{"settled":0,"stillOpen":true,"consumed":0}`

这次运行在租约剩下的时间里——数分钟——一直开着,占着出资方的额度,而它已经花掉的四十个 token 在这整段时间里都没有被记账。拒绝它所能发起的每一次调用,却又把它留在原地,得到的是一次只为了被拒绝而存在的运行。

这件事此前被记录为"需要吊销以事件形式抵达运行时"。那是个错误的框定:运行时本来就在轮询。

## Decision

由清扫来结束它。一次其账户已无法为它授权的运行,会在那里与那些租约已耗尽的运行一起被结算。

清扫本来就是这个运行时结束那些它认为该结束的运行的地方,而且它按自己的间隔运行,因此不需要任何东西抵达它——这种关闭是最终一致的而非即时的,其上界是 `sweepMs` 而不是租约。

判断依据与 `meterRequest` 所做的相同:账户记录缺失、被吊销,或被删除。共用同一个判断正是要点——一次每个调用都被拒绝的运行,不应该同时又是一次赖着不走的运行。

判断只基于正面证据。一次存储无法为其作答的运行会被留给它的租约,因为基于一次什么都没返回的读取去结束运行,比晚一点结束它是更大的错误。

## Consequences

一个被吊销的账户,现在在一次清扫之内而不是一个租约之内释放其运行的占用,而它们的租户会在那一刻、而不是数分钟之后,按这些运行实际花掉的量被记账。

反向对照恰好让那个吊销账户的测试失败,而让另外两个钉住"什么不该变"的测试继续通过:一个账户可用且租约未到期的运行会被放过,一个存储无法为其作答的运行也会被放过。

终止那些运行留下的提供方进程仍然不在这里。结算一次运行了结的是它的账目;而那个进程是由本包并不持有的调用方启动的,要触及它,需要一个能把清理动作挂到运行生命周期上的位置,而那又需要一个会去登记清理动作的生产者。

## Alternatives considered

**把吊销做成事件送达。** 那是即时而非最终一致的,而且需要一条把吊销从执行者那里带过来的缝隙——包括从另一个进程带过来,而控制平面的 API 正是会在那里执行吊销。清扫不需要这些,并且关掉了这道缺口的绝大部分。

**吊销时只终止、不结算。** 那能更早停下进程,却让账目继续悬着,于是租户无论如何还是要等到租约才被记账。释放占用的是结算。

**改为在记账时检查。** 一次已经停止发起调用的运行,恰恰就是那个会赖着不走的,因此这项检查必须跑在时钟上,而不是跑在运行自身的活动上。
