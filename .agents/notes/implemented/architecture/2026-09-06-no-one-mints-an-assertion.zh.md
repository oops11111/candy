# Agent Note:没有任何人在铸造断言

状态:已实现

[English](2026-09-06-no-one-mints-an-assertion.md) | 中文

## 问题

一个被就地(in-process)委派出去的子代理会得到一个全新的 `SessionId` 和一个全新的 Agent,它的模型调用携带的是那个新会话 id,而不是它父会话的。在一个使用 `dsh-claude-cli-route` 的 Candy 部署下,`RunScheduler.runIdentityFor` 为那个会话解析不出任何运行,路由会以 `RUN_NOT_OPEN` 直接拒绝这次调用——一个被委派的子代理根本无法调用模型,而不只是不被计费。

想通过给子代理铸造它自己的执行断言来修复这个问题,结果撞上了一个改变了整个修复方向的事实:`mintExecutionAssertion` 在整个仓库里只有唯一一处调用点,就在声明它的那个包自己内部——其他所有引用都在测试代码里,手工构造一个 token。这个代码库的生产路径里,从来没有任何东西真正铸造过一个断言。这次会话所构建的整套准入、账本、计量与凭据流水线,全部只由手工构造签名 token 的测试端到端地跑过;没有任何真实入口——一个经过认证的 HTTP 请求、一次设备配对后的会话启动——会产生一个断言。计划笔记自己提议里的架构图指名了这个权威(`AUTH`、`DEVICE`、`GATEWAY` 这几个方框,汇入一个"为每次运行交换一个短生命周期、绑定受众的执行断言"的控制平面),但交付表里没有任何一项任务在构建它,R4("Harness Web 与账户配置")和 R5("Windows Harness Host 的租户绑定")也都没有覆盖铸造断言这件事——R4 是给一个已经登录的用户配置 provider 账户的 UI,R5 是之后一步、Windows 专属的主机注册步骤。

一个子代理的断言需要 `workspaceGrantId`、`deviceId` 与 `conversationId`——而 `DurableRunRecord` 一个都没有保留,因为在此之前,没有任何东西在一次运行开启之后还需要它们。

## 决策

把范围收窄,不去做"把完整的认证与设备配对网关建出来"这件事——那是一项安全攸关、跨多个包的工作,本笔记不去尝试。这里交付的是一个真实的生产调用方今天就需要的那一小块:**一个被委派的子代理不需要任何新的认证,因为它没有主张任何新的身份**——它的身份恰好就是它父运行的身份,早已被验证过一次。铸造它的断言,是对一份已经持有的授权的重新陈述,而不是授予一份新的授权,因此它不需要先有一个外部的签发权威才能存在。

`DurableRunRecord` 得到了 `deviceId`、`workspaceGrantId` 与 `conversationId`,通过 `RunScheduler.admitAndOpen` 对 `openRun` 的调用,从已准入的 claims 里接了进来。`RunScheduler.startChildRun(parentSessionId, childSessionId, share, now?)` 通过每一个其他身份解析方法早已共用的那个同一个 `findSessionRun`,解析出父会话开启中的运行,复制它的租户、账户、provider、设备、workspace 授权与对话,铸造一份指名子会话、并把父运行当作 `parentRunId` 的全新断言,再把它推过与调用方自带 token 完全相同的那个 `start()`——复用 `dsh-run-budget` 早已为任何指名了 `parentRunId` 的断言强制执行的、父级子集式的预算与并发核算,原封不动。`share` 是必填的,没有默认值:一个被委派的子代理该拿到父运行剩余预算的多少,是一个策略选择,本服务没有依据去猜测。

铸造出来的 token 从不被传输或持久化;它存在的唯一目的,就是单次、同步地推动 `start()` 既有的准入路径——因此一次铸造出来的子运行,会像一个根运行一样被资助、记账、审计,不需要维护第二条与第一条保持同步的代码路径。

这只是 RunScheduler 这一侧的能力,独立构建、独立测试,与 `runIdentityFor` 和 `disposableSpawn` 在被 `dsh-claude-cli-route` 消费之前先被单独建好完全同一个节奏。把某个真实的子代理驱动器接到它上面,刻意不属于这次改动:`dsh-subagent` 是一个通用的 Harness 包,不携带任何 Candy 概念,要给它一个,需要的是与 `dsh-agent-presets` 的 `guard()` 给了 preset 名册那种同样的、不携带 Candy 概念的扩展点——这是一个独立的、后续的设计。

## 后果

一个 Candy 运行时现在可以为一个自己并未从外部 token 准入过的会话,开出一次真实的、记账的、有预算的、被审计的子运行——这是 `mintExecutionAssertion` 的第一个生产(非测试)调用点。`run-scheduler` 测试套件里新增的七个测试,针对一个真实的存储与账本证明了这一点:一次子运行以一个指名其父运行的全新 `RunId` 开启;它的会话立刻能通过 `runIdentityFor`/`tenantOf` 解析出来,而此前那里只会以 `no-open-run` 拒绝;父运行的剩余预算恰好被减去所请求的那份份额;一个解析不出来的父会话,会以 `runIdentityFor` 早已使用的同一种歧义被拒绝;子运行自己的准入拒绝(一份超支的份额)原样透传出来;而以这种方式开出的两个子运行彼此独立地计量——这证明了为什么要铸造一次真正独立的子运行,而不是把会话别名挂到父运行上:`oneCallAtATime` 那条按运行划分的调用队列,原本会把每一次并行的委派都强行挤到同一条队列上。

通用的断言签发权威(真实的用户认证、设备配对、workspace 授权签发)仍未建成。本笔记的修复不需要它,也不应被解读为已经把它建好了——一个本身还不是从某次开启中运行委派而来的会话,在生产环境里依然没有办法拿到它自己的第一份断言。

## 考虑过的替代方案

**把子代理的会话别名挂到父运行上,而不是铸造一次独立的子运行。** 已拒绝:`RunScheduler.meterRequest`/`meter` 按 `RunId` 对调用做串行化(`oneCallAtATime`),因此两个共享同一个运行 id 的子代理,无论其工作本身有多独立,调用都会被强行挤到同一条队列上——恰好悄无声息地串行化了 `dsh-tools` 自己的并行工具调用池本就是为了支持的那种并行子代理委派场景。给每个子代理一个独立的 `RunId`、复用早已建好的父级子集预算与并发机制,是唯一不会在这一点上倒退的选项。

**现在就把完整的断言签发权威(OAuth、设备配对、网关)建出来,因为这正是计划的架构图所要求的。** 拒绝将其纳入本笔记的范围:那是一项独立的、安全攸关的、跨多个包的设计,用户自己的表述已经把它与这个更窄、已经有充分理由的子代理场景分开了——在这里尝试它,就意味着要去猜测这个仓库里从未设计过的 OAuth 流程与设备配对语义。

**让调用方(未来某个 `dsh-subagent` 接线)直接提供子代理完整的 claims,让 `RunScheduler` 保持一个纯粹的验证者。** 已拒绝:要在 `RunScheduler` 之外重建一个父运行的账户、provider、设备、workspace 授权与对话,就意味着要把这个服务本不对外发布的运行内部细节暴露出去,而铸造任何 token 所需要的那个断言密钥早已是本服务私有的——要求一个外部调用方持有或重新推导它,会让两个组件各自都需要独立读取同一份密钥,这与 `dsh-claude-cli-route` 早先为凭据解析拒绝过的理由完全一样。
