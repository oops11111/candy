# Agent Note: 超出用途寿命的配对码

Status: implemented

[English](2026-09-13-a-code-that-outlived-its-use.md) | 中文

## 问题

配对码已经能保证单次使用并正确过期，但其持久记录永远不会离开 SQLite。租户可以不断签发配对码，使已消费和已过期元数据无限增长。用定时器删除会增加另一套进程生命周期，而全局清扫会让一个租户的请求影响另一租户的记录。

## 决策

增加按租户工作的 `sweepPairingCodes` 注册表操作和 `deletePairingCode` 存储端口。配对码在被消费时进入终态；若从未消费，则在过期时进入终态。配置的保留窗口结束后，该操作只删除由该租户列表返回的终态记录。尚可使用的记录绝不会被选中。

设备 API 在返回设备列表之前及签发另一配对码之前执行清扫。保留窗口默认七天，可配置为零至一年。这是按需清理：它需要租户活动，并且特意不引入定时器、后台工作进程或另一套传输。

## 考虑过的替代方案

- 由一个请求清扫所有租户。拒绝，因为租户操作不得修改其他租户的状态，而且存储在这里没有提供管理员级全局维护契约。
- 在兑换或过期后立即删除记录。拒绝，因为设置页使用终态元数据说明邀请是已使用还是仅仅过期。
- 在同一改动里通过先读数量、再写记录来增加设备／配对码上限。拒绝，因为两个 Candy 进程可能同时看到尚有余量并突破上限。精确上限需要原子的租户级预留账本，或覆盖签发与配额的存储事务。

## 后果

活跃租户只保留一个有界时间窗口内的终态配对元数据，其他租户的记录和尚可使用的邀请不受影响。不活跃租户的旧记录会保留到其下次列出或签发操作，因此要求按绝对时间删除的部署仍需外部维护触发器。精确的多进程设备及未用配对码上限仍是独立的后续安全工作。
