# Agent Note: Candy 运行时池分区

Status: implemented

[English](2026-09-02-candy-runtime-pool-partitioning.md) | 中文

## Problem

[Candy 运行时边界](../../../../docs/candy-runtime-boundaries.zh.md) 允许 worker 共享不可变 CLI 二进制文件与包缓存,并禁止跨 `userId + provider + accountId` 共享已认证的主目录、可写的提供方配置、环境覆盖、进程树、会话存储、私有缓存或工作区挂载。此前没有任何地方表达这个键,因此之后每个包都会各自推导"这两次运行可否共享这个目录"的答案,而第一个把租户 id 写进路径的包就会打开一个漏洞:租户与账户 id 是本仓库不加约束的不透明字符串,由它们构造的路径可能用 `../` 越出基准目录、超出平台路径长度上限,或者——在大小写不敏感的文件系统上——把两个仅大小写不同的租户折叠到同一个目录中。

## Decision

`@deepseek-ai/dsh-runtime-pool`(`packages/control-plane/runtime-pool`)拥有这个键与这个目录。`runtimePoolKey` 把身份三元组摘要为 64 个小写十六进制字符;`runtimePoolRoot` 把一个池直接放在绝对基准目录之下。摘要的输入带有长度前缀,因此 `('ab', 'c')` 与 `('a', 'bc')` 不会因移动字段边界而碰撞;而十六进制不具备使原始 id 作为路径段不安全的遍历、长度或大小写折叠性质。

`RuntimePoolKey` 没有自由形式的构造函数。持有它的唯一途径是签发它的 `runtimePoolKey`,以及在重新接纳存储键之前先检查语法的 `parseRuntimePoolKey`。因此约束是类型的性质,而不是每个调用点都要重复的检查:`runtimePoolRoot` 不可能收到一个能越出基准目录的键。与 `dsh-control-plane` 中的不透明 id 不同,在这里做校验是有依据而非发明的,因为该语法正是本包自己的摘要。

`ProviderKind` 是封闭集合 `deepseek-api | claude-cli | codex-cli`。这推翻了 `dsh-control-plane` README 中记录的一条限制——它曾表示发明一种提供方表示形式会抢先替代 R2 的适配器设计。那条理由过于宽泛:交付计划恰好点名了这三个提供方,因此这个*类别*可从已接受的文档推导得出,并且它与适配器设计是可分离的——流式传输、工具调用、取消与错误映射仍然完全属于 R2。该 README 现在改为指向本处。

本包不触碰文件系统。它只推导路径;创建、填充、设置权限与删除这些路径,属于管理池的运行时。

## Alternatives considered

**把三元组写进路径,并对 id 做净化。** 这是最直观的做法,它需要一个同时具备单射性且在每个目标平台上都文件系统安全的净化器。对 `/` 与 `..` 做百分号编码仍然留下大小写折叠与路径长度上限问题,而任何转义方案都必须被证明对任意 Unicode 都不产生碰撞。摘要无需就转义方案展开争论即可同时获得这三项性质。

**在摘要旁保留一个可读的目录名**(`<digest>-user-alice`)。这对用 `ls` 查看的运维人员更友好,但予以拒绝,因为可读的那一半会重新引入摘要本要避免的遍历、长度与大小写问题。需要把目录映射回租户的运维人员,应当读取目录内的一条记录,而这可以由池的拥有者写入。

**把这个键放进 `dsh-control-plane`,与 id 并列。** 予以拒绝:该包对外宣称的是无外部依赖的身份词汇,而这个键需要 `node:crypto` 与一个 `ProviderKind`,这会让一个包拥有两个变更理由。

**同时推导子目录布局**(`home/`、`cache/`、`sessions/`)。这很有诱惑力,因为边界页面列举了必须分区的内容,但每一个名称都会在消费者需要之前就被发明出来。本包只命名一个根目录,其内部结构留给拥有者。

**在此处强制配额、进程归属与清理。** 这些是同一条交付计划条目的其余部分,它们需要 R1 尚未构建的调度器、会话存储与文件系统归属。提供它们将共同据以分区的那个键,才是能够独立正确的部分。

## Consequences

之后每个包现在对"一个池可以共享什么、它的私有状态存放在哪里"都共享同一个答案,而且即便两个租户的 id 仅大小写不同或携带路径语法,它们也无法进入同一个目录。单元覆盖固定了稳定性、十六进制语法、按三个字段各自的分离、大小写与字段边界碰撞、携带 `../` 的 id 归约为纯十六进制、存储键的语法,以及根目录始终位于基准目录之下。

这完成了 R1 的四条条目,但它所交付的分区仅限于推导:不创建任何目录、不强制任何配额、不放置任何进程,也从不清理任何池。这些仍属于管理池的运行时,并已记录在包 README 中,以免这一缺口被误认为强制执行。`ProviderKind` 集合现在是计划层面的事实而非配置值——新增第四个提供方是一次触及该联合类型的交付计划变更,这是刻意为之:悄悄新增一个,会让池键具有任何已接受文档都未命名的含义。
