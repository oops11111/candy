# Agent Note: 并发度像其他每一个维度一样，在整棵树上守恒

Status: implemented

[English](2026-09-04-concurrency-is-conserved-across-a-tree.md) | 中文

## Problem

[Candy 运行时边界](../../../../docs/candy-runtime-boundaries.zh.md)写道，子运行只能使用「其父运行本就拥有的账户、工作区、工具、token、时间、成本与并发权限」，而交付计划的运行时契约第 6 条重复了这一点。`reserveChild` 对其中最后一项并不成立。

它按每个子运行收父运行一个名额，而对该子运行可以转手让出的那些名额分文不收。于是三个维度在委派树上是守恒的 —— 整棵树无法超支其根运行的 token、毫秒或金钱 —— 而第四个维度只在一层之内守恒。拿已交付的代码实际跑一遍：一个被授予 `children: 4` 的根运行，可以催生四个各自被授予四个的子运行，它们的子运行再来一遍，在深度五时有 1364 个运行同时存活，而那份授予读起来只是「四」。没有任何一层为它下面那些付过费。

那是一份真实的资源，不是记账上的怪癖。每一个存活的运行都是一个提供方进程，带着一个主目录、一份环境和若干文件描述符，跑在一台与其他租户共享的运行时上，而被请求的子运行预算，是从模型所要求的一次委派那里可以够到的。

旧规则是被记录过的，而不是无意的：本包的 README 写过它，一个测试钉住了它，[委派笔记](2026-09-03-run-budget-delegation.zh.md)解释过它。当时的理由是并发度是一份会归还的容量、而不是一份被消耗掉的量，这一点是对的，但它并不蕴含子运行转手让出的那份授予应当免费。

## Decision

一个子运行让父运行付出的，是它自己占的那一个名额，加上它可以委派出去的每一个名额。因此 `children` 计的是一棵子树中任何位置可以同时存活的运行数，而不只是它第一层的数量，而根运行的授予界定整棵树。

`RunLedger` 用同样的方式推导父运行的剩余额度：为每一个开启中的子运行扣掉 `1 + child.reserved.children`，并在该子运行关闭时全部归还。两半各自被独立钉住：单独回退其中任何一半，都会让另一半没有覆盖到的某个测试失败。

`reserveChild` 里的特殊分支随这次改动一起消失了。改为扣 `request.children + 1`，并发度就走上了与另外三个维度相同的短缺检查，于是那条单独的「父运行到底还有没有名额」分支不复存在，第四个维度也不再是例外。

## Consequences

一份授予现在读起来是一个子树规模。一个想表达「四个子运行，每个还能再委派两个」的部署，要求的是十二，而不是四。这是这个数字含义上的一次真实改变，而这个含义才让部署能够推理出：一次运行最多要对多少个提供方进程负责。

花费的守恒未受影响：它本来就成立，现在同样成立。

## Alternatives considered

**改为修订边界文档，写明并发度只按委派层级界定。** 那样可以保住代码和测试，而且它是一个自洽的立场 —— 深度由 `dsh-subagent` 封顶，而花费是守恒的，因此一棵宽的树无法超支其根运行。它被否决，是因为那个数字依然界定不了部署真正在意的东西：耗尽一台共享运行时的是进程数，而一个读起来是四、却允许一千三百多个的上限，比没有上限更糟，因为它看上去像一个上限。

**改为在调度器里按租户限制并发进程总数。** 按租户的配额是另一种同样有用的控制，但它并不能让子运行的授予成为其父运行的子集，而且它把这处矛盾推给了本次发布尚未构建的组件。

**只拿子运行的授予与父运行比对，而不做扣减。** 这与[委派笔记](2026-09-03-run-budget-delegation.zh.md)针对 token 所否决的是同一种不成立：每一次检查都独立地看到父运行的全部额度，于是父运行可以批准任意多个各自装得下的子运行。
