# Agent Note：一份只会倒数的租约

状态：已实现

[English](2026-09-06-a-lease-that-only-counted-down.md) | 中文

## 问题

`RunLedger.renew` 陈述了租约赖以建立的那份契约：「一次仍在工作的运行会通过把自己的租约往后推来这么说；一次不再这么说的运行会被 `expire` 结算。没有别的东西能移动租约，因此一份不再前进的租约,恰好就是一次没有任何东西在驱动的运行。」

从来没有任何东西调用过它。在整个代码库里，`renew` 恰好只有两处调用点，且都在它自己的单元测试里，因此没有任何一份租约前进过——而那句话的后半句被反转了：一份不再前进的租约就是每一次运行，无论它是否在工作。`RunScheduler.sweep` 会结算每一次租约已过的运行，因此每一次运行都在开启 `leaseMs`（默认 300 000 毫秒）之后结束，无论它的 agent 当时工作得多努力。它的额度被归还、它的花费被并入出资方，它的会话被加进 `ended` 记忆——此后 `meterRequest` 会以 `RUN_NOT_OPEN` 和「the run driving it has ended」这条消息拒绝之后的每一次调用。一个五分钟的会话被切断，并且一直保持被切断。

`ended` 记忆正是为这种情形而建，并让**记账**保持了诚实——README 也把这一点说得很直白：「租约可能在一个仍在工作的 agent 之下到期……若不记住这次结束，它的下一次调用看起来就像一次本运行时从未有过的调用，从而免费跑掉」。它堵上了一个被切断的 agent 免费运行的漏洞，同时把这个 agent 留在被切断的状态里。

这是这个子系统中同一种形状的第三个实例，前两个是[没人上过发条的那个时钟](2026-09-04-the-clock-nobody-wound.zh.md)（`expire` 是一次没有任何东西发起的调用）与[一份只做笔记的预算](2026-09-05-a-budget-that-only-took-notes.zh.md)（`charge` 报告的东西没有任何东西在读）：一个建得完整的机制，而驱动它的那一半从未被接上。

## 决策

当本运行时仍然持有该运行所属的会话时，清扫会续期，而不是结算。

租约回答的是一个问题——持有这次运行的运行时是否已经消失——而一个仍然持有该会话的运行时，就是在直接回答这个问题，而不是等着被问。`RunScheduler.driven(runId)` 读取该运行的持久记录以取得它的会话 id，并询问会话存储该会话是否在这里存活；`RunScheduler.renew(runId, now)` 则通过新增的 `ControlPlaneStore.renewRun`，在账本里和持久记录上把租约往后推。两者都跑在调度器自己的那条链上，与对运行记录的每一次写入一样。

会话存储是通过 `ctx.get('sessions')` 读取的，即那个有文档记录的机会式模式：一个没有组装会话存储的组合会把每一次运行都留给它的租约，与此前完全一样。持久记录之所以要跟着账本一起动，是因为被存储的租约正是一个later 读者——重启之后的本运行时、一位运维者、或另一个共享同一 audience 的运行时——用来分辨一次被驱动的运行与一次被遗弃的运行的依据；一次只保存在内存里的续期，会给那位读者留下一条在运行仍在工作时看起来已被遗弃的记录。

顺序把这两个问题分开判定。一个被吊销的账户依然会结束它的运行，无论其会话多么存活：`spent` 会被先检查，因此这条规则判定的是遗弃，而绝不是授权。存活也不等于活动——一个在两轮之间停驻的会话，等待一个工具、一次审批或者一个人，依然归本运行时出资，只有在会话本身消失时才会失去它的运行。

计量曾是另一个候选的续期信号，而且是更窄的那个：一次正在拉取被计量流的运行当然在工作，但一次在两次模型调用之间跑着十分钟测试的运行同样在工作，而只在模型调用时续期仍然会把它切断。会话存活性用一条规则、在一个地方，同时覆盖了模型时间、工具时间与空闲时间。

## 后果

一次运行不再受挂钟寿命的限定。一个工作一小时的 agent 会保住它一开始拿到的那次运行；一个停驻整夜的会话同样保住它，并在会话消失时释放它。租约现在就是它自己的文档所说的那个东西：崩溃兜底，恰好在本运行时无法为该会话作答时才承重——在一次重启之后（那里被恢复的根本来就会在 `Service.init` 时被关闭），或者在没有组装会话存储的地方。

代价是：一个空闲但存活的会话会在其整个存活期间占着它租户的额度与一个并发名额，而此前五分钟后就会被释放。这是对一个开着的会话的诚实读法，而先前的行为之所以看起来更便宜，只是因为它在释放那些其实仍在被使用的运行的额度。

三个真实组合测试针对一个真实的调度器、一个真实的以 SQLite 为后盾的存储和一个真实的会话存储钉住了这条规则：一次其会话存活的运行会挺过一份已过期的租约，并且它的租约在账本与存储两处都被往后推，其下一次调用仍被正常计量；一次其会话已不再由本运行时驱动的运行依然会被结算，而此时会话存储已被组装并在为另一个会话作答；以及一个被吊销的账户在会话存活的情况下依然会结算它的运行。变异检查确认了每一条：去掉存活性检查会让第一个失败，把「组装了任何存储」当作存活会让第二个失败，而让存活性压过吊销会让第三个失败。

## 考虑过的替代方案

**在观察到的工作上续期——每一次被计量的拉取、每一次 charge、每一次 `subprocess/launched`。** 作为主规则被拒绝：它是对「一次仍在工作的运行会这么说」最字面的读法，但它只覆盖这个调度器恰好观察得到的工作。一次没有子进程的长工具调用、一次等待用户审批，以及一个在两轮之间的可续接子会话，都是一次存活的运行在做调度器看不见的事，而每一种都仍会被切断。它还把续期散布到好几个调用点上，而会话存活性只需要一个。

**给租约一个大得多的默认值，机制本身不动。** 已拒绝：这是把悬崖挪走而不是移除它，并且要挑一个数字——它要么对一个长会话来说太短，要么长到无法及时释放一次被遗弃的运行。问题在于「被遗弃」从来没有被度量过，而不在于度量它时用错了常数。

**在一次运行的会话结束时立刻关闭它，并彻底去掉租约。** 很有吸引力——及时关闭严格优于把租约等完——但作为一次独立的改动，在这一批次里被拒绝：调度器今天不监听任何会话或 agent 生命周期事件，而无论如何租约都必须作为崩溃兜底存活下来，用于一个没有关闭任何东西就停止的运行时。加一个 `session/disposed` 监听器会在这条规则之上收紧释放延迟，而不是取代它。
