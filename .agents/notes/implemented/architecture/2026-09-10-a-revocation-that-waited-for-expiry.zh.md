# Agent Note: 等到过期才生效的撤销

Status: implemented

[English](2026-09-10-a-revocation-that-waited-for-expiry.md) | 中文

## 问题

租户可以撤销一台设备,而这台设备照常工作。

`dsh-device-registry` 写下了 `revokedAt`,设备 API 也回答租户绑定已被撤回,但运行路径上没有任何东西读取这条记录。`admitRun` 校验断言、检查世系、解析工作区授权、读取额度、消费 nonce、打开凭据,却在任何一步都没有解析断言所携带的 `deviceId`。于是持有撤销之前铸造的断言的主机,会一直启动运行,直到那份断言过期;而已经拿到新断言的主机则会无限期地继续启动。

工作区授权自身的设备检查让这件事看起来比实际更安全。`admitWorkspaceGrant` 会拒绝 `device-mismatch`,但比较的两侧都未经验证:授权的 `deviceId` 来自一条记录,而运行的 `deviceId` 来自一项没有任何东西解析过的主张。一台从未配对过的设备,或者一台属于早已把机器丢弃的租户的设备,只要授权指名的是同一个字符串,就能通过。

## 决定

准入在解析为设备书写的授权之前,先解析设备本身。

`RunAdmissionPolicy` 新增 `findDevice`,形状与 `findWorkspaceGrant` 相同,而 `admitRun` 以已校验声明所指名的租户与设备调用 `admitDevice`。解析不到任何东西的 id、已被撤销的绑定,以及属于另一个租户的设备,都会拒绝该运行,标记为 `stage: 'device'`,并像 `assertion` 之后的每一个阶段一样携带声明。

**设备在前。**授权的根目录属于某台设备,因此拿授权去核对一项未解析的设备主张,是把一条记录与一个字符串相比。先解析设备,才使授权自身的 `device-mismatch` 成为两条记录之间的比较。

**它位于 nonce 之前**,理由与授权检查相同:重新配对的主机出示的是同一份仍然有效的断言,而烧掉它的一次性令牌,会把运维可以修复的一次拒绝变成一次往返控制面的请求。

`RunScheduler` 用 `ControlPlaneStore.findDevice` 回答这个端口。整个接线就是这些:存储早已持有记录,调度器早已组装策略,缺的只是一行以及它所喂养的那道检查。

## 考虑过的替代方案

**在检查工作区授权的地方、也就是 `admitWorkspaceGrant` 内部检查设备。**否决。一次完全没有文件系统权限的运行仍然以某台设备的身份行事,把两者合并会让不签发授权的部署也无法检查设备。它们是两条记录,有各自的撤销。

**缩短断言有效期,让撤销更快生效。**作为答案否决。它以更多面向控制面的流量换取一个更短的延迟,而且窗口依然存在;记录本来就有,读它就把窗口完全去掉了。

**让设备 API 在撤销时删除该设备的运行。**否决:它有竞态。在撤销与清扫之间被准入的运行仍然是一次运行,而准入处的检查没有这样的间隙。

**让 `admitDevice` 保持无人调用,改在传输层核对令牌。**否决,因为目前没有任何传输携带设备令牌,也因为授权一次运行的正是断言。在运行被准入的地方检查设备,就是在做出决定的地方检查它。

## 结果

撤销现在会拦住下一次运行。这正是设备记录被建出来所要的行为,并且针对真实启动的调度器被钉住:一次运行启动,租户撤销主机,下一次运行以同样的断言密钥与存储被拒绝为 `device/revoked`。

出现了两种此前不存在的拒绝。指名了存储从未配对过的设备的运行会被拒绝而不是被准入;以另一个租户的设备身份行事的运行,会在设备处被拒绝,而不是在授权处被顺带拒绝。

**每个部署现在都必须先配对设备,任何运行才能开始。**不存在隐式设备,而一个不持有设备的存储什么也不准入。这与工作区授权引入的规则相同,也是本组中五处测试夹具发生变化的原因:每一处都提供了一份指名着它从未创建过的设备的授权。其中两处还自相矛盾——第二个租户的授权指名了第一个租户的设备——而在没有任何一步解析二者时,这是检测不出来的。

它没有做的是触及正在运行的操作。已经被准入的运行会保留其凭据与额度直到结算;检查在准入处,而在撤销时取消进行中的工作是另一个决定,需要另一套机制。

## 验证

`packages/control-plane/run-admission/tests/run-admission.spec.ts` 以表格覆盖三种拒绝,并通过把同一个令牌再次交给一个会准入它的策略,钉住被拒绝的设备不会消耗 nonce。`packages/control-plane/run-scheduler/tests/loader-composition.spec.ts` 通过 Loader 启动真实的存储与调度器,端到端地驱动核心场景:一次运行启动,租户撤销设备,下一次运行被拒绝;未配对的设备与另一个租户的设备在那里也会被拒绝。

三项变异对照证明这些用例确实在做判断:去掉这道检查、把它移到 nonce 被消费之后,以及按记录所指名的任何租户准入设备,各自都会让至少两个用例失败,随后实现被还原。
