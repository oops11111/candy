# Agent Note: 没人取过的备份

Status: implemented

[English](2026-09-11-a-backup-nobody-had-taken.md) | 中文

## 问题

Debian 部署页告诉运维如何备份控制面，而从来没有人运行过它。

它所说的内容有两处不对。它让运维执行 `sudo -u candy sqlite3 ... ".backup ..."`，而安装步骤里没有任何一步安装 `sqlite3` 这个包——于是逐字照着该页操作的运维，会在最需要备份的那一刻撞上 `command not found`。而它为这条建议给出的理由是「写入过程中拿到的副本是一个能打开但缺行的文件」，这低估了实际发生的事：SQLite 后端默认运行在 WAL 模式下，因此提交会先留在 `-wal` 文件里，直到一次 checkpoint 把它们折入；在一个还很年轻的数据库上，单独 `cp` 数据库会得到一个里面完全没有表的文件。

恢复那一半同样未经演练。该页让运维把文件放回去并启动服务，而从来没有任何东西在恢复出来的数据库上启动过运行时，去看看它是否作答。

R6 要求一次回滚演练。一份无人执行过的既有流程，正是演练之所以存在要抓的东西。

## 决定

交付一个部署本身就有东西可运行的备份工具，并以测试的形式执行这次演练。

`packages/bundle/candy-app/deploy/candy-backup.mjs` 通过 `node:sqlite` 的 `backup()` 完成在线备份。服务本身是一个 Node 进程，而存储后端就是 `node:sqlite`，因此复制由拥有该数据库的同一个库、同一个运行时完成，而 `sqlite3` 这个包也不再是一项未被列出的前置条件。除了逐页复制之外，还有两项属性是刻意的：目标文件先在其所在目录以临时名写入，只有复制完成之后才重命名，因此被中断的备份不会留下一个看起来完整的文件；而源文件以只读方式打开，因此输错路径会报错，而不会新建一个空数据库去覆盖一个真实的。

`packages/bundle/candy-app/tests/rollback-drill.spec.ts` 执行这次演练。它在一个真实 SQLite 文件上启动存储，启动不会停下的写入者——每一次都是经由真实存储的排队读-改-写——在它们运行期间取备份，然后销毁一切、把备份拷到位、在恢复结果上再次启动。恢复需要回答的不是文件能打开：而是账户全都在那里，并且一份密封凭据仍能在同一个密钥环下打开——这正是「可读」与「可用」之间的区别。

WAL 这项发现是被钉住的，而不是被叙述的。有一个用例写入二十四个账户、单独复制数据库文件、在同一时刻取一份在线备份，并断言在线副本持有全部二十四个而文件副本更少。在这么年轻的数据库上文件副本持有零个，而断言写成不等式而不是零，因为恰好落下的一次 checkpoint 会让「零」变成错的，却不会让这条建议变成错的。

两份文档页现在都点名该工具、说明它为什么不需要额外的东西，并直截了当地说出复制文件会丢掉什么。

## 考虑过的替代方案

**把 `sqlite3` 加进安装步骤。**否决。它引入一个版本与服务写入所用版本无关的包，而由一个不同于写入者的 SQLite 取的备份，是事故期间需要额外推敲的东西。运行时本来就带着这项能力。

**保留 `cp`，并在文档里写明先做 checkpoint。**否决：它把一条命令变成一个带窗口的序列，而那个窗口恰好是运维承压的时刻。`PRAGMA wal_checkpoint` 也必须由某个持有连接的东西对活动数据库执行，而这本来就是在线备份的工作。

**断言写入过程中的 `cp` 必然损坏。**作为不稳定的断言而否决。竞争中的复制是否落成损坏取决于时序。而 WAL 这项事实是确定的——未 checkpoint 的提交根本不在文件里——因此用例钉住的是它。

**把工具写成 TypeScript，放在其他仓库脚本旁边。**否决，因为运维的机器可能是一份解包后的构建产物，而不是装好 `tsx` 的检出。由服务自己的 Node 运行的 `.mjs` 不需要构建步骤、也不需要开发依赖，而这正是 `subprocess-local` 的 spawn 辅助脚本已经确立的先例。

**在运行中的服务内部按定时取备份。**本片否决。备份存到哪里、保留多久、何时运行，都是部署的决定而不是运行时的决定；而一个自己写备份的服务需要一个该页尚未规定的存放位置。

## 结果

运维可以用安装本来就放到机器上的东西取一份一致的备份，而恢复路径是被执行过的，而不是被写下来的。该演练随 bundle 套件一起在 CI 中运行，因此破坏恢复的改动——存储拒绝打开的 schema 版本提升、恢复之后不再作答的后端——会在那里失败，而不是在一次回滚期间。

该页自己的说法现在一处变弱、一处变强：它不再说文件副本只是缺行，也不再暗示 `sqlite3` 是可用的。

它没有做的是覆盖 R6 那条要点的其余部分。没有 feature flag、没有 provider canary、没有资源监控、也没有安全告警；该演练证明的是回滚的数据库那一半，而对回滚 `/opt/candy` 目录树什么也没说——后者该页仍然靠保留上一份来处理。该页上已有的凭据密钥注意事项，仍然是恢复绝不能盲目回滚的那一件事，而没有任何东西强制它。

## 验证

`packages/bundle/candy-app/tests/rollback-drill.spec.ts` 通过：在持续写入期间取的备份持有所写内容的一个时间点子集；对它的一次恢复能够启动并以它所捕获的每一个账户作答，且凭据仍能打开；WAL 下的文件副本严格少于在旁边取的在线备份；不存在的源是一个不写出目标的错误；而不带参数会报告用法。

两项变异对照证明该工具自身的属性是承重的：把在线备份换成 `copyFileSync` 会让两个用例失败，而把源以可写而非只读方式打开会让「源不存在」那个用例失败，随后实现被还原。
