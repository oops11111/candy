# Agent Note: 脱敏够不到的那条流

Status: implemented

[English](2026-09-05-the-stream-redaction-could-not-reach.md) | 中文

## Problem

`dsh-llm` 的 `redactApiKey` 之所以存在,是因为提供方的诊断会引述失败的那个请求,而那个请求携带着凭据——于是一个指名被拒密钥的错误正文"会把它放到适配器的失败所去的任何地方:会话日志、运维人员的控制台、模型的转录"。Claude CLI 适配器对它产出的每个块都应用了这个函数。

而它是用 `stderr: 'inherit'` 启动 CLI 的。那会把父进程自己的描述符交给子进程,于是适配器一个字节也看不到那条流,也就无法改写它。一次探测通过真实的 subprocess 服务运行了一个 CLI,注入了租户密钥,并让它把密钥引述回来;vitest 进程自己的 stderr 上出现了:

`claude: request rejected: invalid x-api-key: sk-ant-PROBESECRET-do-not-log`

同样的文本若从 stdout 到达,本会被脱敏。而完全没有任何缓解措施的那条流,恰恰是直通运维人员控制台的那条——也正是脱敏模块首先指名的那个地方。

## Decision

适配器改为在 `maxStderrBytes` 之下收集 stderr,而不是继承它,并且不配置溢出文件,因此一个租户的诊断留在该运行自己的内存里,而不是共享的临时目录里。收集模式在溢出时保留尾部,那正是诊断需要的,也与 stdout 上限相反:诊断以哪里失败了结尾,而协议流在任何位置都无法承受缺口。

尾部不会被扔掉。一次进程死掉却没有终止帧的运行,没有任何别的关于自己的记述,因此尾部会并入那次失败的消息——并经由每个块本就要经过的脱敏离开,而不是再复制一份脱敏。正常结束、被取消或触发 stdout 上限的运行已经说明了原因,其 stderr 会被丢弃。

## Consequences

凭据再也无法经由这个适配器所拥有的任何路径未脱敏地离开,而一次死掉的运行现在会说出 CLI 临走时说了什么,而不只是指出一个退出码。

两个反向对照,各自恰好让两个测试失败:恢复 `inherit` 会让单元套件与组合 Loader 中关于流处置方式的断言失败;传入空尾部会让诊断断言与脱敏断言失败。

在宿主自己的流上看着 CLI 警告的运维人员,对一次已完成的运行不再看得到它们。这被记录为一项限制而不是被解决:把它们送往日志器,需要一个真正会读取它的消费者。

## Alternatives considered

**用 pipe 拿到 stderr 并在适配器里脱敏。** 它同样能关闭这个泄漏,代价是第二个读取者、它自己的排空逻辑,以及第二个需要强制的界限。收集模式正是这条缝隙对"持有一条我稍后会读取的流的有界尾部"给出的答案,而它所喂给的失败文本本就已经被脱敏。

**保留 `inherit` 并信任 CLI。** 脱敏模块对 stdout 就拒绝了这套推理——密钥在失败的请求里,因此任何回显请求的组件都会回显密钥——而 CLI 的 stderr 比它的协议流受到的约束更少,而不是更多。

**把尾部给每一次失败。** 被取消的运行和触发 stdout 上限的运行都已经携带了精确的原因,再往上追加一条不相干的警告只会让消息更糟。只有那个死掉却没说为什么的进程,才没有别的可交代。
