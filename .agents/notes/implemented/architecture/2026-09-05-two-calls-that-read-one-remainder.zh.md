# Agent Note: 读到同一份剩余额度的两次调用

Status: implemented

[English](2026-09-05-two-calls-that-read-one-remainder.md) | 中文

## Problem

计量器在调用提供方之前读一次运行还能花什么,并在调用结束时记一次账。因此两次重叠的调用都会针对一份谁都还没被记过账的剩余额度起步。

一次探测给一个运行拨了恰好够跑一次假适配器调用的额度,然后同时发起两次:

`{"first":"finish/stop","second":"finish/stop","spent":84,"allowed":42}`

两次都完成了,而这次运行花掉了它被允许的两倍。这些维度界定的是运行,不是调用,因此它们只有在多次调用不观察到同一份剩余额度时才成立——与上一层租户剩余额度是同一种"先读后做"的形状,只是发生在此前那次修复没有触及的这一层。

这里的并发是合法的,而不是调用方的错误:`dsh-compaction-basic` 会把 agent 自己的会话打在它的摘要调用上,因此一个会话的多次调用不必一次只有一个。

## Decision

`RunScheduler.meter` 把一次运行的多次调用排成一列。每一次读到的剩余额度,都是它前面那一次已经被记过账之后的;而一次负担不起剩余额度的调用,会被那个本就会拒绝已耗尽运行的计量器拒绝。

这一列是按运行来的。两个租户永不彼此等待;而调用本就顺序发生的运行——agent 循环就是——也从不等待,因为轮到它下一次调用时这一列已经空了。

选择排队而不是拒绝第二次调用,正是为了让合法的并发调用方继续可用:与一个回合并行的压缩是被排序,而不是被拒绝。

半途放弃一条流的消费方同样会退出这一列,否则该运行之后的每一次调用都会等在一条没人排空的流上。队列中的位置在流被创建时就被占下,并且从那一刻起就可以被让出,因为消费方可能关闭一条它从未读过的流。

`meterRun` 现在如实声明它本就是的那个异步生成器,于是包装层无需先问它能否被关闭就能关闭它。

## Consequences

无论调用方如何调度它的调用,一次运行都不可能花掉超过它所持有的额度。

这依赖于调用会结束。它之所以排在挂钟时间界定（[什么都没说的提供方](2026-09-05-the-provider-that-said-nothing.zh.md)）之后落地,正是因为如此:在那之前,一个沉默的提供方会在它保持沉默的整段时间里占住它那次运行的队列,那是把一次超支换成了一次挂起。

反向对照——不排队直接计量——恰好让那个并发测试失败,而不影响其他任何测试。

## Alternatives considered

**拒绝第二次并发调用。** 更简单,而且它是点明这次重叠而不是把它藏起来。但它会破坏压缩,而那是一个真实的、有意重叠的调用方,于是等于把一个计费缺陷换成了一个功能缺陷。

**为每次调用预留一份剩余额度。** 一次调用的开销在它跑完之前是不知道的,因此这个份额只能是编出来的——而一个错误的份额要么拒绝负担得起的调用,要么放行负担不起的。

**排在调度器已有的那条链上。** 那条链为整个运行时的所有操作定序;把流放上去会让一个租户的长调用挡住其他每个租户的启动。这里要保住的界限属于一次运行,因此这一列也属于一次运行。
