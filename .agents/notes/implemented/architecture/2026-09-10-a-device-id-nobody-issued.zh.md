# Agent Note: 无人签发的设备 id

Status: implemented

[English](2026-09-10-a-device-id-nobody-issued.md) | 中文

## 问题

`DeviceId` 只是一个品牌化字符串,背后没有任何记录。每个消费方都指名它,却没有任何一方解析它:执行断言携带 `deviceId`,持久运行记录保存它,工作区授权标明其根目录是为哪台设备书写的并拒绝来自其他设备的运行——判定方式是把授权上的设备与断言中的设备相比较,而这是两个未经验证的声明彼此吻合。没有任何东西能说明该设备存在、属于谁,或是否仍在为其行事。

同一处空缺也让工作区授权自身的设备检查弱于它读起来的样子。`admitWorkspaceGrant` 会拒绝 `device-mismatch`,但它所信任的 id 来自断言,而该断言所指的租户是部署唯一验证过的东西。租户可以铸造声明任意设备字符串的运行,包括一台早已退役的主机,而下游的每一道检查都会认同这个声明。

也没有任何办法把一台主机接入部署。计划中的 R5 要求 Windows Harness Host 绑定到一个用户和一台设备;而 harness 唯一的身份是 `dsh-anonymous-user-id`,一个按安装生成、被刻意设计为*不*标识个人的 UUID,`host/` 则是本地 Web GUI 的那一半,没有"通过网络访问的机器"这一概念。既没有注册,也没有配对和撤销,因此绑定无从建立。

## 决定

设备是租户通过配对创建的持久记录,并在该记录的整个生命周期内属于该租户。

`dsh-device-registry` 持有它:设备所绑定的租户、运维给出的标签、主机所出示令牌的摘要、配对时刻,以及绑定被撤回的时刻。这里刻意不存在把设备迁移到另一租户的操作。一台应当服务于另一个人的主机就是另一台设备,用那个人自己的配对码配对、持有自己的令牌,而之后的每一道检查读取的是绑定而不是声明。

配对是唯一需要人参与的一步。租户在已认证的会话中签发一个短时效、一次性的配对码,把它带到主机上,主机用它一次性换取自己的身份。只有摘要是持久的——配对码的和令牌的——因此记录的副本既配不成对,也认证不了任何东西。

**认领先于设备写入。**两者之间的失败会烧掉配对码,而不是留下一个仍可使用的码,这是安全的方向:租户可以重新签发一个没能用上的码;而一个在半途失败后幸存的码,会让第二台主机在第一台已经应答过的邀请下完成配对。出于同样的理由,做决定的是认领而不是它上面的读取。两台主机读取同一个未兑换的配对码时都会发现它未兑换;读取的存在只为说明这是三种拒绝中的哪一种,而在读取成功之后失败的认领会被报告为已兑换。这种不可分割性是存储端口上一条明确的义务——`claimPairingCode` 必须在单一步骤中决定兑换与有效期——而不是领域层能用普通的读与写拼出来的东西。

已兑换的配对码保留其记录并标明它产生了哪台设备,于是运维能判断一台设备来自哪次配对,而第二次拒绝成为记录陈述的事实,而不是记录的缺失。被撤销的设备同样保留记录:绑定消失之后,断言和工作区授权仍会指名该 id,而删除记录会让一个被撤销的设备读起来像从未配对过。

`admitDevice` 是断言期的规则,与 `admitWorkspaceGrant` 形状相同,理由也相同——记录才是权威,断言只是指名它,因此在令牌铸造之后被撤销的设备,会在该令牌的下一次使用时被拒绝,而不是等到它过期。

传输保持原样。主机如何连到部署、如何维持连接、如何选择目录或执行命令,都是继承自 Harness 的行为,本包对此毫无增补。它所决定的是设备属于哪个租户,以及它是否仍然属于该租户。

## 考虑过的替代方案

**让主机用租户自己的凭据完成注册。**否决,因为送到主机上的凭据就是主机可能丢失的凭据。一个配对码值十五分钟内的一台设备;而租户的会话 Cookie 或服务商密钥值他们拥有的一切,把它带到一台机器上以使其成为设备,等于把它永久留在那里。

**保存设备令牌而不是它的摘要。**否决,理由与浏览器会话已经保存摘要的理由相同:持久记录会被备份、副本和运维读取,而其中的令牌对他们每一方都能作为该设备通过认证。令牌只返回一次,且无法从记录中还原。

**允许租户对已有设备重新配对。**否决,因为绑定正是之后每一道检查所读取的东西。在租户之间迁移设备,会让一秒钟前铸造的断言指向一台如今属于他人的设备,而关于该设备的每一条审计记录都会同时描述两台不同的机器。重新配对产生新的 id,这本来就是事实的样子。

**用一次读取再一次写入来标记配对码已兑换。**否决,因为两台主机读取同一个未兑换的配对码时都会发现它未兑换,于是都会完成配对。一次性认领因此成为存储端口上的义务,由介质保证其不可分割。

**删除已撤销的设备或用尽的配对码。**否决,因为绑定消失之后,断言和工作区授权仍会指名该 id。被删除的记录会在真相是 `revoked` 时回答 `not-found`,而被删除的配对码无法说明它产生了哪台设备。

## 验证

`packages/control-plane/device-registry/tests/device-registry.spec.ts` 覆盖签发、归一化、三种兑换拒绝、恰好一台主机完成配对的并发兑换、认领之后失败的设备写入、限定到单个租户的列举、撤销及其重复、跨租户撤销、区分已撤销与未知的令牌认证,以及每一种准入拒绝——达到该包语句、分支、函数与行的 100%。

四项变异对照证明这些用例确实在做判断:去掉有效期拒绝、忽略失败的认领、撤销时不检查租户、把认领移到设备写入之后,各自都会让至少一个用例失败,随后实现被还原。

## 结果

`DeviceId` 现在能解析到东西了。一旦准入解析设备,工作区授权的设备检查比较的就是断言的声明与租户创建的记录,而不是另一个声明——但准入目前还不解析。

这正是本笔记诚实的边界。`admitDevice` 已经存在,而运行路径上没有任何调用方:`dsh-run-admission` 仍然原样透传 `deviceId`,一次指名了未配对设备的运行,与此前一样会被准入。规则被写在记录所在之处,是为了让准入那一片只需要调用一样东西,而不是让两样东西彼此吻合。

同一片作为第一片的性质带来另外三处较小的空缺。已兑换和已过期的配对码留在介质上,因此持续签发配对码的部署会让该表不断增长,直到出现类似 `evictNonces` 为重放随机数提供的清扫。设备终身持有一个令牌,因此替换泄露的令牌意味着撤销该设备,再以新的 id 重新配对主机。而设备配对时仍然没有任何东西签发*工作区授权*,那正是授权那篇笔记所说"无人做"的另一半。
