# Agent Note: 没有人在选择路由

Status: proposed

[English](2026-09-10-nobody-chooses-a-route.md) | 中文

## 问题

R3 剩下的事项是能力匹配与账户授权回退,其前置条件是至少存在两条真正可互换的 Agent 路由。这个前置条件现在已经满足,而该事项依然被阻塞——被另一件事阻塞。

两条路由是可互换的。`dsh-llm-pi-ai` 是一个多提供方适配器,它手工声明的路由无需改代码,因此部署仅凭配置就能在 `dsh-llm-deepseek` 旁边立起一条 OpenAI 兼容路由。两者都被指向同一个 `dsh-llm-mock-server`,并被交付携带同一份工具 schema 的同一段对话;两者都接受了它,也都流到了终态 finish。`dsh-llm-claude-cli` 依其自身 README 留在这个集合之外:它拒绝对话历史与工具 schema,因此无法服务主循环。

不存在的,是一个**选择路由的地方**。

受管运行的提供方与账户抵达时就已经被决定了。`ExecutionAssertionClaims` 恰好携带一个 `accountId` 与一个 `provider`,两者都在签名之内,而 `admitRun` 读取它们而不是挑选它们。`RunScheduler.startChildRun` 复制其父代的:子代指名 `account.provider` 与 `run.accountId`,并且不得指名其他任何值,这正是 R3 的预算与工作区工作已经确立的子集规则。`packages/control-plane` 中没有任何东西在运行时查询 `selectDefaultProviderAccount` 或账户的 `isDefault` 标记;默认的存在是为了让管理 API 记录它、让人去读它。

而确实存在的那两套路由机制都只能拒绝。`dsh-tenant-route-policy` 通过 `LlmRuntime.guard()` 强制执行精确的 provider/model 允许清单,而那道接缝被明确记载为单调的:每个守卫都可以拒绝,而没有守卫能强行放行另一个守卫拒绝过的调用。`tool-subagent` 的 `assertAllowedModelSelection` 在上一层是同样的形状——它把模型所请求的路由与一份清单核对,而在没有显式选择时静默返回。

于是「回退到下一条已授权路由」无处可跑。守卫无法替换路由,它只能否决。允许清单无法对候选排序,它只能包含它们。而决定提供方的那个值,被签进了一个在本仓库任何代码看到请求之前就已铸造的令牌里。

## Proposal

在建造任何会做选择的东西之前,先决定由谁来选择。

有三种设计回答这个问题,它们的差别在于断言意味着什么,而不在于匹配器怎么写。

**由铸造断言的控制面选择。**签发断言的组件挑选账户,于是签名令牌继续恰好指名一个。能力匹配与回退成为它的问题,而本仓库除了「别动这道接缝」之外一无所获。这是最小的改动,而它把该特性完全移出运行时——如果回退必须对运行时最先看到的失败做出反应(在分发时失败的凭据、结果上并不具备某项能力的路由),那这样做就是错的。

**断言指名一个集合。**`accountId` 变成这次运行可以动用的账户集合,有序,而准入挑选其中第一个账户可用、且其模型能服务该请求所需能力的。子集规则依然成立:子代可以指名其父代集合的一个子集。这把回退放在观察到失败的地方,并把决定保留在签名之内,因此调用方仍然无法扩大它。代价是改变断言格式、改变 `claims.accountId` 的每一个消费者,以及每次运行指名一个账户的那些审计记录。

**由 Harness 提供候选。**`dsh-llm` 或 `tool-subagent` 增长出一个扩展点,向已注册策略索取一份有序候选清单而不是一个是或否,而 Candy 依据租户的账户与允许清单来回答。这是唯一一种能力匹配可以使用注册表已知信息的设计——`resolveModel` 为每个精确模型回答上下文窗口、默认最大 token 与推理力度——而无需 Candy 复制一份模型目录。它同时也是对一个有文档的 Harness 扩展点的改动,受 `docs/architecture.md` 管辖;而且除非准入也被教会这个集合,否则断言上的提供方会与实际使用的路由不一致。

无论选择哪一种,能力匹配都应当只匹配注册表今天能回答的东西:一个精确模型的上下文窗口、它的默认最大 token,以及它的推理力度。工具支持与输入模态不在 `LlmResolvedModelInfo` 中,因此要按它们匹配就得先把它们加进去,而那是第二个决定,不是这一个。

## Alternatives considered

**现在就针对只能拒绝的守卫建造匹配器与回退。**否决,因为守卫做不到。`LlmRuntime.guard()` 被记载为单调的——没有守卫能强行放行另一个守卫拒绝过的调用——因此想要替换路由的守卫只能否决该请求,然后指望别的东西用另一条路由重试。没有任何东西会重试。

**把账户的 `isDefault` 标记当作选择规则。**否决:它已经另有所指。默认是管理 API 记录下来、供人看出某个提供方偏好哪个账户的东西,而 `selectDefaultProviderAccount` 为每个租户与提供方恰好保持一个。把它读成运行时的路由选择,会让租户的显示偏好悄然压过一个已签名的声明。

**让断言保持单数,通过铸造第二份断言来回退。**以重放为由否决。断言的 nonce 只能用一次,并在准入时被花掉,因此回退将需要每次尝试一份新令牌,也就意味着运行时自己铸造断言——那是控制面的权限,也正是受众绑定存在所要防止的那一件事。

**从提供方 id 推断工具支持。**作为本仓库已两次避开的那种猜测而否决。Claude CLI 的工作发现了三处与合理假设相反的行为,而 Codex 的录制在没人会去看的地方发现了用量。注册表没有陈述的能力,是应当加进注册表的能力,而不是应当预测的能力。

**什么都不记录,等某个部署提出要求再说。**否决,因为计划所陈述的那道门槛——两条可互换路由——现在已经满足,于是下一位读者会据此断定该事项已经就绪,然后以艰难的方式发现这一点。

## Acceptance criteria

- 三种设计之一被记录为已决定;若选择第二种,则连同断言格式的后果一并陈述。
- 能力匹配会拒绝其精确模型无法服务某项既述要求的路由,使用 `LlmRuntime.resolveModel` 而不是 Candy 自己的目录,且拒绝会指名该要求与该路由。
- 账户授权回退会跳过其租户账户缺失或已撤销的路由,并继续到下一条已授权路由,而跳过会按租户被记录。
- 被委派子代的候选集合是其父代的子集,并由一个「子代指名了父代所不能指名的路由」的用例证明。
- 一次真实组合驱动两条可互换路由:第一条不可用,第二条服务该请求,而租户的审计踪迹指名两者。
- 没有任何东西强行放行 `LlmRuntime.guard()` 拒绝过的调用;守卫仍然是最后一道门。

## Risks

**先建匹配器。**没有调用方的能力匹配器是没有归属者的抽象,本仓库的包规则拒绝它。它还会在不知道哪种设计将消费它之前,就把能力词汇表固定下来。

**按注册表并不携带的能力去匹配。**工具支持是路由器最想要的能力,也正是 `LlmResolvedModelInfo` 没有陈述的那一项。从提供方 id 推断它,就是 Claude CLI 与 Codex 两项工作都避开的那种猜测。

**回退掩盖配置错误。**每次请求都悄悄回退的路由看起来很健康,而租户的主账户可能已经坏了一个月。每一次跳过都需要抵达审计踪迹,而那也正是让该特性可被测试的东西。

**回退跨越租户边界。**候选集合必须来自已校验的声明与租户自己的记录,绝不能来自请求字段。这正是断言格式存在所要守住的 confused-deputy 规则,而集合值声明比单个 id 是更大的出错面。

**改变一个签名令牌的含义。**第二种设计重写了每一个下游消费者都信其为单数的那个字段——池键、凭据查找、审计记录、子代子集检查。一次迁移只要让其中任何一个继续读取第一个元素,就会在一个集合形状的名字之下悄然重新引入单账户行为。
